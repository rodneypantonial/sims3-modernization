# 60. Routing world state for async routing (H6, T-RT-a)

Written 2026-10-16. Static only: Ghidra headless on a copy of the ui4 project (`game-copy/ghidra-rta`, symbols CSV imported first), Steam 1.67 `TS3W.exe`. The game was not run. Builds on docs/18 (H6 plan, S0), docs/33 (physics), docs/38 (world, lots), docs/45 (object id hash) and `native/ts3native/routegate.cpp` (S2a).

Tags: **[verified]** = seen in disassembly or decompile (address given). **[inferred]** = reasoning still to confirm by a probe or a run.

Method: one scratch Ghidra script (not committed, kept in the session scratchpad) that (1) lists every `Lock_Acquire 0x4E16F0` call with `0x918` in the 20 instructions before it, (2) gives each function a thread class by forward reach over direct calls (sim = every `IC_*` plus `MonoScriptHost_Simulate 0xD81840`; main = `WorldService_Update 0xC7E3C0`), (3) walks callers backwards from routing state functions and stops at call edges inside a `+0x918` window, (4) prints the shortest unprotected call path from an entry to a state function. A window is acquire to the **last** release in address order; this run uses that instead of S0's "next release", because early-exit releases otherwise make locked calls look unlocked. Limits: direct calls only (no vtables), address-order windows, no data-flow on `ecx`.

A site is therefore uncovered when (a) it runs on another thread, or (b) its first routing touch is neither `+0x918` nor one of the 12 gate sites, or (c) the state has no routing lock at all.

### 1.4 Uncovered sites ranked by risk

1. **Physics quadtree ray path** `0x686CC0 -> 0x681820` from the planner (`0x6583E0`), the goal step and `IsPointRoutable` [verified path]: written by every object move with no lock. Highest frequency. Fix: proxy `0x686CC0` like `0x83B3A0` (docs/33 §5).
2. **Terrain cell shape swap** on the main thread vs the worker's `0xC2A570` [verified both sides]: no lock on either thread, so no gate can cover it. Fix: docs/38 C1 (deferred release of the old shape), which also fixes today's sim-thread race.
3. **`LotTable_Contains 0x628A90`**: ungated lot-table read on 370 sim-thread functions, run before the gated insert [verified]. During a job that inserts a lot, a rehash frees the buckets [inferred]. Fix: add it as gate site 13 (prologue to read and check first).
4. **Object id hash** through `Portal_LockState` and `FootprintLockKeyById` [verified unlocked, docs/45]. The worker reads it while sim-thread creates and destroys objects. Fix: proxy `Portal_LockState 0x64F2C0` to the sim thread, or resolve ids before the job.
5. **World manager lot list** `0xC68960` (dirty check and reads with no lock; rebuild under `[WM+0x228]`) [verified]. Rare (only after a lot change), but main and sim both rebuild. Fix: worker takes `[WM+0x228]` around ApplyPendingUpdates, or the sim thread runs ApplyPendingUpdates before handing off the job.
6. **Save and BuildRoutingData** rewrite the road graph and lot data with no lock [verified paths]. Rare. Fix: drain jobs and refuse new ones while a save or `BuildRoutingData` runs (same hook as world unload, docs/18 hazard 6).
7. **Build/buy exit map free** (`0x82C630` unlocked branch) and **bulldoze / lot activation** footprint and portal writes after an ungated read [verified order]. Rare. Fix: coarse gates on `RoutingSystem_OnExitBuildBuy 0x835240` and `RoutingSystem_RebuildLotRouting 0x835110`.
8. **World flag bytes** `+0x976..+0x97F` read and `+0x97F` written outside the lock [verified]. Benign unless the job writes them [inferred]; check in S2 Verify.
9. **Main-thread debug display** reaching `LotTable_GetOrInsert`: debug-only [inferred].

### 1.5 What a full gate must include

- The 12 S0 sites, plus **`LotTable_Contains 0x628A90`** (13) and coarse gates on **`0x835240`** and **`0x835110`**.
- Worker proxies to the sim thread: `0x83B3A0` (as designed), **`0x686CC0`** (ray path), **`Portal_LockState 0x64F2C0`** (id hash).
- Not gateable, so fix at the source: terrain cell swap (docs/38 C1), world manager lot list (take `[WM+0x228]` on the worker or apply pending updates on the sim thread first).
- Lifecycle: drain jobs and refuse new ones during save (`Save_WritePackage 0xAAC110`), `IC_World_BuildRoutingDataImpl`, world load (`RoutingWorld_LockedOp_WorldInit 0x829410` runs on the main thread) and teardown (`RoutingWorld_Clear 0x82D140`, `DestroyPlanners 0x8299E0`).
- Gate stubs must tell sim from other threads: plain wait off the sim thread (main-thread debug path), pumping wait only on the sim thread.
- S2 Verify additions: per-thread counts at the three new sites, worker calls of `0x681820` that bypass the proxy, and writes to world `+0x97F` while a job runs.

## 2. Closure design per uncovered site (T-RT-b)

Written 2026-10-16. Static only, game not run. Ghidra headless on `game-copy/ghidra-rtb` (copy of rta, symbols CSV imported first), four scratch scripts (direct-call reach, caller lists, short listings, writers of `+0x97F`, `P+0x10E` and `WM+0x1CC`, absolute writes reachable from the physics readers), kept in the session scratchpad. Every hook prologue below was read from `game-copy/bin/TS3W.exe` itself (VA to file offset through the section table; SHA-256 prefix `10b2423e`, Steam 1.67) and matches; none of the stolen bytes has a relative operand. "Job live" means a worker job runs (`g_callerTid` set or `g_async.state == A_RUNNING`), as in `routegate.cpp`.

### 2.1 New facts that change the §1.4 fixes

- **A proxy is slow in async mode** [verified, `ts3native.cpp`]. In sync mode (Mode 1) the sim thread waits in `RunPlan` and serves each worker request at once. In async mode the owner thread serves requests only in two places: a READY poll (`GetOptionHook`, once per poll of the sleeping Sim's task) and a `Lock_Acquire` that would block (`LockAcquireAsync`). A proxied call therefore waits until the sim thread's next poll or blocked acquire, up to about a sim tick [inferred], so a plan that makes N proxied queries can take about N ticks. Proxies are fine for rare calls (the managed portal-lock callback) and wrong for per-node queries. This replaces the `0x83B3A0` proxy of docs/18 S0 and the `0x686CC0` proxy of §1.4 #1 with a worker-side lock (2.2 #1).
- **The physics readers are pure and do not wait** [verified, direct calls]. Nothing reachable from `PhysicsWorld_RayCastVertical 0x686CC0` (7 functions) or `Routing_PhysicsRangeQuery 0x83B3A0` (23 functions, depth 5) writes an absolute address. Nothing reachable from `Routing_PhysicsRayVertical 0x6583E0` (the only caller of `0x686CC0`) or from `0x83B3A0` calls managed code (`0xD75FA0`, `0xE5A600`), `Portal_LockState` or the synchronous remote call `0x7D98C0`. The only lock `0x6583E0` can reach is `[WM+0x228]`, through `World_GetHeightAt -> WorldManager_LotGridLookup -> WorldManager_RebuildLotIndex`. `0x83B3A0` reaches no lock at all. Neither function reaches the other.
- **The quadtree mutators are three leaves** [verified]: `Realm_AddShape 0x6823E0`, `Realm_RemoveShape 0x682080` and `LooseQuadTree_Reinsert 0x6819B0`. Each has one indirect caller besides the direct one. That caller is most likely the cross-thread message path of docs/33 §4 [inferred], so hooks on the leaves catch both inline writes and marshalled ones.
- **The job reads the object id hash directly, not only through `Portal_LockState`** [verified paths]: `IC_Route_Plan -> Route_StartPointsFromPosition -> 0x75D920 -> ObjectService_FindById`, and `Route_GoalStep -> 0xB793F0 -> 0xB74D10 -> 0xB74A20 -> FindById`, which also runs inside `0x6583E0`. `ObjectIdHash_Insert 0x939170` stores `node->next` (`0x9391A7`) before the bucket head (`0x9391AE`), so a reader without a lock sees either the old chain or the new one on x86 [verified asm; x86 store order]. `ObjectIdHash_EraseNode 0x938D00` has one caller, `ObjectService_DestroyById 0x939420` [verified]. `DestroyById` is reached from the sim root (`MonoScriptHost_Simulate -> Animation_SACSPass -> Animation_DrainDeferred`) but not from the main root `WorldService_Update` (depth 12) [verified].
- **`Portal_LockState` needs no proxy of its own** [verified callers]. Its cache `PortalLockCache_Find 0x64F1E0` is called only from it, and it is called only from `Portal_IsLocked 0x64F550` and `Portal_IsDiscouraged 0x64F570`. Their callers, `PortalEdgeCost 0x634500` and `0x632460`, belong to the lot planner, so the job lock and the gate leaves already serialize them. What is left is its `FindById` (covered by #4) and its managed callback (proxied as in 0.7.1; slow in async, but it runs only on a cache miss).
- **`RouteManager_FootprintLockKeyById 0x82B3E0` needs nothing** [verified callers: five `IC_RouteManager_Footprint*LockKey` ICs, sim only]. It only reads the id hash, which is safe next to worker reads. The lot table and the `+0x8BC` map it touches next are reached after gate site `0x62EAB0`.
- **The job never writes the world flag bytes** [verified]. Only three instructions write `+0x97F`: `RoutingWorld_LoadTuning 0x82F910` (sets 1), `ShouldUpdateObjectFootprint 0x82A720` and `ShouldUpdateSimFootprint 0x829A60` (set 0). The job does not reach either footprint function (depth 14 from `IC_Route_Plan` and from `Route_GoalStep`). It reads `+0x97E` (`Route_PlanLocked +0xA`). Byte stores and loads are atomic, so §1.4 #8 is closed and needs no hook.
- **`RoutingWorld_ApplyPendingUpdates 0x82C420`** [verified listing] calls `WorldManager_GetLotList` with `ecx = [world+0x964]`, so `+0x964` holds the world manager. This corrects the "current lot" guess in §1.1; the meaning is inferred from the callee. For each lot it calls `0x631A60` and then `0x82B590`, and it clears `P+0x10E` at the end. It reaches no managed call and no remote call. The only locks it reaches are `[WM+0x228]` (through the rebuild) and gate `0x62EAB0`. `P+0x10E` is set to 1 only by `0x6236D0`, `PathPlanner_Init 0x62E860` and `LotGraph_Build 0x63CB90`, which is a gate site the job can run itself.
- **The lot index has three rebuilders** [verified paths]: the main thread every frame (`WorldService_Update -> WorldManager_Update -> WorldManager_ScoreAndStreamLots -> 0xC68680`), the sim thread (`Locomotion_Notify -> 0x829A60 -> World_LotLookup -> LotGridLookup`) and the job itself (`Route_GoalStep -> Terrain_GetHeight -> LotGridLookup`). The dirty flag `WM+0x1CC` is set by `WorldManager_DetachLot 0xC65830`, `WorldManager_MarkLotIndexDirty 0xC5FEC0`, `0xC65700` and `WorldManager_Init`. `DetachLot` is reached from neither root, so its thread is still open. The rebuild reaches no managed call and no remote call.
- **The cell shape swap** [verified listing]. `WorldCellGrid_SetCellShapes 0xC2A840` runs `mov ecx,[esi+0x38]; test; jz; call PhysShape_Release 0x682760` (return address `0xC2A896`), zeroes `+0x38`, builds the new shape and stores it at `0xC2A99B` or `0xC2AA9A`. `PhysShape_Release` and `PhysShape_AddRef 0x682750` change the count at `+0x4C` without `lock`.
- `RoutingDebug_FrameUpdate 0x818EA0` returns with a plain `RET` (no arguments) [verified, `0x819097`/`0x8190BF`].

### 2.2 Closure per site

Bytes are the stolen prologue: the shortest run of whole instructions of 5 bytes or more. All checked in the exe file. Several sites already carry a ts3native detour (`[HeightCache]` on `0xC2A570`/`0xC2A840`; `[Verify]` timing probes on `0x6583E0`, `0x686CC0`, `0xC2A840`, `0xC688A0`, `0x939170`). `InstallDetour` refuses changed bytes, so each address gets **one** stub. The closure stub owns the address, and a Verify probe on the same address counts from inside that stub instead of installing its own detour.

### 2.4 First async milestone (M1): only a quiet world

Async START is allowed only when all of the following hold. Otherwise `Route.Plan` stays synchronous, which costs nothing and changes nothing.

- Live mode, not build/buy, `g_rtBusy == 0` (no save, `BuildRoutingData` or lot save running), and no world load or teardown (existing docs/18 scope).
- **No pending lot updates** (`[[world+0x95C]+0x10E] == 0`) and **a clean lot index** (`[[world+0x964]+0x1CC] == 0`, after the sim thread's own `GetLotList(0)` when dirty). The worker's `ApplyPendingUpdates` then only reads the flag, unless the job's own lazy lot build sets it again (`vfRtPendingInJob` counts that).

Closures M1 needs anyway, because START cannot rule out their writers: #1 (object moves every tick), #2 (camera driven), #3 and #7 (the gate), #4 (destroys), #6 (a save requested during a job), #9. M1 can do without #5's worker holds, because START refuses a dirty index and counts any dirtying during a job. If `vfRtLotIdxRebuildInJob` or `vfRtPendingInJob` is non-zero in the M1 runs, build #5 before S5. Abort rule for the M1 run: any non-zero `vfRtQtBare`, `vfRtTeardownInJob` or `vfRtGateOffSim`, or any crash in `0x681xxx`, `0x67Exxx` or `0x939xxx`, stops the run (stop-on-error rule).

Names: 4 new rows in `tools/ghidra/symbols/ts3w-1.67.symbols.csv` (tag `<docs/60 §2>`): `Routing_PhysicsRayVertical 0x6583E0`, `LotTable_LotHasPendingUpdate 0x631A60` and `RoutingWorld_ApplyLotUpdate 0x82B590` (both `[unverified]`, named from their use in `ApplyPendingUpdates`), and `WorldManager_MarkLotIndexDirty 0xC5FEC0`.

### 2.5 S5 drain point: travel and world unload (PLAN gap 5)
