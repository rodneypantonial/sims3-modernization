# 50. Object lifecycle: create, script Init, scene add, destroy (M-CORE2b)

Static map of TS3W.exe (Steam 1.67) on a Ghidra copy with our symbols (docs/45 names applied), plus a read of the decompiled ScriptCore and Sims3GameplaySystems assemblies for the managed half. No game runs. Sim-thread costs come only from the existing `probe-out/profile/*simstack*.jsonl` files (35 files, 10,251 samples: BP 3,401, SV 1,723, IP 4,451, SI 676), counted by **leaf frame only** (docs/45 §6 caveat: stack-scan "inclusive" numbers are stale-stack artifacts for small, frequent functions). 1% of sim samples is about 10 ms/s (docs/28).

## 1. Summary

- **Five ways in, one shape** [verified]: every create path is `ReserveId` -> component mask -> `Object_Allocate 0x9361D0` (one block, component ctors in place) -> a per-component pass through a component vtable slot -> object event(s) through `GlobalHandlerChain 0x936C90` -> `ObjectService_AddObject 0x939830` (AddRef, unlocked id hash insert, event 4). The paths differ only in the per-component slot: `+0x04` init (script create), `+0x08` load from stream (lot load), `+0x10` load from resource (catalog / inventory), `+0x00` copy (clone), and `+0x18` finish (resource-backed stream objects).
- **Everything runs on the sim thread** [verified call graph for every caller found; thread from docs/38 and docs/28 §5]. No lock is taken anywhere in create or destroy except the `LOCK`-prefixed refcount at `+0x04` and whatever the allocator and resource system take inside [verified].
- **Native work per object is small.** In the existing profiles (steady play, no world load, no camera pans) every lifecycle function together is at most **0.24% leaf** (25 samples), most of it object-resource lookups (`0x93B9A0`/`0x93BD50`, 0.12%) [measured, leaf, upper bound]. None of the samples hit `Object_Allocate`, the component passes, `DestroyById` or `Object_Destruct` as leaf.
- **The scene add of a lot activation is cheap natively.** `Lot_UpdateObjectSceneNode 0xABFAC0` does a component lookup and an LOD pick, then either records a deferred LOD entry in a hash map or fires object event `0x14`. **No native code registers a handler for event `0x14`**: the only writer of the handler table is `ObjectEvents_Register 0x936BC0`, it has 13 call sites, and they register only events 0, 1, 2, 7, 0x0E, 0x13, 0x18 (Slot component) and 0, 1, 2, 7, 0x1A, 0x1C (Sim component) [verified: xrefs and push operands]. So the `0x14` chain is empty and returns at once [inferred at runtime: no other writer exists in the exe]. This answers docs/48 §1's open "listener -> scene link": there is no native listener; the lot renderer handle comes from `0xAE05D0`/`0xAE0600` and is only passed along.
- **Correction (docs/61, docs/data/results/2026-10-16-queue-lotstream.md):** the lot-add scope messages `0x4C55E8C`/`0x4C55EFA` have **no listener** (byte scan of the whole exe plus the handler-registration scan), so a lot add runs **no managed code** [verified, docs/61 §1]. The native lot add was then measured small: with S3SS lot streaming off, 2 lot adds of 284 objects took 389 µs in total (about 1.4 µs per object) [measured]. The inference in the next bullet, that script work inside the scope causes the lot-add spike, is therefore doubtful; script `Init` (below) still applies to script-created objects, not to the scene add.
- **What a lot add costs is therefore the script side** [superseded, see the correction above]. `Lot_AddLotObjectsToScene 0xAC1130` wraps the object loop in a script message scope (`ScriptMessageScope_Begin 0x7D2DB0` / `_End 0x7D2DF0`, ids `0x4C55E8C`/`0x4C55EFA`, posted through the script host vtable `+0x18`) [verified]. Whatever C# does for those two messages, plus the object loop, runs in one remote-call pump pass with no deadline (docs/28 §5.2 step 5). Per object the native part is a few lookups [verified code shape]; the per-activation spike must come from the script messages or from the pump draining several lots at once [inferred, to measure].
- **Script Init is the expensive per-object step for script-created objects** [inferred from the managed code]: `ScriptProxy.CreateLogic(className)` -> `SubstituteClass` -> `TryCreateLogic`, which calls `Assembly.CreateInstance(className)` on **every loaded assembly** until one succeeds, then `IScriptLogic.Init(postLoad)`; for a `GameObject` that is `UserToolUtils.GetProduct` (catalog lookup), `OnCreation` or `OnLoad`, `LotManager.PlaceObjectOnLot`, `OnStartup` and each object component, all in the Mono interpreter (docs/29: no JIT).
- **Lot load (world load) defers script creation.** `ScriptComponent_LoadFromStream 0x950280` does not create the managed proxy; it appends (object id, class name) or (object id, saved handle) to a pending list in the script host (`0x9501B0`, `0x94FCE0`) [verified writes; the consumer that drains the list is not traced]. The native part of a lot load is `LotObjects_LoadFromStream 0xC70320` -> per object `ObjectService_CreateFromStream 0x939B60`, with a loading-screen tick every 32 objects (`WorldLoad_ProgressTick 0xC5FB60`) [verified].
- **Destroy is immediate, not deferred**, except in two places: `Animation_DrainDeferred 0x571A50` (docs/22) and lot load placeholders flagged `0x400000` that are destroyed after the whole lot is read [verified]. `DestroyById` fires event 5, tells an optional owner (`+0x30` of the caller, vtable `+0x3C`), removes the object from the update list, sets the destroyed flag, erases it from the hash, fires event 6 and drops two references; memory goes back only when the last reference drops (`Object_DeletingDtor 0x935DF0` -> each component's vtable `+0x2C` -> service allocator `+0xC`) [verified].

## 3. Refcounts

- `+0x04` is changed only with `LOCK` instructions; dropping from 1 sets it back to 1 and calls vtable slot 0 with 1 (deleting dtor) [verified, every path above]. `RefPtr_Release 0x7460F0` and `RefPtr_Assign 0xB96150` are the smart-pointer helpers used by the create paths [verified].
- A live object has at least one reference from the hash (`AddObject` AddRef, `DestroyById` drops it) and one from its creator; `CreateObject` returns with the creator's reference held, `CloneObject` drops its own after `AddObject` [verified].
- `FindById` does not AddRef (docs/45 §4): a pointer held across a `DestroyById` stays valid only while someone else holds a reference [inferred].

## 4. Per-object cost drivers

Ranked by expected cost, static reading plus the leaf samples.

1. **Script `Init` (paths A2, C3)** [inferred; not part of the lot scene add, which runs no managed code (docs/61)]: reflection by name over all assemblies, then the full interpreted `GameObject.Init` chain. This is per object, every time, and the managed half is invisible to native leaf counts (it shows up as interpreter and GC leaf time, docs/29).
2. **Resource-backed lookups (paths B, C)** [measured 0.12% leaf in play; inferred larger at world load]: `ObjectResource_Load`/`ResolveSpec` fetch synchronously through the resource system (resource lock and RefPack decode, docs/39), up to three tries for missing content.
3. **Component passes** [verified shape]: one virtual call per component per pass, two or three passes per create. Cheap in native terms; the Model and Footprint loads may queue resource work [inferred].
4. **Script messages around lot add and for missing objects** [inferred]: what C# does with `0x4C55E8C`/`0x4C55EFA` decides the cost of a lot activation.
5. **Hash insert, events, allocation** [measured: no leaf samples]: negligible per object.

## 6. Candidates

| # | Candidate | Expected gain | Size | Risk | Next step |
|---|---|---|---|---|---|
| L1 | **Chunked lot add**: re-post the remainder of `Lot_AddLotObjectsToScene` as a **new pump job for the next Simulate pass**, not as an inline call (docs/28 §5.4: a same-thread `PostRemoteMethodCall` runs inline). Keep the message scope per chunk | spreads one activation over passes; size unknown until measured | small-medium | medium: the script message pair must stay balanced per chunk; S3SS detours the same entry | Measure ms per `0xAC1130` call and per script message with a probe (the parked `[LotStream]` build, docs/38 C4) |
| L2 | **Defer non-visible objects**: `0xABFAC0` already has a deferred path (`Lot_DeferSceneLod`); widen it with a distance or frustum test so far objects take the hash path first | fewer immediate scene events | small | low-medium: the deferred map is read by `WorldService_Update` on main (docs/48) | Only worth it if L1's probe shows the per-object part matters; native per-object work looks small |
| L3 | **Cheaper `TryCreateLogic`**: cache class name -> `Type` (or the assembly that holds it) so each create calls one `Activator.CreateInstance` instead of one `Assembly.CreateInstance` per loaded assembly | per script create; larger with many script mods (each mod adds an assembly) | small (managed patch or MonoPatcher-style hook) | low: same type is created | Count assemblies in a heavy mod setup and time `CreateLogic` with a managed probe |
| L4 | **`DestroyAll` bucket scan**: start from the last non-empty bucket instead of bucket 0 | shutdown and world switch only | tiny | low | Measure world-switch teardown first; not a stutter item |
| L5 | **Batch missing-content messages** (`0x7E44AD3` per missing object at lot load) | world load with broken CC | small | low | Only if a load with missing content shows it |

None of these targets steady-play stutter; L1 and L3 target lot activation and object spawn spikes. Per the offload goal (docs/23 #17), none of the lifecycle steps can leave the sim thread as is: the id hash is unlocked (docs/45 §5) and script `Init` needs the Mono thread.

## 8. Open items

- The native caller of `ScriptProxy.CreateLogic` (host field `+0x164C`) and the drain of the pending script-create list (`0x9501B0` writes): find with a runtime breakpoint on the `CreateLogic` method or a scalar search for `0x164C` relative to the host's secondary vtable base.
- The two vcalls in `IC_Simulator_CreateObjectImpl` (`+0x17C`, `+0x04`): the host's secondary vtable is not at `0x108B6A4` (that base gives a shutdown function at `+0x18`); resolve from `g_ScriptHostForWorldEvents`'s stored vtable at runtime.
- What the C# side does for script message `0x7E44AD3` (missing object). (The lot-add scope `0x4C55E8C`/`0x4C55EFA` has no listener: answered by docs/61.)
- Owner of mask global `0x11ECF08` (the LOD component used by `0xABFAC0` and `Query_GetObjectsOnLot_impl`): its value is set at runtime; read it with a probe.
