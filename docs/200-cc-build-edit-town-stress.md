## 2. How Build/Buy placement and delete work

- **Catalogue click** = `BuildBuyModel.SelectBuyProduct(product, hide)` -> `UserToolUtils.SetCurrentUserTool(4, productKey, ...)` + `StartForwardingEventsToUserTools` [verified static, Sims3GameplaySystems `BuildBuyModel.cs`]. Tool 4 is the native hand / placement tool; the object is created by native code when the click lands and reported back through `World.OnObjectPlacedInLot(objectId, lotId)` (WorldEvent `OnObjectPlacedInLot`) [verified static: callback registration in `World.cs`; that the native tool fires it for a Buy placement is inferred from the name, checked by the `placed` count of the first run].
- **Pattern presets**: `SelectBuyPreset` -> `UserToolGeneric(2, key, preset)` for floors, `(1, ...)` for walls, `(51, ...)` other [verified static].
- **Sell / delete**: the Buy sell button is `UserToolGeneric(12)` (`BuyController.OnSellTool`), a click on an object sells it; the native tool then raises `OnHandToolSold`, which `LotManager.OnHandToolSold` and the Interior Designer career listen to [verified static]. Hand tool = 4 with an empty key, design tool = 11, clone (eyedropper) = 22.
- **Undo stack**: native only; script sees only lengths via `World.OnUndoRedoStateChange(undoLen, redoLen)` and no script code subscribes or clears it [verified static: no subscriber in the DLLs]. Whether the native list holds deleted objects (and their resources) until mode exit is open [inferred risk, the `-empty` mark after exiting to live mode separates it from in-mode growth].
- **Catalogue icons**: docs/193 L1 (the `mCustomControlInstanceDict` pin) is refuted; L2 (cell layouts freed only by finalizers) stays, covered by `catalog_loop` and the forced-GC pairs.
- **Build items**: walls (tool 0, 25 room), floors (2), wallpaper / paint (1), doors and windows are objects (tool 4 with a wall-object product), stairs (16), terrain paint (design / terrain tools, not driven). Resource paths: products from the catalogue (`UserToolUtils.GetProductList`, `GetFloorPatternPresetListByType`, `GetWallPatternPresetListByType`); textures through the ResourceCache (docs/39, docs/198 §4).

## 3. Edit Town and lot counts

- **Lot plots are fixed by the world file** [verified static for the script surface]: `World` exposes no call that creates a lot except `World.CreateHouseboatLot(width, height, type, subtype)` / `DeleteHouseboatLot`; `EditTownModel` has place-contents, bulldoze, change type, evict, move, export, but no new-plot call. New plots are made in Create-a-World [community: CAW is a separate program that writes the `.world` file].
- **The only in-game plot growth is houseboats (Island Paradise)** [verified static]: `Gangway.ChangeHouseboatSize` creates a houseboat (+ its own lot) at a port, one per gangway; when a houseboat sails off, `Helm` / `Houseboat.UnsetPortGangway` frees the port, so another houseboat can be bought there. No houseboat count cap was found in script [verified static: no constant or check]; a native cap in `CreateHouseboatLot` is not checked [inferred open]. So the lot count is bounded by the world file everywhere except IP houseboats, where it is bounded only by what the player does (and by docs/66 address space).
- **Lot placement from the library** (`EditTownPlaceTool.PlaceLotTask`) [verified static]: `BeginPlaceLotContents(info, lotId)` (import of an export-bin package or the game bin's `LotContents`; sets the plot's lot type to the entry's) -> `UpdateRoutingData` -> `PlaceLotContents(angle, position, progress)` (`BinCommon.PlaceLotContents`) -> `EndPlaceLotContents` (commercial / residential subtype, flush of a temporarily imported export package, `EnsureLotObjects`, dirty-thumbnail update). **Bulldoze** (`EditTownBulldozeTool`) -> `EditTownModel.BulldozeLot` -> `KickSimsOffLotAndBulldoze` (`SendObjectsToProperLot`, `BinCommon.BulldozeLot`, thumbnails, 4 s sleep). Household placement uses `PlaceFromGameBin` / `PlaceFromExportBin` (pay, move-in) on top; not driven (household state, evictions).
- **What can grow in Edit Town** [inferred]: per placed lot the imported contents and their resources, lot thumbnails (`UpdateDirtyLotThumbnails`), routing data rebuilds; all bounded by the plot count, so a leak shows as growth per place + bulldoze cycle on one plot.
- **CAW automation verdict**: not with ts3agent. CAW does not run TS3W.exe's script VM with our plugin; plot creation would need driving a separate editor UI (GUI automation) and a world rebuild per test. Not worth it: the game loads a fixed plot set, so world-editing growth is measured per plot cycle in Edit Town instead.

## 5. Built (ts3agent, 2026-10-26)

| Phase | Per cycle | Marks (+ forced GC pair) | Targets [inferred] |
|---|---|---|---|
| 1 patterns | 10 CC wall patterns, 24 CC floor patterns, 3 CC doors/windows in the 10 x 4 room; sold and repainted EA | `bcc-full` / `bcc-empty` | pattern textures and materials, catalogue thumbnails (docs/40, docs/53) |
| 2 walls | a building with `levels` (3) floors and `room_size` (4) tile rooms, on `building: [lx0, lz0, w, d]` or the first free 16 x 12 / 12 x 12 / 12 x 8 / 8 x 8 area nearest the lot centre. | 3 portals | inside each building cycle: up to `doors` (72) doors, CC and EA alternating (`BuildCategoryFlags` door bit), on the camera-side face of every x-line (interior lines and the far outer wall), tiles 1 and rw-2 of each room, on every level; `stairs` (2) per level below the top (CC and EA alternating). The 16 x 12 default gives 4 x 3 rooms per level, 3 x-lines x 8 door tiles x 3 levels = 72 door slots, and 4 stairs (2 on level 0, 2 on level 1). Ladders and railings are not placed: ladders need pools or boats, and railings add little to the routing graph. Both are counted.

**Counts per mark** come from the lot and routing APIs, not from what the agent asked for. Each count covers the footprint on levels 0 .. levels-1: `walls` (unit edges with `World.WallExistsBetween`), `floor_tiles` (`World.HasSolidFloor`), `rooms` (lot-wide, `World.GetInsideRoomsAtLevel`, `eRoomDefinition.Default`), and lot-wide `doors` / `stairs` / `ladders` / `portal_objects` (`IHasPortalComponent`). The result has `walls_phase` {footprint, levels, rooms_grid, start, per_cycle [full, empty, build/remove drags, level and aim misses]} and `portals_phase` {per_cycle [doors/stairs tried, placed, CC placed, click_misses, pick_misses, aim_misses, sold, fallback_deletes, extra_deletes, full, empty]}. `walls_phase` `empty` against `start` shows what the Ctrl-drag delete left behind.

**Screen points off the ground:** `Px` calibrates the floor-pick homography on one plane: the displayed level, then the level below, then the ground. It maps a world point at any height by intersecting the camera ray (from `CameraController.GetPosition`) with that plane. This is exact for a pinhole camera whose eye is that position [inferred]. Door clicks must pass a `PickWallAtWindowPoint` check (within 0.9 m and 1.5 m in height), or they count as `pick_misses`.

Risks [inferred, first run]: Ctrl on the forwarded mouse events deletes walls and floor (the player's shortcut, never driven); `GetWorldPosition` on a level with no floor yet may return the ground height (then 3 m per level is assumed); the floor tool in tile mode paints the dragged rectangle; walls and floors on an upper level need the level below built first (`SetDisplayLevel` stops at max + 1, which shows up as `build_level_misses`); stairs from a tile-centre click may be refused (counted); the cutaway may hide inner x-lines (counted as `pick_misses`); a 2-tile EA door on a 1-tile slot is refused (counted as `click_misses`). Repro `build-cc-cycle` maxS is 1200 s (patterns ~200 s + 2 x ~300 s buildings, +50%, estimated); in queue `cc-build-items.json`, `bp-ccb-cycle` has a 24 min window, a 50 min timeout and requires 5 bcc + 2 bccw + 2 bccp mark pairs.

## 8. Scripted CC: one script assembly per item (2026-10-26, built, not run)

Goal: CC that behaves like script-heavy CC, to measure per-assembly and per-use memory (Mono images, metadata, class and vtable tables, statics, interpreter data, interaction instances, state machines, clips) in the 32-bit address space (Error 12).

**Generator** `tools/cc-gen-script.ts` (output only under `game-copy/cc-synth/`, git-ignored: it holds EA-derived IL and resources; never committed or published):
- **Sources:** base game plus every EP/SP (`<pack>/GameData/Shared/Packages`, `DeltaPackages`, thumbnails) and `Game/Bin` (jazz, ITUN, class tuning: on Steam all packs' tuning and jazz sit there). EP/SP OBJDs use group `0x08000000` etc., not 0 [verified: EP1 FullBuild]; a `DeltaPackages/pNN` OBJD is credited to the pack whose FullBuild is `pNN`. Picks: one source per cloned class, base and packs round-robin (`--ep-share`), OBJDs with a catalogue-size body (>= 1 KB) [inferred: spawners, relics, rabbit holes are ~0.5 KB; the load smoke's product count checks it].
- **Script clone (IL level, no decompiler):** `ildasm` of the script DLL (cached in `game-copy/cc-synth/.il/`), the OBJK `scriptClass` and its same-module bases up to the first class with nested `InteractionDefinition` types (max 4 classes; never `Sims3.Gameplay.Abstracts.*`, every object is cast to those) are copied with all nested types (interactions, definitions, helpers, compiler closures), renamed to `CCGenScript.S<seed>.I<n>.<Class>`; every other same-module type reference gets an `[Sims3GameplayObjects]` (or Systems / StoreObjects) prefix, except `<PrivateImplementationDetails>` (since `cc-script-100b` the referenced fields and data are copied into the clone, §8.1); `ldc.r4/r8 inf/nan` rewritten as bit patterns (ilasm cannot read ildasm's text form). The new assembly `CCGenS<seed>I<n>` carries `[Tunable]` + `[PersistableStatic]` like EA's gameplay DLLs and is built with the .NET Framework `ilasm` (fresh MVID each, checked unique). Subclass fallback (an empty class deriving from the original leaf: EA's code and animations, own type and assembly) only when ilasm fails or the class has internalcall / pinvoke / data labels; the manifest gives the reason.
- **Access checks:** none in TS3W's Mono 1.2.3 [verified static 2026-10-26: the only `MethodAccessException` raise (class name referenced at `0xE7CED8`) is the reflection invoke path "Cannot invoke constructor of an abstract class."; no `FieldAccessException` name and no inaccessible/visibility message in the exe], so clones may use EA internal and private members.
- **Animations:** a string literal followed within 4 instructions by an `Acquire`/`StateMachine` call that names a JAZZ (instance = FNV64 of the lowercase name [verified: "stove", "fridge"]) is renamed `ccgs<seed>_<n>_<name>`; the jazz is copied under the new name with its self key and every CLIP key rewritten to per-item copies (a jazz names its clips by full key [verified: "stove" jazz 148 clip keys]); literals that are clip names are renamed and copied too. The same literal used as an actor name stays (actor and state hashes inside the jazz stay the original's). Two OBJDs name their jazz by bare instance (SwingSet, Sprinkler) and get the copy's instance.
- **Tuning:** every ITUN whose `Interaction name` / `Object name` is a cloned type (or nested in one) is copied with the names rewritten (ITUNs load by KeySearch over type `0x03B33DDF` [verified static, `AutonomyTuning.LoadAllInteractions`]); class tuning XML `0x0333406C` at FNV64(full name) copied to FNV64(new name) for the class and its nested types.
- **Object:** `cc-gen.ts cloneItem` (unchanged, imported) for OBJD/OBJK/VPXY/meshes/textures/thumbnails; OBJK `scriptClass` -> the cloned leaf class; catalogue name `CCGenScript <name> #n`. Read back with cc-gen's `verifyPackage` (keys unique vs the game and the set, no stray old instance).
- **Manifest** per item: mode (`il` / `subclass` + reason), origin pack, OBJD key, OBJK class, cloned classes (orig -> new), assembly name, MVID, bytes, IL lines, interaction definitions (new and original names), jazz copies with clip counts, literals left shared (`jazzNotRenamed`), clips, ITUNs, class tunings.

**Set `cc-script-100`** (`--count 100 --seed 1 --ep-share 0.5`, 41 s): 100 IL clones, 0 fallbacks, 0 problems; 50 base + 50 from 17 packs (EP1-11, SP1-4, SP8, SP9); 233 MB on disk (clips 108 MB, assemblies 2.4 MB: 4-201 KB each, median 18 KB; IL 274-45,053 lines); 624 interaction definitions (1-74 per item, median 4); 128 jazz copies (77 items), 2,930 clips; 815 ITUNs, 252 class tunings; 100 distinct MVIDs.

### 8.1 Load crash on `cc-script-100` and set `cc-script-100b` (2026-10-26)

First run (queue `cc-script`, 01:56-02:03 UTC, asi `allocsites2`): `bp-ccs-nocc` PASS; `bp-ccs-load` and `bp-ccs-cycle` both died ~18 s after launch, before the main menu (`probe server exited (0)` = the game was gone), with the same EA report: ACCESS_VIOLATION reading `0x10` at `0xE7A349` [verified: `xcpt ... 26-10-26 10.01.23.txt` and `10.02.34.txt`]. No ScriptError file was written. Details in docs/67 §19.
- **Where:** `0xE7A349` is in Mono's `RuntimeHelpers.InitializeArray` IC `0xE7A330` (name/function tables `0x10B546C` / `0x10B5E04`), called by the interpreter (`0xE591D4` <- `0xE5A48E` <- `interp_runtime_invoke 0xE5A600`). It reads `field->data` (`+0x10`) of a NULL field handle [verified disassembly].
- **Why:** 17 of the 100 clones run array initializers (`ldtoken field [Sims3GameplayObjects]'<PrivateImplementationDetails>{B044CCB2-...}'::'$$method0x...'` + `InitializeArray`, mostly in `.cctor`s), and the generator left those refs pointing at EA's assembly. That type name carries a per-compile GUID. The installed simler90 core mod (`simler90GameplayCoreMod-UPDATE242-Steam.package`, which `content no-cc` does not stash) ships its own recompiled `Sims3GameplayObjects` / `Sims3GameplaySystems` with `{B67F5F42-...}` / `{E8701302-...}` [verified: extracted with `tools/extract-assemblies.ts`]. So the ref resolves to NULL and the first such static constructor faults. Without simler90 the clones would have run [inferred].
- **Fix (`tools/cc-gen-script.ts` `pidSubset`):** each clone gets its own `<PrivateImplementationDetails>{GUID}` type. It holds only the fields the cloned code references, their `__StaticArrayInitTypeSize=N` types and their `.data` blobs (`parseIl` now keeps `.data` entries; each blob's byte count is checked against the type's `.size`). The refs stay unprefixed, so they resolve inside the clone's own module. Switch-on-string dictionary fields are now per clone (EA code fills them lazily). If a copy is incomplete, the item falls back to a subclass with the reason in the manifest. The self-check covers the subset, the data parse (with `)` in comments) and ilasm.
- **Set `cc-script-100b`** (same arguments, 42 s): 100 IL clones, 0 fallbacks, 0 problems. 17 assemblies use InitializeArray. After an ildasm round trip, none has a cross-assembly `<PrivateImplementationDetails>` ref, and all 68 copied data blobs are byte-equal to EA's [verified]. Every `[Sims3GameplayObjects]` / `[Sims3GameplaySystems]` type and member name the 100 clones reference also exists in simler90's assemblies [verified, string-level check]. `cc-script-100` is kept as it was. Queue `cc-script.json` points at `cc-script-100b` (dry-run ok, not run).
- **Lesson for scripted-CC generators:** never reference compiler-generated names (`<PrivateImplementationDetails>{GUID}`, `<>c__DisplayClass`, cached delegate fields) across assemblies. Core mods recompile EA's DLLs, and real script CC has the same exposure.

## 11. Steady-state leak test: same set vs fresh set (2026-10-26, built, not run)

Goal (Rodney): add items, remove them, add the same number again, several times. Once caches have filled, the full marks (peaks) and the empty marks (troughs) should repeat. Growth from cycle 2 on = leak; steps that shrink = a cache settling; largest free shrinking while free stays = fragmentation.

**How `live-cc-cycle` picks items** [verified static, `ContentHandlers.cs`]: the same items every cycle. Its 4 `place_objects` calls use skip 0 / 100 / 200 / 300 only to get 400 distinct products inside one cycle (catalogue sorted by key, so a skip picks the same products every time); `wear_parts` uses nth 0 every cycle (Sim i wears part nth + i of the sorted pool list per body type); `buy_object pool` uses nth 0 / 25 / 50 / 75 every cycle. Two things were not fixed: the Sims (`sim: "town"` = active household + the instantiated Sims at call time, sorted by id: townies that come or go between cycles change the set and the index of every later Sim, so parts move between Sims) and object positions (`FindGoodLocationNearby` from each lot's centre: the same as long as the lots look the same).

**Agent change:** `wear_parts {sim: "town", remember: "<name>"}`: the first call stores the picked Sims (SimDescriptionIds and their index); later calls with the same name dress exactly those Sims at the same index (so the same parts), and report a remembered Sim that is no longer instantiated as an error row instead of picking another one. Kept until a reload.

**Repros** (`tools/harness/repros.json`, cc-2k-v2, 6 cycles, ~2.5 min each; the CAS pool = all 1000 cc-2k-v2 CAS parts: af Hair 166, af Top 334, ef Hair 166, ef Body 167, tf Body 167):

|---|---|---|
| objects (150 per cycle over the town) | CCGen #0-149 every cycle | skip c x 150: #0-149, 150-299, ..., 750-899 |
| CAS (25 remembered Sims, Hair + FullBody + UpperBody) | nth 0 every cycle | nth c x 25: no part twice in a 166+ list |
| inventory (25 into the active Sim) | pool #0-24 every cycle | pool #c x 25 (150 of 200) |

Per cycle: objects + Sims dressed -> `<p>-full`, `remove_objects` + `restore_outfit all` -> `<p>-empty`, inventory -> `<p>-inv-full`, remove -> `<p>-inv-empty`; `mem_gc` (gc-before / gc-after) after every mark. Precondition, written in the job note: both fixes installed when the queue starts (`node tools/setup/install-fixes.ts install --only user-cc,store-repacks-test` otherwise), and no leftover content stash manifest (`queue.ts --restore-content`).

**Pass per job:** the `alloc sites on` line (EA heap hooks 4/4, ntdll hooks 7), `diag: mem` load + `ccn-loaded` + `gc-after` lines, `allocsites:` `gc-after` `sum` and `usum` lines, no `FAIL` / `SKIP alloc sites` / `!` metric, no crash.

**Report** `node tools/cc-count-report.ts` (`--self-check`; newest log per job in `probe-out/queue`, or `--date`, or `--none/--k1/--k2/--real <log>`): per job at the last `gc-after` sample `free`, `big` (largest free), `priv`, `rcN`, and allocsites live MB by owner as heap MB / virtual+map MB; then deltas per 1,000 CC items (none -> 1k, 1k -> 2k, none -> 2k) and none -> real per 1,000 resources. Owners: `catalogue` (`World/Catalog/*`), `CAS`, `LocStr` (string tables), `ResourceSystem` (packages, indexes, ResourceCache), `ResourceLoad` (AsyncLoader, PackedStream), `Mono`, `other`, `untracked` (`usum` private + map). The build drops EA tag strings (docs/190 §8), so the owner is the TS3W.exe address range of the row's `at` (its `from` when `at` is inside the EA allocator `0x4E3000-0x4E7000`): docs/190 §2 / §5.3 ranges and docs/201 §13.2 sites; catalogue `0xC90000-0xCA0000` and LocStr `0x59B000-0x59D000` are [inferred] around the verified functions. Limits: only the top 32 live sites are named, the rest and every DLL row fall into `other` (sum line minus the named owners); heap rows sit inside EA cores that are also virtual rows, so heap + virtual totals overlap (read the columns apart).
