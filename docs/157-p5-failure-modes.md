# 157. P5 / P5b / P5c failure modes and fault injection

Date 2026-10-22. Static read of `native/ts3native/p5.cpp`, `p5b.cpp`, `p5c.cpp`, `p4.cpp`, `p4clone.cpp`, `replay.cpp` and the routing call path in `ts3native.cpp`, plus new selftests; no game run. Ledger §244. Background: docs/94 §19-§22 (P5 refusals, lazy stop, faults, tripwires, nr skew, mod guard M2-1..M2-3, VerifyEvery, P5b/P5c windows), docs/88 design G, docs/67 §10 (crash H) and §11 (crash I).

Question: in how many ways can Mode=2 (P5), the lent lock (P5b, `ReleaseLock=1`) and FreeLock (P5c) fail in a live game, where is each failure caught, what does the code do then, and does a test prove it.

Result: 21 failure modes. Before this work 8 had no test of their recovery path. Now all 8 are covered: by fault-injection hooks in a test-only build (`TS3N_FAULTINJ`, §2) and by new selftests. No real bug found. Three open risks remained, all by design: §3. 2026-10-23 (ts3native 0.36.35, counters v106, §4-§5): risks 1 and 2 now have guards (retake watchdog escalation, refusal-storm breaker), the lock-key writer gap of docs/156 (U1) has a cover, replayed inserts are checked against live's answer, and the clone-run fault and the live audit mismatches of the P5 verify runs are triaged.

Line numbers are the ones on this branch.

## 2. Fault injection (`TS3N_FAULTINJ`)

Test builds only. `selftest.cpp` defines it before including `ts3native.cpp`; a live probe build sets `CL=/DTS3N_FAULTINJ`. A release `ts3native.asi` contains none of it (build.cmd's release line has no define).

- `p4.cpp`: `FI_*` bits and state near `P4CloneAcquire`; `FI_OOM` turns a granted acquire into a copy failure (released to the provider, `P4_AB_MAT`); `FiInRun` (after `P4EaHeapUnlock`) runs inside `P4Guarded`'s `__try` on the worker in a Mode=2 clone run, with the P5b / P5c window open if the job lends: `FI_MANAGED` (`P4Abort(P4_AB_MANAGED)`), `FI_AV` (write through NULL; with `FI_EAHEAP` first enters EA's heap lock `[0x11CB864]+0x4E4` and bumps its depth word, crash H's shape), and selftest-only `FI_STALE` (a recorded write after the cut), `FI_CLOSE` (`rtClosing` set), `FI_BUDGET` (records `t_budget.on` in the run).
- `p5.cpp`: `P5Plan` picks the bits per plan: every `FaultInjectEvery`-th armed Mode=2 plan injects the next bit of `FaultInject` in turn (`FI_EAHEAP` only modifies `FI_AV`), log `FaultInject: Mode=2 plan ... injects 0x..`; a bit the plan never reached is dropped at its end. `ApplyP5` reads `[RouteSnap] FaultInject` masked to the live-safe bits 1, 2, 4, 8 (OOM, managed, AV, EA heap) and `FaultInjectEvery` (default 10). `FI_STALE` and `FI_CLOSE` change shared state (`g_spWrites` without a record, the real closing flag), so live builds never read them.

Selftests (all in the normal selftest run):

- `TestP5` (single thread, P5b off): 64 `FI_OOM` jobs in a row, each released to the provider with no flags and answered by the game, Mode=2 still on; `FI_BUDGET` with a past FbJobCapMs deadline on the thread: `t_budget.on` 0 in the clone run, answer taken.
- `TestP5Fault` (p5fault-test.h, threaded, in `TestP5b`'s fake world: real `CRITICAL_SECTION` `+0x918`, `P5bWorker`, the sim taking the lent lock as steering in every open window): F1 AV in a P5b window, F2 AV with the EA heap lock in a P5c window, F3 three managed tripwires in P5c windows, F4 world close mid-run, F5 a 2.3 s steering holder. Every job: no hang (8 s limit), an answer in the route's list, window closed, `g_p5bIn` 0, `g_p5cJob` 0, the worker owning `+0x918` at the IC's tail, frame object intact (`P5bWorker` checks).

Day verify queue `tools/harness/queues/p5-fault-verify.json` (not run): `bp-p5-fault-trip` (`FaultInject=3` every 10: managed / OOM alternating, third tripwire turns Mode=2 off) and `bp-p5-fault-av` (`FaultInject=12` every 20: one AV holding the EA heap lock in a lent P5c window, P4 off, the game runs on). 5 min each, noisy machine OK, pass rules in the job notes. Needs `game-copy/ts3native.asi.faultinj` (build steps in the queue note).

## 3. Open risks (by design, not fixed here)

1. **Retake watchdog has no escalation** (row 11). *Guard since 0.36.35: §4.3 (the waiting retake still waits; later windows no longer open).* An admitted holder that blocks on the job through a wait site that is not routed through `P5cHandBegin` would hang the worker with a `P5b: worker waited` line every 2 s. Known wait sites are covered (row 14); a new one added later would not be. Mitigation today: the queues stop on that log line. A timeout (hand the job to the game's plan and turn P5b off) needs a way to abandon the clone run's frame while the holder still runs: design only.
2. **Refusal storm cost** (row 9). *Breaker since 0.36.35: §4.4.* Each refused job can spend up to `kPcWaitMs` (50 ms) in the acquire; with the lock not lent early (`PcAcquireOwnOnly` false) that is under the job's `+0x918`, so the sim waits too. Correctness holds (every request answered); a breaker (Mode=2 off after N refusals in a row) would trade it for coverage. Read `m2Fb` mat share in the verify runs first (p5-bundle-verify passes at mat <= 5%).
3. **`HeapCreate` failure** [inferred, not tested]: `RpAlloc` (replay.cpp:93) calls `HeapAlloc` with a NULL heap if `HeapCreate` failed. The `PcAcquire` copy path is inside `__try` (refused as `PS_COPY`), consumer paths count `rpFaults`, but a call outside a guard would fault. Only under address-space exhaustion, which takes the game down first.

### 4.1 Lock-key writer cover (docs/156 U1 / F1; the docs/178 T8 risk)

`Footprint_SetLockKeyObject 0x807110` swaps `fp+0x20` of an inserted footprint with no W1/W2 record, so the clone kept the set it had at the INS [verified, docs/156 §1]. `0x807110` is already T-S7's tripwire site (steerro.cpp; one owner per docs/68), so the cover hooks its only IC caller instead: the slot `+0x8C` call in `RouteManager_FootprintLockKeyApply 0x82B2B0`, 8 bytes `mov edx,[edi]; mov eax,[edx+0x8C]` at `0x82B3A1` (no relative operand; the only branch into the range is `0x82B349`'s jne to its first byte; capstone plus a raw rel8/rel32 scan of `.text`) [verified]. There `edi` = the routing footprint, `ebp` = the new set, `ebx` = the routing world (`[ebx+0x95C]` = P, as at `0x82B31F`). `RpLockKeyEnter` (replay.cpp, sim thread): when the set changes on an inserted footprint (`+0x34` bits 26-30), it forces every live lot that holds an FME of its key / ~key (bucket walk of the live map; only the sim writes it), counts the change as a routing write (`g_spWrites`: a P5c answer cut before it is refused as stale), and sends Q-less FMEs through the cut's Q-less refresh (`RpNoQNote`). Counters `rpLockKeyForce` / `rpLockKeyNoLot`; log `snap replay: lock-key set of footprint ... changed in place` (1-8, then powers of two). The set contents were already covered (`g_spKeysDirty` at the 4 IC slots, docs/156 row 12b). The other `fp+0x20` writer, slot `+0xA8 0x80C8C0` (`0x639B40` from `RoutingWorld_OnMessage 0x835300`, message `0x38E3C1E`), runs only during world load, which ends in the world epoch: no cover needed [verified static, I-156-6 closed 2026-10-23]. Selftest `TestP5Covers` A.

### 4.2 Replayed-insert answer check (`[RouteSnap] InsCheck`, default 1 = log only)

The INS record copies the footprint at ApplyInsert's entry, but the replay inserts whichever copy `RpFpUse` picks (an older copy refreshed in place keeps a child's parent pointer; an own-block child answers through its pinned parent copy), and the leaf insert uses that copy's `+0x2C` answer. The record now also carries live's answers (the footprint and its list children, levels 0-3, asked just before the game asks them); after the replayed insert the consumer compares the answers of the FMEs that insert made (`RpInsCheck`) and logs `snap replay: replayed insert on Q ...: copy of footprint ... answers ..., live answered ... at the record`; `InsCheck=2` also forces the lot (difference over 0.01 or flat on one side). Log only by default: the live answer is asked before the game's insert, which may transform a first-inserted footprint's points (W6d via `0x80E0E0`), so a difference on a parent at its first insert can be ours [inferred, I-157-7]. Selftest `TestP5Covers` B.

### 4.3 Retake watchdog escalation (risk 1)

`P5bRetake` (p5b.cpp): a retake still waiting after `[RouteSnap] RetakeEscalateMs` (default 4000, 0 = off) calls `P5bEscalate` once per session: `p5bRelease` 0 (every later `P5bOpen` refuses, why 0) and `p5cOff` 1, counter `p5bWdEscalate`, log `P5b: retake watchdog escalation: ... lending (P5b and P5c) off for this session; this retake keeps waiting`. The waiting retake cannot give up (the clone run's frame and the game's call are on the worker's stack), so it still waits for the holder; the escalation stops every later window, so an unknown wait site cannot repeat. `p5bRelease` is also the `--ab routesnaprel` switch: an A/B toggle turns lending back on. Lock model config `p5c-escalate` (the escalation may fire at any waiting retake; P5bOpen refuses after it): 15,752 states, clean. Selftest `TestP5Fault` F6.

### 4.4 Refusal-storm breaker (risk 2)

`P5Storm` (p5.cpp), once per Mode=2 plan that reached the acquire: a refused acquire or run (any `m2Fb` reason) extends the run; a taken or verified answer, or a clean run with nr skew, ends it. `[RouteSnap] StormRefusals` (default 128, 0 = off) in a row pause Mode=2 for `StormPauseMs` (default 30000): its plans then run the game's plan with no acquire (`m2Fb` other, `p5StormSkips`); the third storm turns Mode=2 off for the session (`P5_OFF_STORM`, `m2Off` 4; logs `RouteSnap: Mode=2 refusal storm n: ...` and `Mode=2 off: 3 refusal storms`). Counters `p5StormTrips`, `p5StormSkips`, `p5StormRunMax`. No lock behaviour changes (the pause skips the acquire before any window), so the lock model needs no new state. Selftest `TestP5Fault` F7 (breaker at 4 with `FI_OOM` refusals: pause, a taken job resets the run, third storm = off); `TestP5`'s 64 refusals in a row stay under the default.

## 5. The snap-p5c clone-run fault and the P5 verify audit mismatches (step 2, data + static)

### 5.1 The clone-run fault (plan 318) [verified cause; fixed in 0.36.2]

`snap-p5c-ab-2026-10-20-ip-snap-p5c-ab-0813` (0.35.25): `P4 FAULT in a clone run: exception C0000005 at 0x3D95D666 (plan 318, kind 3)`, stack `0x668654 0x66C291 ...`, then `RouteSnap: Mode=2 off: P4 fault`. docs/94 §22.31 (I-94-508) read it with the 0.35.24 IP fault: both walk a quadtree leaf's {FME, mask} entries and call through the FME's `+8` footprint whose vtable word is heap: a clone footprint copy freed and reused. Cause: a replayed remove whose copy answered other bounds than the clone's insert used erased only part of the clone's leaves; the rest named the freed FME and copy [verified disassembly `0x666750`, `0x666010`, `0x6668A4`]. The 0.35.26 IP run (`ip-snap-p5c-ab-2056`) faulted the same way (`0x00667F07` in the same walk `0x667DB0`, plan 212). Fix 0.36.2 (`RpRemFlat` collects every flat or different copy; `RpRemCovered` erases all their leaves with a cover rect). Since then 8 replay runs on 0.36.x (IP 0.36.2 x2, BP avoidro x3, BP Mode=2 / P5b / P5c and IP Mode=2 verify on asi.0338) show no `P4 FAULT` and no `fault applying record` [measured, logs]. No further fix.

### 5.2 The P5 verify audit mismatches (asi.0338: BP Mode=2 4 lines, BP P5b 8, IP Mode=2 32, BP P5c 0) [measured]

All the same shape: lot Q 1 (the level index), `only live` 30-603 entries, `only in the clone` 0, every listed entry a child footprint `0xFEBF90` with full masks (`entry +4 / +8 0xFFFFFFFF`), FME `+0x10` `0x200` (IP) / `0x600` (BP); the lot total differs by exactly the Q 1 difference (not moved to another Q of the lot); whole-map node counts equal (e.g. 126682 / 126682). Audit records apply in ring order after every earlier record, so nothing is late. IP shows the same child shape as BP, no water, pool or houseboat class among the diff entries; IP's 32 lines are 16 audits (more patched removes on IP, docs/94 §22.24). Across every replay run in `probe-out`: BP 0.35.5-0.35.26, 30+ runs, 0 mismatches; the first runs after the 0.36.2 cover (IP 0.36.2 x2) already have this shape (48 child-only-live lines), then BP 0.36.13 (avoidro) and 0.36.33. Before 0.36.2 the IP mismatches had the opposite shape (`only in the clone`).

### 5.3 Cause [inferred, strong; I-157-6]: no missed writer; the 0.36.2 cover erases the game's own leftover leaves

ApplyRemove `0x666750` erases an FME's leaves only in the nodes the footprint's *current* `+0x2C` rect reaches, then erases the map node and frees the FME [verified, docs/94 §22.31.2]. Child bounds move in live without a record (the child's `+0x10`, the parent's widening by its child-list state: docs/94 §22.24.5; IP 0.35.24's child REM patch lines "copy bounds 0.100 ... patched to live 2.100": live 2.0 narrower than at the insert; this run's logged patches are `0xFEB848` parents off by ~0.001, the child ones are past the log's first 8). So live keeps leaf entries in the cells between the insert-time and the remove-time rect, on a freed (pooled) FME whose `+8` child usually still lives: harmless in live. The clone did the same until 0.36.2, but its copies are freed by our GC: the faults of §5.1. The cover erases every leaf of such a remove, so the clone has exactly those leftovers fewer than live: only live, children, full masks, Q 1, map counts equal. That is why the shape starts at 0.36.2. Check (built, 0.36.35): `RpAuditDiff` also counts the only-live entries whose FME no live map node holds and logs `... N of the M only-live entries are on an FME no live map node holds ...` with `: explained, game leftovers only` when N = M and nothing is clone-only; N = M on every diff confirms I-157-6 (a reused FME block can make N < M).

Consequences: (1) these mismatches are by design; a forced rebase copies live's leftovers back until the next such remove. (2) A live search that walks a leftover sees the child cells as obstacles where the clone does not, so a verify M2 near such a cell is the game's leftover, not a clone error (read the `obst` block). (3) The queue rule asked for (`logForbid "snap replay audit MISMATCH": 0` in p5-verify-0338.json and p5-bundle-verify.json, plus `P4 FAULT in a clone run`) fails every run with this shape; once N = M is confirmed, forbid only diff lines without "explained".

The lock-key gap (§4.1) is a different gap (a wrong set pointer, no leaf difference); no diff entry is a lock-key, portal, water or houseboat class.

## 8. Hardware watchpoint helper (`[Watchpoint]`, built, default off, not run in game)

`native/ts3native/watchpt.cpp`. `WpArm(addr, len 1/2/4, writeOnly)` takes a free DR0-DR3 slot. A helper thread snapshots the process's threads (toolhelp), then for each one except itself: suspend, `GetThreadContext(CONTEXT_DEBUG_REGISTERS)`, set DR0-DR3 / DR7 (other DR7 bits kept), `SetThreadContext`, resume. The caller waits on the helper, so its own registers are set too. A vectored handler (first in the chain) takes `EXCEPTION_SINGLE_STEP` with a watched DR6 bit. It logs `watchpoint DRn hit k: <addr> len L written by eip E (value now V), thread T, stack (n) f0..f5` (first `LogHits` per slot, then only counted; stack = `CrStack` return-address scan), clears DR6 and continues; the slot stays armed. `WpDisarm(slot)` clears it on every thread. `[Watchpoint] Enabled=0` (default) installs nothing and `WpArm` returns -1.

- Use: call `WpArm` from the hook where the object is made (for §7.3: the replay's INS record of a child `0xFEBF90` on a repeating lot, `&child->+0x10`, 4, write-only). Correctness jobs only: each arm suspends every thread once (PLAN measurement rule (iii)).
- Limits: threads started after an arm are not watched (Windows starts them with DR7 = 0; shortcut, re-arm). Four addresses at most. Data breakpoints trap after the write, so `eip` is the next instruction. A debugger attached to the game takes the same registers.
- Selftest `TestWatchpoint` (`watchpt-test.h`): off returns -1; unaligned / length 3 refused; a test thread arms on its own local, a read is not caught, its write is, the main thread's write is (every thread armed), after disarm nothing is. Passed on this machine (32-bit selftest under WOW64): 2 hits, 0 threads not set.

## 10. Drift proof build: rebase hold for the diff, constructor pairs counted, the watch follows the child (built 0.36.40, counters v111, default off, not run in game)

### 10.1 What changed

- **`[RouteSnap] AuditHoldRebase=1`** (replay.cpp, default 0). An audit mismatch that sets the pending diff (the first 4 per session, as before) also sets a hold on that lot, under the ring lock and before its force. Each cut takes the hold with the forces. While it holds, the cut does not rebase that lot, whether the rebase is forced, signature-driven or a shell refresh, and the force is put back. `RpAuditDiff` runs at the next consumer hold, on the clone that still carries the drift, and then releases the hold (line `snap replay audit diff lot ...: ran on the drifted clone, the lot's rebase held until now`). It is bounded to one cut: if the hold is still set at the second cut, that cut releases it and rebases the lot (`... rebase hold released by timeout`). The hold is not taken under `g_rpForceAll`, or for a lot the mirror lacks. One hold per lot in a row, so the repeat mismatch the held cut's own audit finds rebases at once. Counters v111 `rpHold[3]`: 0 held, 1 released by the diff, 2 released by timeout. Why it is needed [inferred, I-157-11]: with `LotsUnlocked=1` a LOTS record is applied outside the lock, at the start of the round, so the forced rebase lands before the hold's diff. Without the consumer thread (selftest) the diff already ran first.
- **Watchpoint constructor pairs** (watchpt.cpp). A hit with eip `0x80750D`, or with eip `0x62627B` and `[esp]` = `0x807557` (the `ret 4` of `0x626270` called at `0x807555`), is counted in `wpCtor` and not logged. It does not use the `LogHits` budget. This is always on when `[Watchpoint] Enabled=1`, since it only filters log lines.
- **Child identity on hit lines.** Each logged hit on a `Lot=` slot appends `child id 0x<+0x18><+0x14> parent 0x<+0xC>`, read at hit time. A reused block shows a different id or parent than the arm line.
- **`[Watchpoint] Follow=1`** (default 0). At the W2 `0x666750` entry (replay.cpp `RpPreBody`), a remove whose key is the watched child's parent id, its own id or its `~id` disarms that slot. It logs `... removed (W2 key ...): DRn disarmed` and keeps the slot reserved (`Arms` is not freed). The next W1 insert on the lot of a child with the same parent id and child id is armed in that slot (`... re-armed DRn at its insert (follows the removed child)`). That is the footprint the game rebuilt. Counters v111 `wpFollow[2]`: 0 disarmed, 1 re-armed. Child ids repeat across parents (`0xFFFFFFFF00000000`, `0x0000078000000000`), so the parent id carries the match.
- Selftests: `TestWatchpointLot` covers Follow off (a remove keeps the arm), Follow on (disarm, the old block no longer caught, another parent's child not armed, the same parent's new child re-armed and its write caught, removal by the child's own id), and `WpCtorHit` on both eips with right and wrong `[esp]`.
