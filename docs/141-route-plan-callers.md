## 1. Funnels and direct callers

`Sims3.SimIFace.Route.Plan()` has 178 direct callers, `PlanFromPoint` 21; with every `PlanTo*`, `PlanToSlot*`, `PlanToLotCore`, `Replan` and `ReplanFromPoint` helper the planner has **648 direct callers outside `Sims3.SimIFace.Route`** [verified, index]. ts3fixes hooks the 4 `ScriptCore.Route` entries (`RouteBackoff.cs`: `Plan` -> `PlanAsync` own START or foreign START; `Replan`/`PlanFromPoint`/`ReplanFromPoint` -> A10 kinds 1-3, own task only, no foreign path) [verified, code]. So for Replan-family callers a foreign or task-less context is always synchronous today, whatever `FallbackAsync` says, and ts3native also refuses a route being followed (`Active`) [verified, docs/134 §2.1].

## 2. Method

`tools/route-plan-callers.ts` (Node, reads `index.json` and the assemblies, ~20 s):

1. Funnels: the 47 methods above. Direct callers: every method with a call edge into a funnel.
2. Upward walk: callers (all IL call kinds), plus the base and interface declarations a virtual method overrides (callers of the declaration reach the override), plus the creator of a delegate when the creator does not hand it to a known registration API (taken as called synchronously by its creator) [inferred for each such delegate].
3. Stop at an entry point; its kind gives the class:

   | entry | rule | class |
   |---|---|---|
   | `interaction` | `Run`/`RunFromInventory` on an `InteractionInstance` subtype | a |
   | `sim-task` | `Sim.Simulate` | a |
   | `interaction-cleanup` | `Cleanup` on an `InteractionInstance` subtype (runs after `Run` in the actor's task; also on reset) | a |
   | `social-callback` | any `SocialCallback` method (called by name from the social interaction's `Run`) [inferred] | a |
   | `definition-test` | `InteractionDefinition.Test` (autonomy in the Sim's task, or the pie menu) | a + c |
   | `object-task` | `Simulate` with no managed caller (an object's own task) | b |
   | `alarm` | delegate given to `AlarmManager.AddAlarm*` | b (verified yieldable above) |
   | `oneshot-task`, `oneshot` | delegate given to a `OneShotFunctionTask`/`OneShotFunctionWithParams` or `OneShotFunction` constructor (own script task) | b |
   | `event` | `ProcessEvent`, any `EventListener` subtype, or a delegate given to `EventTracker.AddListener` (runs inside `SendEvent`, in the sender's context) | c (conservative) |
   | `ui` | delegate given to an `add_*` event of a `Sims3.UI`/`Sims3.Gameplay.UI` type | c |
   | `native-callback` | no managed caller, no delegate creator, name `On*`/`Handle*`/`*Callback`/`*Handler` | c |
   | `reset`, `dispose` | `OnReset`/`ResetSim`, `Dispose`/`Destroy` (inline in whoever resets or destroys) | c (conservative) |
   | `load` | `OnLoad`, `PostLoad`, `PersistPostLoad`, `PostWorldLoad`, `OnLoadFixup`, ... (world load, no live state) | c |
   | `cctor` | static constructor | c |
   | `situation-state`, `object-init`, `buff-callback`, `interaction-setup` | hubs called from every context (`Situation` state `Init`, `OnCreation`/`OnStartup`, `Buff.OnAddition`/`OnRemoval`, `CreateInstance`/`ConfigureInteraction`) | x |
   | `virtual-hub` | the method only overrides a declaration with more than 12 overrides (an `IGameObject` member, `GetLocalizedName`, ...): class hierarchy analysis would link every call site to it | x |
   | `no-managed-caller` | none of the above and no caller: mod-only API (`IActor.RouteTo*`), reflection, unresolved dispatch, or dead | u |

4. Two outputs: `kind=caller` rows (each direct caller with the contexts that reach it, the count of entries per context, one shortest c chain, a `hub` mark when its walk passed 40k methods) and `kind=entry` rows (each entry once, with its shortest chain to a direct caller).
5. Columns `foreign_hint` (route probably owned by another object: social, group, vehicle, push, situation, ...) and `plan_size` (`world`: lot visits, travel, vehicles, safe-spot and lot-routability plans; `local-or-object`: slots, jigs, radius/radial plans; `any`: the caller decides) are **name heuristics** [inferred].

Limits: the walk stops at hubs (x), so a c context above a hub (an event that adds a buff whose `OnAddition` plans) is not listed; long chains (> ~10 hops) through `Sim.PlayReaction` -> `InteractionInstance.RunInteraction` or `InteractionQueue.InsertInteraction` -> `GameObject.SetObjectToReset` are real call edges but each needs a reading before a fix relies on it; whether the planner call on a chain actually runs (branch conditions) is not checked.

### 6.1 What `ForceReplan` does, per route action

`FollowRouteAction.ForceReplan(load)` does **not plan** for a Sim when `load` is false: if the Sim is routing and still holds the action, it inserts a `ReplanRouteInterruptAction` next in the Sim's route-action list and returns. That action's `OnEnqueue` kills the follow action (stop), and its `PerformAction` replans the interrupted route (`Route.Replan`) in the Sim's own route loop, i.e. its own task, after the follow stopped: A10 async territory (I-87-13) [verified, IL]. So docs/141 §3.3 and §4 #2 overstated the problem: the "mark dirty, replan in the Sim's task" design already exists in the game for every plain walking route action. What still plans inside the caller [verified, IL of each override]:

| override | follower | in the caller | after the replan | verdict |
|---|---|---|---|---|
| `FollowRouteAction` (base; plain walking `FollowSubPathRouteAction` without stroller) | Sim | nothing (interrupt inserted) | - | **already deferred** by the game |
| `PortalRouteThroughAction` (doors, gates, velvet ropes, box stalls, training posts, elevator doors: `RouteThroughPortalObject`) | Sim | frees its lane, `PathAdaptor.Replan(pos, !load)` = `ReplanFromPoint`, sync | route followed: insert the new subpath action after this one, kill this one; plan failed: kill `RouteFail`; route not followed yet: nothing (the caller follows the replanned route in place) | **deferred by `replandefer`** when followed and current; else the game's code |
| `PortalAction` / `PortalAnimateThroughAction` (stairs, ladders, pools, houseboat, subway...) | Sim | `mbReplan = true` only (base call on load or a destroyed portal); `PerformAction` then returns `ContinueAndPopPathAndReplan` after the portal | - | **already deferred** by the game |
| `FollowSubPathRouteAction` with a stroller slave, `GetInStrollerRouteAction` | Sim + stroller | `ReplanFromPoint`, sync, `allowKill` false | the route is swapped in place, result unused | sync, rare: **left** |
| `VehicleFollowSubPathRouteAction`, `BoatFollowSubPathRouteAction` | car, boat (not a Sim) | `ReplanFromPoint` / hover-train custom paths, sync, `allowKill` false | the vehicle keeps following the swapped route | no Sim route loop to hand it to: **left** |

### 6.2 What each caller expects after `ForceReplan` returns

| caller | after the call | verdict |
|---|---|---|
| `PathAdaptor.FootprintReplanCallback`, `PartReplanCallback` (dest object footprint / part availability) | returns | nothing read: defer allowed |
| `ScriptAdaptor.RouteExitReasonsAddedCallback` (exit reason `Replan`) | returns | defer allowed |
| `RoutingComponent.ForceRouteReplan(false)` (`OnBuildBuyExit`, `OnRoutingDataChanged`) | returns when not `load` | defer allowed; `load` (`PostWorldLoad`) keeps the game's code |
| `ElevatorDoors` portal component `OnApproachingPortalObject` | called from `PortalRouteThroughAction.DoPortal` **before** `PerformRoute`: after a teleport the replanned route is followed right after the call | **needs the new path now**: the route is not active yet, so `replandefer` keeps the sync replan (the `IsActive` guard) |
| `ElevatorDoors` `OnPortalStart` | unregisters the Sim; route followed | defer allowed |
| `Houseboat` `OnPortalStart`, `Subway` `OnPortalStop` | `GetCurrentRouteAction() is PortalAction`: animate-through, `mbReplan` only | game already defers |
| `SteeringAdaptor.HandleEventNeedReplan` | **dead code**: private, no IL caller (index), and `ProcessEvent` maps `EventNeedReplan` to the no-op group | nothing to do |

So #2's synchronous remainder for Sims is the door/elevator action, plus rare strollers; vehicles and boats stay sync. **#4** (`ExitBuildBuyMode`, `ForceReplanOfAllSimRoutes`): per Sim the loop only inserts the interrupt (cheap) except Sims standing in a doorway (sync, as above); the real cost is that every routing Sim's interrupt replans in the same tick, so up to N A10 STARTs hit an 8-deep job queue (32 with `FallbackAsync=1`) and the rest plan sync as `QueueFull` [inferred from the code paths; the A/B measures it].

### 6.3 Built (ts3fixes, `ReplanDefer.cs`, both default off)

- **`replandefer`** (`kReplanDefer`): hooks `PortalRouteThroughAction.ForceReplan`. When not `load`, the follower is a Sim, this is the Sim's current route action, a path adaptor exists and the route is being followed (`ReplanDeferCore.ShouldDefer`), it frees the lane as the game does and inserts the game's own `ReplanRouteInterruptAction` (internal class, built by reflection; missing = switch off, logged in `ts3fixes.applied`). The Sim stops and reroutes the way the base class does it for every other walking action, a tick or so later, from its own task. Otherwise the game's method runs. Difference from the game: `Route.Replan` instead of `ReplanFromPoint(position)` (the same route object; both from where the Sim stands [inferred]), and on a failed replan the interrupt plays the route-fail reaction when the route asks for it (`DoRouteFail`) instead of the `ReplanFailure` kill.
- **`replanspread`** (`kReplanSpread`): hooks `RoutingComponent.OnBuildBuyExit` and `OnRoutingDataChanged` (each one call to `ForceRouteReplan(false)`). Calls are held in a queue (one entry per component) and replayed by our `OneShotFunctionTask`, at most 4 routing Sims per sim tick (non-routing ones cost nothing and are replayed too), destroyed owners dropped, all dropped at world shutdown; replay calls `OnRoutingDataChanged` (same body). A Sim's reroute starts up to N/4 ticks after the exit instead of at once.

### 7.1 #1 reset -> safe spot

- **What the game does.** `Sim.AttemptToFindSafeLocation`: `IsInSafeLocation` (1 plan), a `FindGoodLocation` from the Sim's spot then one routability check (1 plan), the same unconstrained (1 plan), then `FindPositionNearFrontDoor` for the current lot and, if that fails and it is not the home lot, for the home lot; with `forceHome` (and for babies, toddlers off daycare) straight to the front-door search. `FindRoutablePointInsideNearFrontDoor` builds an `IsPointSafelyRoutable` checker and passes its `Test` as `PlacementCheckFunc` to up to 4 `PlaceAtGoodLocation` calls; `Test` skips a point it already rejected (per-call dictionary), otherwise counts and runs `IsPointInLotSafelyRoutable`.
- **One plan per checked cell, not 8.** `IsPointInLotSafelyRoutable` is one `PlanFromPoint` with 8 radial destinations (4 corners, 4 edge midpoints, radius 1 m, 2 m on a houseboat), after cheap rejections (wrong lot, water, sea) [verified]. §4 row 1 said "8 x N plans": wrong, N plans.
- **First safe cell wins already.** The native FGL core `0xB470C0` calls the managed check through host `+0x134` only for cells that pass the native tests and returns at the first cell that passes everything (docs/110 §3.3) [verified static]. So "early accept" is the game's behaviour; the cost is the failed cells before it, and an unreachable lot (Sim boxed in, lot walled off) checks every cell of every search.
- **EA caps this itself, once.** `IsPointSafelyRoutable.SetLimit(n)`: `Test` refuses without planning once its count passed n. The vacation start (`GameStates`, travel) puts a shared checker with limit 5 in the static `Sim.sIsPointSafelyRoutable`, which `FindRoutablePointInsideNearFrontDoor` uses instead of a fresh one [verified]. Ours: every call gets a fresh checker for its own lot with the same limit 5, through that same static, set only for the call. Same cells, same order (one search engine, one check), so the result equals the game's while the first safe cell is among the first 6 checked [verified by construction; how often a reset needs more is unmeasured].
- **Safety of the shared static.** The game reads it once into a local at the top of the call. A plan inside `Test` may yield (ts3fixes own-task async plans), and another task's call could start meanwhile: it goes through our hook too and gets its own checker; a call that sees one of ours while the switch was just turned off is capped as well (runtime toggle only, commented as a shortcut). EA's own vacation checker is never replaced (our hook passes through while it is set).
- **Worst case per reset:** 3 + 2 x 6 = 15 plans with the cap; without it 3 + every checked cell of up to 8 searches.
- **`routablecache` (built 2026-10-13, opt-in).** Hooks `IsPointInLotSafelyRoutable` and answers from the SafeSpot verdict cache (0.5 m cell + exact route profile, a sim-day per lot, dropped on household change or lot move; not for the world lot or a parented Sim). Why it stayed opt-in: the default-off rule, then two A/Bs that never exercised a reset: 2026-10-13 in-load BP 38.8 vs 38.2 it/s, 2.68 vs 2.64 hitches/s (no 3 AM in the window), 2026-10-14 BP 38.0 vs 44.3 it/s with only 28 cache hits in the run, marked FAIL (PLAN.md test round 2026-10-14) [verified, PLAN]. 28 answered checks cannot cost 14% of it/s; that gap is run-to-run variance of the kind docs/136 measured for slot order (~+-15%) [inferred]. Its risks are a stale "routable" for up to a sim-day after a wall goes up on that cell and the 0.5 m cell answering for nearby candidate points. With both on, a cached answer still counts toward the checker's limit (the game counts before it calls), so a cached "no" uses the cap without a plan. The A/B has a third arm with it.

### 7.2 #3 `LotManager.GetFarthestLot`

- **The loop** [verified]: `GetFarthestLot(lot, actor, bSimCanRoute)` returns null for a missing or world lot; for every lot of `AllLotsWithoutCommonExceptions` (no world lot, dive lots, houseboats, uncharted islands) other than `lot`, if its squared distance beats the running maximum (start `float.MinValue`) and `actor != null && bSimCanRoute`, it plans `lot.PlanToLot(actor.CreateRoute())` and keeps the lot only on success. Answer: the farthest lot the plan accepts, ties to the first in list order; plans: every lot that beats the running maximum when met.
- **Only 2 callers route** (`bSimCanRoute: true`): `AlienSituation.SendAlienHome` (from the visit alarm `TimeToLeave` and an interaction callback, b/a) and `TravelUtil`'s early-departure destination (an interaction `Run`, a) [verified]. The 20 other call sites (passport, boarding school, aliens arriving, moving, travel return, ...) use `GetFarthestLot(lot)`, which never plans. So #3 is not a c chain: with `FallbackAsync=1` these plans are already own-task or foreign-task async plans; the fix only cuts their number.
- **Sorted = same answer, fewer plans** (`FarthestPick.Sorted`): order by squared distance descending, ties by list order, plan until the first success. Proof: the game's answer A is routable and farther than every other routable lot, and every lot the sorted walk plans before A is farther than A and unroutable; the game's running maximum is always the distance of an accepted (routable) lot, so never above d(A), and a lot farther than A beats it when met: the game plans it too. Hence the same A, and the sorted plans are a subset of the game's: 1 + the unroutable lots farther than A. Selftest `tools/selftest/farthestpick` (20k random worlds with ties, `farthestpick selftest ok`): same answer every time, every sorted plan also a game plan, 65,149 vs 130,588 plans in total [verified, selftest].
- **Cap 3 and cache (where it can differ).** After 3 failed plans the next lot by distance is returned unplanned, as the no-route overload would pick among the rest; the game would keep planning nearer lots (and return null if none routes). A verified answer is kept for a sim-day per start lot, with the actor's current lot and its route profile (`ProfileOf`, not for a parented Sim) as the key. A cached lot that became unroutable is still returned; the Sim then fails that route like any other.

### 7.3 #5 `Lot.GetRoutableIndoorPositions`

- **The loop** [verified]: with a Sim, a placement test object out of world and one route from the Sim; for every display level and every inside room (skip public rooms of apartment lots and rooms not larger than the size given), the room's objects in random order (`RandomizeListOfObjects`), each object's fire positions in that room: a random facing (`GetRandomDirXZ`), `FindGoodLocationInSameRoom`, and when that places, `PlanToPointRadius(pos, 0.5)`; the first success not already in the result ends the room. A room the Sim cannot reach plans every object x position.
- **Real callers** [verified]: `FireFightingJob.SetupTasks` (large fires, earthquakes; from `GoToOccupationJobLocation.Run`, the firefighter's own interaction, and it already sleeps in a wait loop) and `NpcParty.BringNpcGuests` (a `OneShotFunction`, `Threaded`). Both are yielding tasks: the fire job's plans are own-task, the party's are foreign-task (the host's route from the party task), which `FallbackAsync=1` already sends to the worker. The event, social-callback and alarm chains of §4 row 5 go `Lifeguard+BeachSurvey..ctor -> Job.SetupTasks -> FireFightingJob.SetupTasks`: the call in the constructor is a virtual call on a `BeachSurvey` (not a `FireFightingJob`), linked by class-hierarchy analysis only [verified, class declarations]. No `OneShotFunctionTask` move is needed.
- **The cap** (`indoorcap`): the same loop with the same random calls in the same order; a room is given up after 4 failed plans. Same answer whenever each room's first success comes within 4 failures; otherwise that room has no position (the party places fewer guests indoors, the fire job has fewer fire spots), and the random sequence after that room differs from the game's.
