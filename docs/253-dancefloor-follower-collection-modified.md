## 2. Which list, and who can change it (question 1)

EA's method, IL read from the shipped DLL [verified: IL `IL_0008`-`IL_0032`]: a foreach over the new `List<DanceFloor>` that `GetDanceFloorsNearObject(danceObject)` returns; the first floor whose `RouteOntoADanceFloorWithFollower(actor, follower)` succeeds is returned, else null.

- `GetDanceFloorsNearObject` builds `new List<DanceFloor>()`, fills it from `Lot.GetObjectsInRoom<DanceFloor>` (that foreach ends inside the helper), sorts it with a lambda that captures only `center`, and returns it. Nothing stores it: no field, no static, no closure. The only reference is the enumerator struct in local 2 of `FindAndRouteOntoADanceFloorWithFollower` [verified: decompile + IL].
- The loop does route and yield inside the foreach: `RouteOntoADanceFloorWithFollower` calls `route.Plan()` and then `actor.DoRouteWithFollowers(route, list)` (a second, new `List<Sim>` with the follower). `DoRouteWithFollowers` sleeps the task for the length of the walk, and with `[RouteAsync]` `Plan()` sleeps too, so other Sims' `Simulate` runs in between [verified: decompile; docs/185 for the async plan wait].
- But no managed code can reach the list: another Sim's task has no reference to it, reflection-based cleaners (NRaas ErrorTrap dereferences, Overwatch, ts3agent snapshots) walk object fields and never see interpreter frame locals, and the ErrorTrap "Destroyed Object Found" corrections at 15:31 and 15:37 in this session act on fields of live objects only [verified: `ErrorTrapSpace/Dereferences/Controllers/DereferenceGameObject.cs`; inferred for "never see frame locals"].
- Mono's `List<T>.Enumerator.MoveNext` throws this message only when `ver != l._version` [verified: `mscorlib` decompile]. `_version` changes on Add/Insert/Remove/Clear/Sort/Reverse and the indexer set; the last of those on this list is the `Sort` before the enumerator is created.

So in managed terms the throw is impossible. It needs a memory-level change [inferred, not yet measured]: (a) the list object was freed while the task slept and its memory now holds another `List`1` with a different `_version` (premature collection or a double allocation), (b) the `ver` or `l` word of local 2 in the task's frame was overwritten, or (c) the `_version` word of the live list was written by native code. The task frame of a yielding mint task is `GC_malloc` memory owned by the task's `ThreadContext` (docs/29 §1.3), so (a) and (b) both need something outside EA's normal path.

## 3. Vanilla EA bug? (question 2)

- Web: no hit for `FindAndRouteOntoADanceFloorWithFollower` or `DanceTogetherA` with this exception (searches 2026-11-08; only unrelated Sims 4 dance routing threads).
- NRaas: Woohooer's `DanceTogetherAEx` (`NRaasWoohooer/WoohooerSpace/Interactions/DanceTogetherAEx.cs:85`) calls EA's method unchanged, and ErrorTrap has no check or correction for it. NRaas collected script errors from many players for years; no workaround suggests they never saw it [inferred].
- EA's code has a real bug next to it: the sort lambda's first `if` computes `num.CompareTo(num2)` and drops the result, so the comparer is not consistent. That changes only the order of the floors and runs before the enumerator exists; it cannot cause this throw [verified: decompile].
- Our own data: the same error appears twice in all `probe-out/*/events.jsonl`: this run, and `probe-out/20261104-033850` (Rafael Striker, household Talon and Striker, also on Waylon's Haunt, job `bp-rel025d-blcap-reload`, ts3native 0.36.168 `rel025d`, `docs/data/results/2026-11-03-queue-rel025d-verify.md` line 9) [verified]. That run was a v0.2.5 rc build with `[GC] BlackListCapKB` and `[RouteAsync]`, before CasTrim existed.

Verdict for question 2: no evidence of a vanilla EA bug. The code path cannot throw this in managed terms, so even a vanilla repeat would point at the runtime, not at EA's C#.

## 6. Verdict

**Unknown, treated as ours until proven** (crash-cause-before-fix). Evidence: EA's managed code cannot modify this list (§2), the error needs a frame or heap change at memory level, both hits are on our builds (0.36.168 and 0.36.198), each with `[RouteAsync]`, the unseen fallback and the `[GC]` tuning on, and there is no web or NRaas trace of a vanilla report. Not proven ours either: no change in the enabled set writes managed memory, and two clean vanilla sessions are too few. Both hits are NPCs on Waylon's Haunt; no household Sim was involved.

What would decide it: the diagnostics in §7 (which of (a), (b), (c) happened), then the repro in §8 on vanilla `TS3W.exe` with no ts3native, and with ts3native but `[RouteAsync]` and `[GC]` off.

## 7. Proposed diagnostics and guard (not built)

Not a small-fix candidate yet: docs/252 needs a known EA cause, and catching the throw would hide a possible memory bug of ours. Order: diagnostics first, the guard only after §6 is decided.

- ts3fixes switch `dancefloorlistdiag` (off by default; counters: reserve with `node tools/registry.ts reserve fixes 6 --by ... --what "dancefloorlistdiag (docs/253)"`). Replace `FindAndRouteOntoADanceFloorWithFollower` the way the other ts3fixes EA patches do: build the list with EA's `GetDanceFloorsNearObject`, keep its `Count`, `_version` (reflection, read once per call), identity hash and first item; loop by index; after each `RouteOntoADanceFloorWithFollower` read them again. Log one line per mismatch: `dancefloor list: version A->B count C->D same items yes/no type <T> actor <name> household <bool> slept <ms> gc <n>` (`gc` = ts3native's Boehm collection count, if the counter export has it; else the `[GC]` log index). Counters: calls, routes, version changed with same items (= a write into a live list, case c), items or type changed (= freed and reused, case a), throws caught.
- The same check in ts3native around the task's sleep is not needed first; the managed check tells (a) from (c), and a frame overwrite (b) shows as a throw with all three values unchanged.
- Guard, only after the cause is known (switch `dancefloorlistguard`, default per that verdict): loop over `list.ToArray()` taken before the first route and return `null` on any `InvalidOperationException`. `null` is EA's own "no floor" result: `DanceTogetherA.BaseRun` then dances without a floor [verified: `Stereo.cs` BaseRun]. Applies to every Sim (it only acts after the throw), so the household rule holds: controlled Sims get vanilla results unless the vanilla path would throw.

## 9. Shared-cause hypothesis with the CasTrim cell lines [inferred]

The same castrim-live session had the AV at `0xD4B156` that docs/539 §13.6 triages, and the docs/539 §13.7 detector logs `cas trim: float-5 cell` / `cas trim: outfit cell bad` for outfit record cells that hold a float or a small integer where a pointer belongs. Both that and this throw fit one shape: a heap block freed while something still uses it, then reused by another object, so a reader sees another object's words (here the list's `_version`, there an outfit cell). This is [inferred] only: no run has shown the two in one load, the two heaps differ (Boehm for the list, EA's native heap for the compositor cells), and §4 found no change of ours that writes either. The queue's arm 4 runs both detectors in one load to test it: dance floor MISMATCH lines with class `freed` next to float-5 / bad-cell lines in the same load would support it; MISMATCH lines without them, or the reverse, would not.
