# 184. NRaas source cross-reference: ErrorTrap catalog, IC contexts, names, process

Written 2026-10-24. **Static only:** a read of the NRaas source (https://github.com/Chain-Reaction/NRaas, commit `2f57186`, 2026-07-29; local read-only clone `game-copy/nraas-src`, git-ignored), cross-referenced with our docs and ts3fixes. No game run, no build, no queue.

Boundaries: NRaas has **no license file**, so nothing of theirs is copied here; rows cite repo path, class and method names and describe behaviour in our own words. Their `Sims3/` folder holds EA's script projects (and ErrorTrap's modified `ScriptCore`): not read for this doc, never copied. Every NRaas-derived statement is **community-reported** (source read, not run) unless a row says otherwise. NRaas is script-only; native work (routing, `+0x918`, footprints, Mono) stays ours.

Installed on the reference machine: ErrorTrap and Overwatch only (docs/128 §1). GoHere, Traveler, StoryProgression, Traffic and the rest matter for players who run them, not for our reference A/Bs.

## Summary

- **ErrorTrap is 683 files in `NRaasErrorTrap/ErrorTrapSpace`:** 19 `Checks/*` (per-object fixes at post-load), 8 `Dereferences/Controllers/*` (whole-world passes one sim-minute after load), 650 `Dereferences/Performers/Deref*` (one per EA type that can hold a dangling reference) plus `ErrorTrap.cs` hooks into its own `ScriptCore` (`ExceptionTrap.OnScriptError`, `OnLoadReference`, `OnLoadArrayReference`, `OnPrePostLoad`, `OnPostPostLoad`, `OnRemoveObject`, `OnProcessObjectGuid`).
- **New to us (top):** (1) `OnScriptError` turns any script exception in a Sim's `SimUpdate` into a full `ResetSimTask` (destroys the `SimUpdate` proxy; reset = safe-location placement), after scanning every `SimDescription` against an address parsed from the stack trace; (2) `DereferenceFollowRouteAction` finds `FollowRouteAction`s not in their Sim's `mRouteActions` after load and either clears `mRouteActions` (distance left 0) or resets the Sim 30 sim-minutes later; (3) ErrorTrap destroys orphaned `OneShotFunction` proxies at world load (target object destroyed) and tracks every `Simulator` add/remove through `OnProcessObjectGuid`; (4) NRaas `ResetSimTask.ResetRouting` reads `SimRoutingComponent.LockedDoorsDuringPlan` and resets every door in it, refuting the "mods inferred absent" half of I-150-13-5; (5) GoHere swaps EA's `Route.PostPlanCallback` for its own (`AncientPortalRoutingHelper.OnPreLoad`), which can start nested `CreateRoute`/`PlanToSlot`/`ReplanFromPoint`/`PlanToPointFromPoint` plans inside the post-plan callback (subway/hover-train reroute).
- **Contradicts us:** docs/11 says nothing in the game sets `Route.AboutToPlanCallback`/`PostPlanCallback`; GoHere removes `SimRoutingComponent.PostPlanRouteCallback` from `PostPlanCallback`, so EA does set it (docs/04a §2 and docs/10 already read `PostPlanRouteCallback` as live). I-150-13-5 (mod half), see §3.
- **NRaas alarms are class b with their own task:** `Common.AlarmTask.OnTimer` (`NRaas/Common.cs`) only starts a `Common.FunctionTask` (a `Task` that runs the function once and destroys itself), so NRaas alarm work never runs inline in `AlarmManager.Simulate` and `Common.Sleep` yields there. Every NRaas route plan found outside interactions runs in such a task, a `OneShotFunction`, an interaction, or a route-follow callback; GoHere's door-filter option plans from the NRaas menu interaction or option task, so no NRaas plan is class c (§2, corrected by docs/141 §8).
- **Best process improvement:** feed the installed mod assemblies to `tools/route-plan-callers.ts` / `managed-callgraph.ts --mods` with a type-to-source map into this clone, so GoHere's `DoRoute` replacement and post-plan reroutes get docs/141 a/b/c classes (§4 P1, ~1-2 h). **Done 2026-10-24: docs/141 §8** (installed IL + all 57 source sites classified, `docs/data/nraas-source-map.csv`).

## 5. Overwatch's `SimEx.IsPointInLotSafelyRoutable` vs `routablecache`: not worth extending (2026-10-24, static)

Question (§2 row 3): Overwatch's Stuck Check plans through NRaas's own copy `NRaas/Helpers/SimEx.IsPointInLotSafelyRoutable`, which ts3fixes `routablecache` (`FewerPlans.cs` `RoutableCacheHook`, hooks EA's `Sim.IsPointInLotSafelyRoutable`) never answers. Should the cache cover the copy? Ledger I-184-22.

**What the copy is** [verified: IL of the installed `NRaasOverwatch.dll`, call graph with `--mods` (docs/141 §8); source read]: the only planner call in the installed NRaas assemblies; one `PlanFromPoint` with 8 radial goals (4 corners, 4 edge midpoints), the same early rejections as EA's, its route from NRaas's `SimRoutingComponentEx.CreateRouteAsAdult` + `SetRouteOptions` copy (same option set as EA's by a token compare [inferred]); its one caller is `StuckCheck.PrivatePerformAction`, in the nightly alarm's `Common.FunctionTask` (class b). ts3fixes already hooks the copy: `overwatchstuck` (default on, `OverwatchStuck.cs`) runs it unchanged and then yields a tick, so each plan has its own tick.

**What it costs** (docs/145 §12, `docs/data/results/2026-10-24-sv-cause-run-analysis.md`):

| quantity | value | source |
|---|---|---|
| calls per check | 1 per stuck candidate (unmoved Sim, same or no interaction since the last check, not in a hidden room) | source + IL [verified] |
| plans per call | 1 (`PlanFromPoint`, 8 goals) | [verified] |
| checks per sim-night | ~4 BP, ~1.6 SV (task runs per firing minus the fresh run: 85 runs / ~17 firings, 89 / ~25) | docs/145 §12.1 [inferred from task-run counts] |
| time per plan | 0.6-12 ms (SV soak), 88 ms max seen | docs/145 §12.3-12.4 [measured] |
| per sim-night | ~5-50 ms of plan time, each plan in its own tick | product of the above [inferred] |
| the Stuck Check's real hitch | the Sim walk between two checks (100-336 ms SV), not the plan | I-145-15, `overwatchstuckslice` |
| the stuck check freezes in the SV cause run | EA's `LotManager.RunStuckCheckHelper` (59 sync plans, 20.2 s, max 2,019 ms), not Overwatch | SV cause run [measured]; fix `stuckcheckown` |

**Would a cached answer be the game's answer?** Same inputs, same verdict holds only partly:
- The inputs match `routablecache`'s key: same lot, same point, and a route profile built the same way (EA `CreateRouteAsAdult` vs NRaas's copy: same flags, same option set [inferred]), so a `RouteProfile` read back from EA's builder would equal the copy's in the cases checked.
- But `routablecache` is exact only for the same tick and the same world state; it keeps a verdict for up to a sim-day per lot. Overwatch asks once per sim-day per stationary Sim, and asks *because* the Sim may be stuck: a wall, object or footprint that appeared since the cached verdict is exactly the case it exists to catch. A stale "routable" would skip a needed reset. `OverwatchStuck.cs` already records this choice ("Not cached ... another Sim's or another tick's verdict is not exact").
- Hit rate: the lot's verdict set lives a sim-day from its first check, and Overwatch checks each candidate once per night; a hit needs an EA safe-spot or watchdog check of the same 0.5 m cell on that lot earlier the same day. Expected near zero.

**Verdict: not worth it; nothing built.** Gain <= ~50 ms of plan time per sim-night already spread one plan per tick, near-zero hits, and the one wrong answer the cache can give (stale "routable") defeats the check's purpose. The Overwatch hitch to work on is the walk (`overwatchstuckslice`, docs/145 §12.4); the stuck check freezes are EA's (`stuckcheckown`, docs/163 §7). Reopen only if a run with the counters of `overwatchstuck` ([44]/[45]) shows many more checks per night (e.g. > 50) or plans > 100 ms; then the design would be: a second `RoutableCacheHook` entry on `SimEx.IsPointInLotSafelyRoutable` (static, `Sim ths` first) with the same key, **read-only** (record verdicts from Overwatch's plans for EA's later checks, never answer Overwatch), which keeps Overwatch exact and lets its fresh plans warm the cache for same-day EA resets.
