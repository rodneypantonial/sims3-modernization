# 858. `[StiltRemove]`: stilts that cannot be removed or get deleted by a neighbour (2026-11-21, contributor, default off, NOT RUN)

Code: `native/ts3native/stiltremove.cpp` (selftest `stiltremove-test.h`), switches `[StiltRemove] Enabled`, `PlaceKeep` (§5) and `PartClamp` (§6) (ts3native.ini, each default 0), counters v923 `sr*` at 0x6B48-0x6B67 (docs/registry.md). Tags: [verified] = read in the disassembly of the Steam 1.67 TS3W.exe (or the decompiled scripts, read locally, not committed); [inferred] = reasoning, not traced.

Players report that the stilts of an Island Paradise stilted foundation "remain forever" once the lot went through the Library (saved to the bin and placed back): delete and sledgehammer leave them standing, also after a save and reload.

## 1. How stilts are stored [verified]

- Each lot owns a stilted foundation manager at `[lot+0x2B8]` (ctor `0xC1D860`, init `0xC1F780`, made in the lot loads `0xAC9B10` / `0xACA060`). It keeps three maps: stilt groups (`+0x1C`, "StiltGroupHashMap": group id -> group record with its own stilt map), a location map (`+0x3C`, "StiltLocHashMap": stilt key -> group id) and 8x8-tile partitions (`+0x5C`, "StiltPartitionData"), which the query `0xC1F4D0` rebuilds from the group maps (`0xC1F390`) when the dirty byte `+0x78` is set. Both loads set it.
- A stilt's key is `0xC1AB00({x, z, level})` = `floor(z*8+0.5) << 12 | level << 24 | floor(x*8+0.5)`; level is 0 at every call site.
- A stilt record holds a render position (`+0x00`, a vector) and its grid point (`+0x14` / `+0x18`). `0xC1ABE0` places the render position: it starts at the grid point and moves it 0.245·√2 ≈ 0.35 or 0.245/√2 ≈ 0.17 tile inward when neighbouring foundation cells are missing (edges and corners).
- Building (`0xC1E4D0`), the save load's upgrade of data version <= 2 (`0xC1DBB0`) and both lookups of the foundation tools key a stilt by its **grid point**. The save (`0xC1BE80`, chunk `0x0F3F5476`, version 3; per group `0xC1B830`) writes the stored key, and the version-3 load (`0xC1ECC0` -> `0xC1DBB0`) reads it back unchanged.

## 2. The bug [verified]

Placing a lot from the Library or the town bin runs `DownloadContent.ImportLotContents` (`Bin.PlaceLot`, the place tool's `PlayFlowModel.BeginPlaceLotContents`; internal call `0x997540`) -> `0xAD5000` -> the lot import `0xACE4A0` -> the stilt import `0xC1EDD0` -> one group at a time `0xC1DF40`. The group loader gives the group a new id, rotates the render position and the grid point into the new lot (`0xCB32B0`, rotation steps plus offsets) and stores both, but builds the key from the rotated **render position** (`[esp+0x1C]` / `[esp+0x40]`, call at `0xC1E2FB`), not from the grid point every other path uses. With the inset of §1 the two differ for every edge and corner stilt (0.17 tile is more than the key's 1/16-tile step).

So the stilts are registered (the guess "the import does not register them" is wrong: group map, location map and partitions all get them), only under a key nothing computes:

- Removal path (delete / sledgehammer of a foundation or deck): `RemoveAnyStiltedFoundationsInBlock` `0xCA7E00` (callers `0xCAEDA9`, `0xCAF1BB`) or the undoable `UserToolUndoableDeckFoundation` `0xD1EA20` (undo / redo `0xD1D2B0`) -> collect `0xC1F810` -> partitions `0xC1F4D0` -> per stilt `0xC1E9E0`, which keys by the partition's grid point and looks it up in the location map. A miss returns without an edit: the stilt is never collected. The apply step `0xC1EED0` -> remove `0xC1E8F0` would miss the same way.
- The save writes the bad key, the next load reads it back: the stilt stays for good. The same miss also drops the move edits `0xC1E9E0` makes when foundations around a stilt change [inferred: same lookup, not traced in game].
- Stilts whose render position equals the grid point (no inset) keep a matching key and stay removable [inferred from `0xC1ABE0`'s branches].

## 3. Fix (`Enabled=1`)

- Import: the call at `0xC1E2FB` goes to `StImportKey`, which keys the stilt by the rotated grid point the record stores (`[esp+0x64]` / `[esp+0x68]` in the group loader's frame). `srImport` counts imported stilts, `srImportFixed` those whose render-position key differed.
- Load: the version test at `0xC1DD49` (`cmp [ebp+0x10],2; ja`) jumps to `StLoadStub`, which keys every loaded stilt by its grid point (EA's own version <= 2 path) and continues at `0xC1DD86`. `srLoadFixed` counts version-3 keys that differed: stilts an earlier import broke, repaired in memory and written right by the next save. A stilt with a good key gets the same key back, so a clean save loads as before.
- Both sites and the frame offsets the import hook reads are byte-checked first (`0xC1DD49`, `0xC1E2D0`-`0xC1E2FF`, `0xC1E192`-`0xC1E1B2`); on a mismatch nothing is written (`SKIP StiltRemove`, `srMode` -1). EA 1.69 and retail 1.67: no address, SKIP.
- Log: `stilt key fixed at import` / `stilt key repaired at load` with grid point and keys, the first 8 of each, then powers of two.
- Save data: the repaired keys are saved, so the switch stays opt-in. Two stilts at one grid point would merge into one record at load [inferred: EA's inserts are find-or-insert; building never makes two]. Household rule: not applicable (lot build data).

## 5. `PlaceKeep=1`: a foundation or deck placed next to a stilted foundation deletes the shared edge's stilts

**Bug [verified].** The place function `0xCAECA0` (args: lot, foundation type, block corners `p0` / `p1` as bytes x, z, level, ..., undo object as arg 6) handles a type that is not stilted (`0xAFFCF0` false; stilted kinds are 7/8/9) as follows: it calls `RemoveAnyStiltedFoundationsInBlock 0xCA7E00(lot, p0, p1, diag, recheck, undo, arg9)` at `0xCAEDA9` (regular kinds at level 0; kinds 3/6 at level 1 with the block rebuilt in the frame from level 0 to level-1, `0xCAED64`-`0xCAEDA7`), with `recheck` 0 (`push 0` at `0xCAED57` / `0xCAED8A`), **before** the cell write `0xCAAC80` (`0xCAEEA4`). With recheck 0 the collect `0xC1F810` (or, with an undo object, `0xD1EA20`, which passes the same flag on at `0xD1EB0E`-`0xD1EB45`) hands every stilt in the block to `0xC1E9E0` with the edge flag 0, and `0xC1E9E0` removes it unchecked (`0xC1EA70` -> `0xC1EC36`). The block's edge grid points are shared with a stilted neighbour, so its edge stilts go too.

EA's delete / sledgehammer path `0xCAEF90` does it in the other order: cells first (`0xCAAC80` at `0xCAF11F`), the undo records (`0xD1D080` / `0xD1E190`), then `0xCA7E00` with recheck 1 (`0xCAF1BB`), then `0xCA76B0(lot, 0)`. With recheck 1 a stilt on the block edge (`0xAFEBE0` / `0xAFEAB0`) goes to `0xC1ABE0` on the written cells: removed when no stilted cell still touches it, left alone when its place is unchanged, moved (remove + add edit) when its inset changed. A stilt inside the block is removed as before. A plain flip of the `push 0` to 1 would be wrong: before the write the old cells of a replaced stilted foundation still count as stilted.

**Fix.** The call at `0xCAEDA9` goes to `StPlaceDefer` (same cdecl arguments): it copies both block corners (the deck branch builds them in the frame and `0xCAEDC2` overwrites one) and the other arguments, and keeps the place function's frame. The call to `0xCA76B0(lot, 0)` at `0xCAEF5F`, which every path after the cell write reaches (success, the three undo branches and the failed write at `0xCAEF53`) and which is also the delete path's last call, goes to `StPlaceEndStub`: when the record belongs to this call (same frame and lot) and the write succeeded (`[frame+0x12]`, stored at `0xCAEEAE`; the epilogue returns it from there, `0xCAEF7A`), it runs `0xCA7E00` once with the kept arguments and recheck 1, then jumps to EA's `0xCA76B0`. So the place path follows the delete path's order and flag exactly.

Why it is safe [verified unless tagged]:
- Arguments: lot (`esi`), undo object (`ebx` = arg 6, still used by the undo branches after the write) and arg 9 are unchanged by then; the corners are copies. `0xCA7E00` and `0xCA76B0` are plain cdecl without register inputs.
- Nothing between the old and the new call site needs the stilts gone: `0xCA7C50`, `0xCA8220`, `0xCA8570`, `0xCA86B0`, `0xC5D920`, `0xCAAC80`, `0xCAE470`, `0xD1E190`, `0xD1D080` and `0xCA76B0` reach neither `[lot+0x2B8]` nor any function in `0xC1A000`-`0xC20000` within three direct-call levels (a control-flow scan of each function and its direct callees, positive control `0xCA7E00`; virtual calls not followed). The delete path runs the same functions with the stilts still present.
- One removal per placement: the original call is gone, the deferred one runs once and clears the record first; a record not of this call (another frame or lot) or a failed write is dropped and logged, never run. A failed write therefore removes nothing (EA removed the stilts before it knew).
- Result: recheck 1 removes a subset of what EA's place path removed (inside the block the same, on the edge only stilts no stilted cell needs) and may move an edge stilt whose inset changed, as delete does.
- Undo [inferred]: the stilt edits are now recorded after the write's records, the delete path's order; undo / redo of a placement was not traced (`0xD1D2B0`).
- Counters `srPlaceMode` (+0x6B58), `srPlaceRecheck` (+0x6B5C, removals run after the write). Log: `stilt place: removal in block (x0,z0)-(x1,z1) level a-b run after the cell write with the neighbour check (N so far)`, `stilt place: deferred removal ... dropped (cell write failed | not this call ...)`, first 8 then powers of two.
- Sites byte-checked first (`0xCAED4D`-`0xCAEDB1` with the call target, `0xCAEEA9`-`0xCAEEB8`, `0xCAEF5C`-`0xCAEF84` with the call target); the end call is written before the defer call. EA 1.69 / retail: no address, SKIP. Save data: none beyond the stilts EA keeps.
- Tester check: Build mode, a stilted foundation, then a regular foundation or deck placed touching one side: Off: the stilts on the shared side disappear. On: they stay, `stilt place: ...` lines in ts3native.log. Undo the placement and redo it once.

## 6. `PartClamp=1`: stilt partition index at a lot's far edge

**Index sites [verified].** The manager files every stilt in an 8x8-tile partition (`+0x5C` array of 32-byte entries, `+0x6C` cols = `(([lot+0x174]-1)>>3)+1`, `+0x70` rows from `[lot+0x178]`, `+0x74` cols*rows; `0xC1F780` / `0xC1F390`): `idx = (floor(z)>>3) * cols + (floor(x)>>3)`, unsigned shifts, no bound check, in exactly two functions: insert `0xC1CF80` (callers build `0xC1E530` and the rebuild `0xC1F473`) and remove `0xC1C120` (caller `0xC1E8F0`, the apply step's removal, `0xC1E945`). The query `0xC1F4D0` clamps its range to `[0, cols-1]` / `[0, rows-1]` (`0xC1F69D`-`0xC1F6D7`) and only reads. No other code in the manager indexes the array (`+0x6C` / `+0x5C` / `+0x70` users: the two functions, the query, init, rebuild, ctor `0xC1D8D3`, dtor `0xC1D6B0`; `0xC1C827` is a group record copy).

**Which point [verified].** The grid point, not the inset render position: build `0xC1E4D0` inserts `{arg1, arg2, 0}`, the struct it keys by, and the apply step `0xC1EED0` passes edit `+4` / `+8` (the grid point; render x / z are `+0xC` / `+0x10`) as arg1 / arg2 (`0xC1EFD9`, `0xC1F060`); the rebuild inserts node `+0x24` / `+0x28` = record `+0x14` / `+0x18`. `[lot+0x174]` counts tiles: cells are valid for `0 <= x < [lot+0x174]` (`0xCAAECC`, inside the cell write), grid points for `0 <= x <= [lot+0x174]` (`0xCAF240`).

**Reachability.** A stilted cell in the last column (x = W-1) has stilts at x = W. With W a multiple of 8 (40, 64) that gives col = cols: the stilt is filed in the next row's first partition, which the query never reads for that block (the stilt cannot be collected: delete leaves it), and in the last row idx = cols*rows (one entry past the array; the same for z = D: a whole row past it, a heap overwrite at insert). Whether Build mode lets a stilted foundation touch the far lot edge was not traced (no placement rule found that forbids it; the cell write accepts x = W-1). [inferred] reachable on 40- and 64-wide or -deep lots with a stilted foundation on the +x / +z edge; never seen in our runs.

**Fix.** The four `mov reg,[esp+10h]; shr reg,3` (row and column in insert `0xC1D03E` / `0xC1D06B` and remove `0xC1C1E0` / `0xC1C20D`) become calls (+ 2 nops) to stubs that return `min(v>>3, n-1)` (a negative v gives 0), n = rows or cols from the manager, keeping the registers the function still uses. Insert and remove clamp alike, so a clamped stilt is found and removed again; with the clamp, x = W lands in column cols-1, which the query reads for every block that touches the last column. Unreachable cases cost nothing: points inside the array get EA's index. Both functions (`0xC1D03E`-`0xC1D07E`, `0xC1C1E0`-`0xC1C21C`) are byte-checked before any write. Partitions are not saved (rebuilt at every load), so no save data. Counters `srClampMode` (+0x6B60), `srClamped` (+0x6B64). Log: `stilt partition index clamped (insert|remove row|column): grid v -> i of n (N so far)`.
- Tester check: a 40x40 or 64x64 lot (Edit Town), a stilted foundation whose side lies on the lot's far edge (the side away from the lot's origin corner; try both far edges), then delete it. Look for `stilt partition index clamped` lines; with the clamp the edge stilts go with the foundation.
