# 91. Routing I/O study, part A: what the route search reads

Written 2026-10-18. Static only: the game was not run, no probe, no native code. Part A of the 4-part I/O study that follows the wait split (PLAN item 6, `ip-ar-ab-wait`): the moved planning came back as waits on the game's shared routing data, so per-site fixes only move the wait. The plan now is to replace the game's route **search** with our own search over our own **snapshot** of the routing data, so the worker never touches game state. This doc lists the search's **data inputs**. Out of scope here: portals and script callbacks, route-object parameters and dynamic obstacles (part B), outputs (part C).

Tools: Ghidra headless decompiles on a private copy of the docs/89 project (`game-copy/ghidra-io-a`, copied from `ghidra-usf`, read-only runs); capstone 5 on `game-copy/bin/TS3W.exe` (Steam 1.67) with `game-copy/analysis/functions.csv`; a direct-call closure from `Route_PlanLocked 0x82C6E0` (12 hops, stopped at `Lock_Acquire`/`Lock_Release`/`EA_AllocTagged`): **1,289 functions, 856 register-indirect call sites**; the vtable store index from docs/82 (1,633 vtables, 76 with constructors in the routing ranges `0x600000-0x680000` / `0x800000-0x840000`); a DBPF index reader over the installed `.world` packages for resource sizes. Effort figures are days for Claude working with Rodney (CLAUDE.md).

Tags as in AGENTS.md: **[verified]** = read in the disassembly, decompile or a package index (address or file given); **[inferred]** = reasoning, to confirm with the §6 probe.

## 1. Summary

- **Twelve input families** (§2). Five are static per world and can come from package data: the world waypoint graph R, the terrain heightmap, the lot/level/room skeleton, the lot placement in the world, tuning. Four change in play and exist only in live memory in their current form: the per-level lot quadtrees with their footprints, the water passability marks, the physics loose quadtree (object shapes), and the lazily built room connectivity. Three are planner-private caches or scratch that our search replaces outright (A\* scratch, world-planner caches, the lot table itself as an index).
- **The world-level graph is a packed waypoint grid, not the road graph** [verified]. The search reads `RTData` **R** embedded in the routing world at `world+0x54` (32 m chunks, per-chunk waypoint records with packed neighbour references and per-edge bytes). It is loaded from one resource of type **`0x05CD4BB3`** per world (`0x66D110`, called under `+0x918` from `RoutingWorld_LockedOp_WorldInit 0x829410` and `RoutingWorld_LockedSaveStep 0x829F10`), 0.74-1.17 MB in memory (§3.1). The street/footpath graph `WorldRoutingData` (`0x810310`) is only the build-time source (`IC_World_BuildRoutingDataImpl`, world save) and is not in the plan closure. This sharpens docs/60 §1.1 and docs/18 Q2 ("routing world graph"): what the plan reads is R, and `WorldRoutingData` is only R's source at build time.
- **`[world+0x960]` is the world planner, not a water planner** [verified]. It is "PathPlannerWorld" (0x198 bytes, constructor `0x657C50`, vtable `0xFED364`, initialised by `0x654060` with the current-lot value `[world+0x964]`, P, R and the water/cell grid **G** at `world+0x8C`). The world A\* `0x676260` runs with `this` = W+0x18 (an embedded PathContainer), graph R, grid G. Corrects docs/60 §1.1 ("water planner `+0x960`").
- **The plan itself writes four of its inputs** [verified paths]: pending lot updates rewrite R's waypoint blocked bits (`RoutingWorld_ApplyLotUpdate 0x82B590` at every plan start when `P+0x10E` is set); a lot-table miss inserts a lot entry; first use of a lot builds its lot graph, quadtrees and footprints (`RoomGraph_FirstUse 0x63D2F0 -> LotGraph_Build 0x63CB90`), which also writes water marks into G (`0x62D9F0 -> 0x670510`); quadtree queries flush deferred inserts and removes. A snapshot builder must do these on the sim thread (or at snapshot time) so the worker's search stays read-only.
- **Static base exists for the lot side too** [verified package index]: every world package carries per-lot routing resources `0x046A7235` (levels, footprint membership, quadtrees; 12.5-27.0 MB in memory per world) and `0x07CD07EC` (24 bytes per lot), loaded by `RoutingWorld_LoadLotData 0x82CA10` (version 5) and also written into every save (docs/25, docs/26). Saves then diverge with play; the live state is what the search must see.
- **Snapshot size per world** [inferred from package sizes]: about 1 MB (R) + 2-3 MB (G) + 13-27 MB (lot routing, serialized size; live structures with pointers are larger) + small tables. A full copy per plan is out of the question; the snapshot must be built once at load and updated per lot (or per level) from change events. The docs/76 and docs/79 dirty hooks give the object side; this doc adds the routing-side writers per input (§3).
- **Blockers for a pure package-built snapshot:** (1) footprints and quadtrees change with every object move, parent change and Sim footprint toggle (docs/89: the per-object footprint writers alone wait 15 ms/s BP / 19 ms/s IP in `env-on`), so the lot side must be copied from live memory or rebuilt by our own code from the same object events; (2) the in-room graph *is* the quadtree (§3.6), so a copy needs the quadtree cell structure, not only the footprint polygons; (3) the water grid G is built from the heightmap, lots, roads and footprints by `0x6734A0`, which the plan closure does not reach, and no static caller at plain world load was found (open, §5) (corrected 2026-10-18, see docs/100 §1: G is built at every world load, on the main thread, by message `0x38E3C1E` to `RoutingWorld_OnMessage 0x835300`, which Ghidra never turned into a function).

## 3. Details per input

### 3.1 World waypoint graph R

- **Record format** [verified, `WorldRoutingData_LoadChunks 0x810720` builder and `0x66D110` loader]: per chunk a u16 waypoint count, then a u16 offset per waypoint (relative to the chunk start). Each waypoint: byte `+0` edge count n, byte `+1` flags (low 5 bits = waypoint type, `0x40` = per-edge extra byte present, `0x80` = blocked), byte `+2` surface class (computed at load by `0x66CB90`: type 1 gives `0x28`, type 7 gives 10, type `0xD` gives `0x1F`, otherwise the terrain type at the point from `0xC6C0C0`), bytes `+3/+4` = x/z offset inside the chunk (scaled by `DAT_00FE8278`), then n u16 neighbour references (bits 0-9 waypoint index, bits 10-12 chunk dx+3, bits 13-15 chunk dz+3: neighbours lie within ±3 chunks), then n bytes per edge when `0x40` is set. Record size 5 + 3n bytes. Waypoint index is 10 bits, so at most 1,024 waypoints per 32 m chunk.
- **Who reads it in a plan** [verified]: `WorldAStar_Search 0x676260` (graph argument; neighbour decode at the closed-bitset test), the four cost modes `RouteCost_Mode1..4` (`0x674E40`, `0x673850`, `0x674250`, `0x675800`; mode by travel kind) plus the switch default `RouteCost_Default 0x6734E0`, a fifth target (corrected 2026-10-18, see docs/102 §1), the closest-waypoint search `0x65BC20` ("Routing/closestWps"), street analysis `0x659BC0` ("Routing/StreetRuns"). Mode 3 also calls `World_LotLookup`, `World_GetHeightAt` and `RoutingWorld_Get` [verified calls; per edge inferred].
- **Components**: after load `0x66CE10` floods connected components ("Routing/seeds"), one byte per waypoint (`-2` unassigned, `-1` for type `0xE`) [verified]; the planner uses them to reject unreachable goals early [inferred].
- **In-play writes** [verified]: `ApplyLotUpdate 0x82B590` walks the lot's edge waypoint list (`0x651DA0`, W) and sets or clears bit 7 of the flag byte per waypoint (from `0x633EA0` and the lot-edge flag hash `+0x144` via `0x625480`/`0x624750`), and mirrors it into bit 29 of word `+0x4C` of the matching entry in the outside room record's list `+4` [verified offsets; "outside room portals" as the meaning is inferred]. Same pattern in `0x832890`. Both run under `+0x918` on the sim thread; `ApplyLotUpdate` runs inside `Route_PlanLocked` (pending updates) and from build/buy exit.
- **When R is absent** (`world+0x97D` = 0, copied to W+0x88 at `0x82C753`), the hierarchical planner skips the world leg and plans lot-only (`0x65E0D0`, test on `[W+0x10]+0xC` and W+0x88) [verified].
- **Snapshot**: parse resource `0x05CD4BB3` (or copy R's two arrays once after load, 1 MB), then replay lot-edge blocked bits from our lot copy. The per-lot edge waypoint lists are in the lot graph (`+0x124` hash) and in W's caches.

### 3.2 Water/cell grid G

- Read by: the job's start classification (`0x66DA10` on the start cell), `PathPlan_WithRetries 0x661B50` (start/goal cell water test, `0x66D850` cell index from world origin `WM+0xB4/+0xB8`, `>>2` = 4 units per cell), the world A\* and cost modes (grid argument), and the water planner `WaterPath_Plan 0x671930` -> `WaterJps_Search 0x620560` (byte grid g1 per boat class chosen from the route's option word `& 0xCF00`: `0x4100`, `0x4200`, `0x4300` give classes 2-4; mark grid g2 index from `0x66D6E0`) [verified].
- Built by `0x6729D0` from the terrain heightmap (`0xC2A370`, "Terrain/TerrainData/HeightMap"; "World/HeightMap" `0xAA85D0`), lots (`WorldManager_GetLotList`, `World_LotLookup`), road polygons (`0xB7CB60`, `0xB74D10`), low bridges ("Routing/lowBridges"), sea level (`0xC61670`) and footprint polygons ("Routing/footprintVec", "Routing/tileAsPoly"); "PathPlan/PassabilityMap" grids from `0x61F5C0` [verified strings and calls; roles inferred].
- Marks: `0x670510` (2 call sites in `0x62D9F0`) and `0x670750` (from `0x6729D0` and from `0x6733C0` under hanging footprints `0x636BF0`) write the `+0x7C0` grids [verified]. `0x62D9F0` runs inside `LotRouting_RemoveObjectFootprints 0x635700`, i.e. on every footprint update of every object (and inside lazy lot builds in a plan) [verified callers]; which cells it marks (only water cells under docks and boats, or all) is not read yet (open).

### 3.3 Lot placement and lot index

`World_LotLookup 0xC68990` maps a world point to a Lot object through the world manager's lot grid hash (`0xC688A0`), rebuilding it first if dirty (`0xC68680`, lock `wm+0x228`). The search then uses the Lot's 64-bit key (`+0x48/+0x4C`) to reach the lot table and `Lot_WorldToLocal2D 0xAB8540` or the lot graph transforms (`+0xA0..+0x11C`) for local coordinates [verified]. `0xB01390` (job start test) and `0xAB1F00` (lot level/floor helper, called by the hierarchical planner and lot builds) read the Lot object too [verified calls; field roles not read]. Static per world except edit-town changes; the docs/60 §1.4 #5 race (unlocked readers of the lot list) disappears once the worker reads our copy.

### 3.4 Lot table and lot graph

See docs/80 §2 (table) and the layout row above. The plan reaches `LotTable_GetOrInsert` from `LotTable_LotHasPendingUpdate 0x631A60` (pending updates), `LotSearch_Entry 0x640E00`, `LotPlan_Inner 0x63F6E0`, `InRoomPlan 0x632E40` and `QuadTreeBuild` [verified]. Our snapshot keys lots directly; it does not need the game's table, only its contents.

### 3.5 Room connectivity (lazy)

`RoomGraph_FirstUse 0x63D2F0` builds the room records on the first plan that needs a lot: it calls `LotGraph_Build` if `+0x8C` is clear, resets the A\* search object, and runs room-to-room A\* (`RoomToRoomAStar 0x6339F0`, "Routing/startSet", "Routing/AStarGoalNode") to fill "Routing/connected" and "Routing/portalGoals" [verified calls and tags]. `LotGraph_Build` reads the Lot (`FindLotById 0xC62D40`), its level count (`0xB48850`), validates portals (`0x636330`, "ValidateLotData/activePortalSet"), collects object footprints ("Scratch/footprintList" `0x626F40`), hanging footprints (`0x636BF0`), room ids (`0x635440`), lot-edge and tunnel footprints (`0x63A1C0`, `0x639DE0`), builds the per-level quadtrees and inserts the footprints [verified]. For the snapshot this is a **derivation**: our builder can run the same derivation (or call the game's on the sim thread before copying) so the worker never meets an unbuilt lot. `LotGraph_RebuildRooms 0x63D7B0` and `RoomGraph_Refresh 0x63D860` are the rebuild entry points after lot edits.

### 3.6 Per-level quadtrees = the in-room graph

The in-room planner (`InRoomPlan 0x632E40` -> `QuadTreeCellAStar 0x61E500`) searches over **quadtree cells**: start, graph and goal nodes are objects of three small classes (vtables `0xFE9AD0` constructor `0x61AC40`, `0xFEA080` "cAStarGraphNode" `0x61B380`, `0xFEABD0` `0x61EB40`; (corrected 2026-10-18, see docs/98 §1 and ledger I-98-1: `0xFE9AD0`/`0x61AC40` is the GOAL node, 0x50 bytes, and `0xFEABD0`/`0x61EB40` the START node, 0x48 bytes), whose slots `+0x10/+0x14/+0x1C` are folded constant stubs (start/goal tests) and whose expand slot `+0x2C` is `0x61AF40`, which touches only A\* state (`AStarSearch_NodeState 0x61E030`) [verified]. Neighbours come from the cell walk `0x66BFD0`/`0x72C920` over the level's quadtree, with footprint membership per cell from the leaf entry masks (`LotQuadTree_CollectLeaf 0x669850`, `CollectMasked 0x669230`, "QuadTreeCellPos/parentFootprints" `0x66B090`) [verified calls; neighbour rules not read]. Iteration cap per in-room search: 64000, or `0x40002` when the context flag `0x100000` at `+0x50` is set [verified]. So a snapshot of a level must keep the cell subdivision and the per-cell footprint lists; a flat polygon list would force our own cell decomposition (which is fine for our own search, but then results differ from the game's).

### 3.7 Footprints read by the search

Reads (docs/83 §2 for the gather path, extended to the planner): id, class and type bytes, the `+0x28`/`+0x60` predicate slots, the per-level polygon cache and its bounds; the cost of a cell or portal edge also reads portal lock and discourage state (`PortalEdgeCost 0x634500` -> `Portal_IsLocked 0x64F550`, `Portal_IsDiscouraged 0x64F570`; part B). The 9 concrete classes and their slots are resolved in docs/82 §3.1; the planner closure adds no class beyond them [verified: every footprint constructor in the 76-vtable inventory is one of those 9 plus the base `0x10205B8` and middle `0x1020AE8`].
