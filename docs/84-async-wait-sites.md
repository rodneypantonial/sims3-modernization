## 1. Summary

Input: probe P0 (0.11.4, `bp-p0-async`, queue on, seeded, 10 min, 10,996 jobs): the sim thread waited 44.4 s = **73.9 ms/s** during jobs [verified, `h6-m1-2026-10-17-bp-p0-async-native.json` `blockKey/N/Us`]. ## 2. Discourage footprints

### 2.1 What runs under `+0x918`

`IC_RouteManager_RemoveDiscourageFootprint 0x754580` and `IC_RouteManager_AddDiscourageFootprint 0x75DB50` look the object up by its 64-bit id (`ObjectService_FindById`, sim-only map), take an atomic reference (`lock` add on `[obj+4]`), call the internal function on the routing world and drop the reference (atomic, delete at zero). The Add IC first converts the script float array to a vector of 16-byte points through script host slot `+0x78` and frees it after the call [verified decompiles]. The internal functions are `thiscall(world)`: `RoutingWorld_RemoveDiscourageFootprint 0x834860 (obj)`, `ret 4`; `RoutingWorld_AddDiscourageFootprint 0x834370 (obj, points, highImpassable, allowPlacementInWorld, placementFootprint)`, `ret 0x14` [verified]. Each has one caller, its IC (`0x7545CC`, `0x75DC82`) [verified, docs/60].

**Remove `0x834860`** [verified disassembly `0x834860..0x8349B3`]. Returns 0 without the lock when world `+0x974` is 0 or obj is NULL (`0x834868..0x834878`). Then: `+0x918` (`0x83488B`); footprint component `C` = `Object_GetComponent(g_CompBit_Footprint 0x11E8FA8)`, return 0 if none; `Locomotion_Notify 0x947590 (C, 1, 0)`: writes bit 0 of `C+0x40` and, if it changed, calls `RoutingWorld_UpdateSimFootprint 0x833560` (`+0x918` again, recursive); transform component read; `0x947A90 (C, NULL)`: swaps the component's polygon pointer `C+0x2C` (AddRef/Release through its slots 0/+4) and rebuilds the array `C+0x48` from the list `0x9342D0` (resize `0xAEF830`). Then the lock-key map at world `+0x8B8` (buckets `+0x8BC`, count `+0x8C0`, size `+0x8C4`, keyed by the object id at `obj+8/+0xC`): on a hit it erases the node (`0x82CED0`, frees it); on a miss it calls `0x635700 (lot, id)` (`ecx` = planner P `[world+0x95C]`), which finds the object's footprints per quadtree level (`0x6649C0`), removes them (`0x635440`, `LotQuadTree` remove `0x6675B0`: deferred-flag or flush) and marks the lot (`0x62D9F0`), then clears world `+0x994`. Last, `P+0x10D` is set to 1 around `RoutingWorld_UpdateObjectFootprintCore 0x8321F0 (obj, 1, lot, 1, 0)` and restored (`0x624620`), `+0x918` released, return 1.

**Add `0x834370`** [verified decompile]. Returns 0 without the lock when `+0x974` is 0, obj is NULL or fewer than 3 points. Under `+0x918`: footprint and transform components (return 0 if no footprint component); the object's lot and level from its position (`0xB03750`: `World_LotLookup` or `0x789040`, level via `0xADD740`); active-lot test `0xC88FD0`; `0xC62D40` (`WorldManager_FindLotById` plus lot vtable `+0x40`); lot-membership component (`0x749660` = `Object_GetComponent(0x11ECF08)`) and **`0xC8ADD0`**, which, when the object's stored lot `comp+8/+0xC` differs from the lot just found, stores the new lot, calls `0xC89AB0` and fires **`World_FireEvent(0x11)`** through `0xC8A290` (object lot changed; a managed callback) [verified `0xC8A346`]; `Locomotion_Notify (C, 1, 0)`; the points are moved into object space with the inverse object transform (`0x958EE0`, `0x829600`); a polygon object `"Routing/DiscourageFootprint"` (`0x82A5C0`) is appended as a 0x40-byte record to the component's list (`0x9342D0`, grow `0x82F7F0`), set with `0x947A90`; then `UpdateObjectFootprintCore (obj, 1, lot, 1, flag)` under the same `P+0x10D` bracket; release.

**`UpdateObjectFootprintCore 0x8321F0`** (both paths, hop 1) [verified decompile]: takes `+0x918` (recursive); reads the lot, footprint, transform and steering components (`0x953690`), the level offsets (`0x948090`); per level allocates a `"Routing/ObjectFootprint"` (`0x80C780`) and inserts it (`LotRouting` insert `0x6376D0` -> `LotQuadTree_Insert 0x666C50`) or parks it in the lock-key map (`0x82DC70`); then for the component's polygon list builds a `"Routing/PrivateFootprint"` (class `0xFEBBC0`), removes the old one (`0x635700`), sets its polygons (`Footprint_SetLevelPolygons 0x80F6A0`) and inserts it.

**Locks, in order** [verified sites, 5 hops]: `+0x918` first; inside it `+0x918` again (`0x832253`, `0x83358E`, `RoutingWorld_UpdateLotLocked 0x82C157`, `RemoveFootprintLocked 0x82A0F1`), then leaves only: entry pool `0x11CEFA8` (`0x61ED8B`), `0x11D8F90` (`0x807455`), footprint registry `0x11D9068` (`0x80EDDC`), `wm+0x228` (`WorldManager_RebuildLotIndex`, hop 4), allocator. Nothing takes `+0x918` while holding a leaf. **Managed / remote / event:** Add reaches `World_FireEvent(0x11)` at hop 2 (above); Remove reaches none within 5 hops [verified, direct calls; footprint and component vtable calls not all resolved]. `0xD726F0` inside `LotQuadTree_Insert` is a plain chained-hash find that only lives in the Mono address range, not a managed call [verified decompile]. No `0x7D98C0`, `0xD75FA0`, `0xEA1400` [verified]. Closure size: Remove 298, Add 377 functions at 5 hops, still open at hop 5 (§2.6).

### 2.2 What script gets back

Both C# wrappers return the native `bool` (`ScriptCore.RouteManager`, `Sims3.SimIFace.Route.AddDiscourageFootprint`/`RemoveDiscourageFootprint`) [verified]. Every gameplay caller ignores it: `DynamicSimFootprint.Enabled` (the Sim's own footprint, toggled through `SimRoutingComponent.Enable/Disable/ForceUpdateDynamicFootprint`, 122 call sites: postures, route interrupt actions, reset, dispose), `Sprinkler`, `LotManager`, `PlatformPortalComponent`, `PetSurfaceComponent`, `SittableComponent`, `PetGuardSitutation`, `DynamicRegionBase` [verified grep]. Only two debug interactions in `GameObject` (`DEBUG_*DiscourageRegion`) return it as their `Run()` result [verified]. The native side writes nothing back to script except the event `0x11` above. So a deferred call can return the value the original returns before its lock (0 for the early outs) and 1 otherwise; only the debug interactions could see a 1 where the original says 0 (no footprint component).

### 2.3 Running the calls on the routing worker (co-location): not as they are

The worker could hold `+0x918` and run queued calls between jobs, but the calls are not routing-only [verified §2.1]: (1) Add can fire the managed event `0x11` (the worker must not run managed code; a proxy brings it back to the sim and costs a tick per call, docs/60 §2.1); (2) both read the object model while the sim mutates it: object transform (a walking Sim moves every tick: torn matrix, footprint in the wrong place), components, the lot index; (3) both write the Sim's footprint component: `C+0x40` bit 0 is a plain byte read-modify-write that the sim also does every tick from `Animation_UpdateActors -> Locomotion_Notify` (docs/82 §8), and `0x947A90` reallocates `C+0x48`; (4) `Locomotion_Notify` reaches `UpdateSimFootprint`. Making the worker variant safe means splitting each call into a sim half (object model, component, event) and a routing half and re-implementing `UpdateObjectFootprintCore` on snapshots. **Not feasible at this size**; the deferred variant below gets the same wait removal.

### 2.4 Design D: defer on the sim thread, apply in order when no job runs

Detours **D1** `0x834370` and **D2** `0x834860`, sim thread only. **Defer** when all hold: a job runs (`g_async.state == A_RUNNING`); this thread does not own `+0x918` and is not serving the job (`tid == g_async.owner && g_inInvoke` means borrow: call the original); the queue has room. Else, if the queue is not empty, take `+0x918` (waits as today), drain, then call the original; if empty, call the original.

Defer steps: (1) the original's lock-free early outs, same result (`+0x974`, obj, Add: count < 3 returns 0); (2) record `{kind, object id = obj+8/+0xC, Add: copy of the n x 16-byte points and the three flags}` in a FIFO (cap 256); (3) return 1. No reference is kept: the id is resolved again when applied.

**Apply (drain)** on the sim thread, outermost owner of `+0x918` with no job running (uncontended acquire, never a wait). For each record in order: `ObjectService_FindById(id)` (sim-only map, sim thread); not found means the object was destroyed: drop the record (destroy removed its routing footprints [inferred], and an Add for a dead object must not create one). Else atomic AddRef as the IC does, call the original internal function with the world, the object and, for Add, a vector `{copy, copy + 16n, copy + 16n}` (it reads only begin and end [verified]), atomic Release. Records added while draining (an event handler calling the IC) go to the tail: the drain runs until empty, so order is kept.

**Drain points.** Add may fire a managed event, so Add records drain only where the sim is already inside a script IC: `GetOptionHook` (READY poll and START, `ts3native.cpp` ~1281; also the moment a new job is queued, so a plan asked after an Add is queued after it is applied, when no job is running), D1/D2 themselves, the destroy stub `0x939420`, and the coarse gates `0x835110`/`0x835240` (build/rebuild ICs). Remove records also drain at any outermost sim `+0x918` acquire when no job runs (`LockAcquireHook`, `RgEnter`). FIFO: a pending Add stops later records from draining at non-IC points.

**Ordering and visibility** [inferred unless marked]:
- Same object, add then remove (or `ForceUpdateDynamicFootprint`: remove then add): FIFO applies them in script order. No coalescing.
- A job already running when the call came: it planned without the change in today's code too (the call waited for it). A job started between defer and apply plans on the world one job earlier. Option **G** (`[Discourage] Gate=1`, for A/B): the worker does not start a job while records are pending; the sim drains at its next `GetOptionHook` poll. G keeps today's order exactly but idles the worker up to one poll interval per drain, so default off.
- Sim-thread reads during the gap (steering, `IsPointObstructedBySim`, the §3 read-only queries) see the world without the change, i.e. one tick older. Script cannot read the routing state of the footprint directly; its own flag (`DynamicSimFootprint.mbEnabled`) is managed state and changes at once [verified].
- The Sim's own replan right after a toggle (`ObstacleEncounteredRouteInterruptAction` enables, then `Replan`) [verified C#]: the planner excludes the planned Sim's own footprints by id [inferred, docs/83 §5 exclude path; tripwire T-D4].
- `Locomotion_Notify (C, 1, 0)` runs later than today: if the per-tick call from `Animation_UpdateActors` sets the bit first, the deferred call returns early; if it sets the opposite value first, the deferred call flips it and the next tick's call flips it back (it compares with the stored bit every tick [verified `0x947590`]). One-tick transient.
- Overflow, save, world teardown: wait, drain, then the original (no record may be applied after a later call).

**What the drain touches:** exactly the originals, on the thread that runs them today, holding `+0x918` with no job running, i.e. today's preconditions. The worker touches nothing new.

### 2.5 Hooks, counters, gain, risks

| Hook | Bytes (stolen length, read from the exe) | Convention |
|---|---|---|
| D1 `RoutingWorld_AddDiscourageFootprint 0x834370` | `55 8B EC 83 E4 F0` (6) | thiscall, `ret 0x14` |
| D2 `RoutingWorld_RemoveDiscourageFootprint 0x834860` | `83 EC 14 53 55` (5) | thiscall, `ret 4` |

Neither has a ts3native detour today and docs/68 does not list them [verified grep]; run `tools/hook-sites.ts --check` before building. Drain calls go into existing hooks (`GetOptionHook`, `LockAcquireHook`, `RgEnter`, the destroy and coarse gate stubs).

Counters: `vfDiscDeferred[add/remove]`, `vfDiscApplied`, `vfDiscDropped` (object gone), `vfDiscPendingMax`, `vfDiscAgeUs` (defer to apply, max and sum), `vfDiscJobsWhilePending` (jobs started with records pending), `vfDiscOverflowWait`, `vfDiscNested` (records added during a drain). Tripwires: **T-D1** `vfDiscDrainInJob` (a drain while a job runs or without `+0x918`) = 0; **T-D2** `vfDiscOrder` (per-object sequence numbers applied out of order) = 0; **T-D3** `vfDiscEv11` (event `0x11` fired during a drain at a non-IC point) = 0; **T-D4** `vfDiscSelfPlan` (a job started for an object with a pending record of its own) for the ordering note above. Shadow check: none possible for a deferral (the effect is the routing world later); verify instead with the routing debug dump or a probe that, after each drain, compares the object's quadtree footprints with a sync run of the same seed. Repro per AGENTS: an agent trigger that makes several Sims stand and walk (route interrupt actions, posture changes) during a burst of plans, plus a `repros.json` entry.

**Gain:** up to **21.4 ms/s** (28.8%) of sim wait [inferred upper bound]. **Risks:** a job planning one step earlier (G removes it); the Add event moved to a later IC point; records for objects whose id is reused (64-bit ids are not reused [inferred]); unresolved vtable calls in the originals (they run as today, so this adds no new risk).

### 2.6 Closure

The new code (precheck, record copy, id lookup, drain loop) is ours and calls only `ObjectService_FindById` and the originals. The originals do not close at 5 hops (Remove 298, Add 377 functions, frontier open at hop 5) [verified], but they run on the same thread, under the same lock and with no job running, exactly as today, so **no 6-hop pass is needed**. The one property that matters, managed reach, is found at hop 2 (event `0x11`) and handled by the drain points.

## 3. Steering: `RoutingWorld_ObstacleQuery 0x82EDB0`

### 3.1 What it does, and what it reads beyond `0x82F0B0`

`thiscall(world)(point, radius, outVec, collectMode, optionWord)`, `ret 0x14` [verified]. Same shape as `0x82F0B0` (docs/83 §2): `+0x918`; release and empty `outVec`; `World_LotLookup` on the point (no lot: release, return 0); a stack context `ctx` with `ctx+0x54` = lot, `ctx+0x40` = pointer to an option record whose first word is `optionWord` and whose words 2-3 (an id) are 0, `ctx+0x50` = 0, a `"Routing/PortalCheckCache"` hash and a footprint set; then `LotRouting_FootprintsNearPoint 0x631F10` (`Contains` gate 13, `0x62FB10`, transform `0x62ED40`, then `QueryPoint 0x667480`: flush if `Q+0x48 < 1`, `Q+0x48` plain +1/-1, walk `0x663E20` with visitor `0x662DD0` (mode 1, class filter) or `0x662DB0` (mode 0, collect all), passing `ctx`); copy into `outVec` sorted, with the same refcount pattern as `0x82F0B0`; free; release [verified decompiles].

Differences from the `0x82F0B0` read set [verified unless marked]:
- **Point walk `0x663E20`** instead of the segment walk: its helpers (`0x669BE0`, `0x669C30`, `0x669C20`, `0x669CB0`, `QuadTreeCellPos_B 0x66A040`, circle-cell test `0x66A8E0`) read `Q+0x24/+0x38/+0x44` and cell data and write only the iterator array on the walk's stack.
- **Non-NULL context in the visitor** (`0x669CD0 -> 0x669230/0x669850/0x669B90`). The option-object branches read `[record+0x28]` (`0x8294E0`), which is the frame word that `0x82EDB0` sets to 0, so the routing-options tests (`RoutingOptions_Test 0x81C880`, the id list `0x81C970`) are skipped; `ctx+0x50 = 0` skips the type `0x13/0x18` and `0x1E` branches. What remains: slot `+0x60` with `optionWord` (true stub `0x9C1B00` in all 9 classes), slot `+0x84` -> `+0x7C` (`0x620CC0` -> `0x806FE0`: id `+0x14/+0x18`) compared with the record's zero id, and slot `+8` with the record: `0x80F840` (reads `+0x40/+0x44`, `+0x34`), `0x807090` (classes `0xFEBA98`, `0xFEBE38`, `0xFEB5F8`, `0xFEB720`, and via `0x807B70` `0xFEBD10`: if `[fp+0x20]` is set, the emptiness of two id vectors of that object, `0x946E70`/`0x946E90`, then byte `+0x34`), `0x80C300` (`+0x41` flags, `+0x34`), `0x8066C0` (id), `0x6119F0` (0).
- **New field `fp+0x20`**: a reference-counted lock-key object set through slot `+0x8C 0x807110`. Of the 61 register-indirect `+0x8C` call sites in the exe, the ones in routing code are `RouteManager_FootprintLockKeyApply 0x82B2B0` (from the lock-key ICs), locomotion code (`0x81F550` from `0x8469F0`, `0x849810`, `0x84AF20`, `0x852700`, `0x9566C0`) and `0x80C8C0` (no direct caller, a vtable slot itself); none in the planner (`0x64xxxx`-`0x65xxxx`) [verified scan; receiver class and thread inferred]. So the sim RO reader is on the writer's own thread.
- No polygon cache, no object id hash, no lock, no managed or event call in the query (docs/81 §3, docs/82 §4).

### 3.2 What the locomotion caller does with it (the reason to clone the whole caller)

`Locomotion_ObstacleCheck 0x85FD10` (`thiscall(agent)`, 5 args, `ret 0x14`, end `0x85FF29`) [verified]: for the first path node with flag `node+0x30`, it converts the node (`0x85AE60`) and calls `0x82EDB0` twice with identical arguments (`0x85FE0B`, return `0x85FE10`; `0x85FE7C`), mode 0 and option word `agent+0xB8`, into the same stack vector (the second call empties and refills it); then for every flagged node it calls `RouteFollow_EditPath 0x85F5A0` (`0x85FED7`) with that vector as `exclude`; then frees the vector (`0xAAC090`). `EditPath` uses `exclude` only by object id (docs/83 §5). P0 shows the wait at the first call only; the second call and `EditPath`'s `0x82F0B0` find the lock free because the first wait ran to the end of the job [inferred from P0: no `0x85FE81` or `0x85FEDC`/`0x85F6CB` key]. **A read-only first call alone would move the wait to the second call or to `EditPath`.** The design must cover all three.

### 3.3 Does the docs/83 writer set cover the point walk?

Yes for every structure the point query shares with the segment query (lot table W5, lot entry W4/W5, Q W2/W3, nodes and entries W1/W2, footprint lifetime through `FootprintMapEntry`). The extra reads of §3.1 are written at construction (`+0x40/+0x44`, `+0x41`, `+0x34`; `Footprint_BaseCtor 0x807A20` zeroes `+0x20`) or by sim-thread code (`fp+0x20` and its vectors) [verified stores; thread inferred], so no W7 is needed; tripwire T-S7 checks it. `Q+0x48/+0x4C` stay read-only (fallback rule). The job's own `0x82EDB0` calls (`0x655AF6`) write `Q+0x48` and refcounts, as in docs/83 §4: stale-only for our reads.

### 3.4 Design S: read-only `Locomotion_ObstacleCheck`

**Detour S2** `0x85FD10`, bytes `55 8B EC 83 E4 F0` (6, no relative operand), thiscall, `ret 0x14`. RO path when all hold (as docs/83 §6): sim thread, job running, not the `+0x918` owner, not serving the job, lot index clean (`[[world+0x964]+0x1CC] == 0`), `TryAcquireSRWLockShared(QL)`. Hold QL for the whole clone (µs), release it before returning. Any fallback condition releases QL and runs the trampoline (today's behaviour, waits).

Clone steps:
1. Find the first flagged node as the original; `0x85AE60` on it (already concurrent with jobs today).
2. **RO point query** (shared with §4): lot by `World_LotLookup`; `Contains` and find without the gates (docs/83 step 3: `0xC88FD0` reject, `LotTable_Find 0x627E00`, end-bucket and key check, entry = `node+0x10`); `Q = entry+0x74[level - entry+0x40]` bounds-checked; lot coordinates with the `0x62ED40` formula; fallback if `Q+0x4C != 0 && Q+0x48 < 1`; walk `0x663E20` (`ecx = Q`; args `ctx, x, y, radius, RoVisitPt, &list`) with our `RoVisitPt`: the §3.1 visitor for this context (record = `{optionWord, 0, 0, 0}`, record `+0x28 = 0`, `ctx+0x50 = 0`), modes 0 and 1, the leaf, masked and child branches of `0x669CD0` on the docs/83 node layout, calling the original slots `+0x60`, `+0x28`, `+8` (with the record), `+0xC`, `+0x84`; raw pointers into a fixed array (cap 512), no `+0x90/+0x94`, no set, no local-list refcounts.
3. `exclude` = ids (`+0x7C`) of the result. One query stands for both original calls (identical inputs).
4. For each flagged node: the docs/83 RO `EditPath` clone (its steps 1-9 without its own detour S1 and without QL handling) with the id `exclude` list, appending to the caller's ids vector (`0x572400`).
5. Release QL. Nothing to free (the original's vector never existed).

Worker side: docs/83 W1-W6 unchanged (12 detours plus the `0x63CB90` gate stub). S2 replaces docs/83's S1 for this caller (`EditPath`'s only other caller is the plan tail `0x85FF30`, which runs on the worker) [verified callers]; S1 is not needed.

Shadow mode (`[RoSteer] Shadow=1`, sim, no job): call the trampoline, then the clone under QL with a private ids vector; compare the appended id sequences; second level: call `0x82EDB0` and compare its element ids with the RO list. Counters: `vfRoLocoTaken`, `vfRoLocoFb[reason]` (try failed, dirty index, no lot, deferred flag, invalid cache, overflow), `vfRoLocoUs`, `vfRoLocoShadowMismatch` (= 0), `vfRoLocoShadowOrder`; docs/83 T1-T4 extended to `0x667480` and `0x82EDB0` (T1); **T-S7** worker entries to `0x807110` and to the lock-key ICs during a job = 0 (`0x807110` bytes `8B 41 20 8B 54 24 04`, 7, `ret 4`, for a counting stub only).

**Gain:** up to **16.3 ms/s** (22.1%) [inferred upper bound]. **Risks:** the docs/83 risks (worker writer coverage, cache validity, id order); the lot grid read race (existing); `fp+0x20` writer thread (T-S7); answers reflect the world in the middle of the job (as docs/81: only the job's own in-flight writes differ).

**Closure:** the point part closes at **hop 2** (35 functions: walk helpers, the 9 classes' slots `+8/+0xC/+0x28/+0x60/+0x7C/+0x84`, `0x946E70/0x946E90`, `0x8294E0`, `0x81C880`, `0x81C970`, `0x81CEF0 -> 0x81CCD0 -> 0x626AA0`, `0x627E00`, `0xC88FD0`); no lock, `lock` write, absolute write, managed, remote or event call; its only non-stack writes are the walk's stack iterators and `0x627E00`'s out parameter [verified scans; folded one-instruction stubs read by hand]. The `EditPath` part closes at hop 4 (docs/83 §8). **No 6-hop pass needed.**

### 3.5 `RouteFollow_A` and `RouteFollow_B` (4.3%)

### 4.2 Is a lock-free read safe?

**`Contains` itself** [verified `0x628A90..0x628B02`, `0x627E00..0x627E68`]: rejects key 0, the all-ones key and the active lot (`0xC88FD0` returns `[[0x11ECBC4]+0xB0]`, compared at `+0x48/+0x4C`; it returns 0 when `0x11ECBC4` is 0 and `Contains` then reads `[0+0x48]`, an existing teardown crash path), runs `LotTable_Find 0x627E00` (`thiscall(P+0x48)(out, key*)`, `ret 8`: bucket `keyLo % [tbl+8]`, chain through `node+0x190`, key at `node+0`), compares with the end slot `[P+0x4C] + [P+0x50]*4` and then the 8 bytes at `node+0x10/+0x14` with the key. Writes: its stack and `Find`'s out parameter only. **No hidden write** (no cache, refcount, stamp or lazy rebuild); the `GetOrInsert` hit path that follows writes nothing either (docs/80 §2).

**What the worker writes to the table, and when** [verified single callers; timing inferred]: `LotTable_Insert 0x62E680` (only caller `GetOrInsert 0x62EB16`) and `LotTable_Rehash 0x625940` (only caller `Insert 0x62E6FE`), only on a `GetOrInsert` miss, i.e. a lot key new to the table (world load, lot placement, houseboats). Node erase `0x62DDB0` only from `LotGraph_Reset 0x62E420` (sim roots under `+0x918`: `RemoveLot 0x829D50`, `SaveLotData`, `LoadLotData`). **W5** (docs/83, exclusive QL on `0x62E680`) covers insert and rehash.

**Ordering and torn reads without a lock** [verified stores, docs/80 §2; reasoning inferred]: an insert writes the whole node, then `node+0x190` (`0x62E710`), then the bucket head (`0x62E719`): on x86 (stores in order) a reader sees the old or the new chain, never a half node. A rehash moves nodes one at a time (a reader can miss a present lot: false "no"), frees the old bucket array, then stores `[tbl+4]` and `[tbl+8]` separately: a reader can pair the freed array with a count, or read the freed array: crash. So **without QL a lock-free read is unsafe against a rehash**; under QL shared (try) it is safe, and the SRW acquire/release are full barriers, so no torn pair can be seen.

**What the families read after the hit, and who writes it** [verified stores unless marked]:
- Lot entry portal vector `entry+0x44/+0x48`: `LotRouting_AddPortal 0x6379E0`, `RemovePortals 0x6399E0` (sim ICs, after their own `Contains`, so they wait for any job today) and `ValidateLotData 0x636330` (`"Routing/ValidateLotData/activePortalSet"`, only caller `LotGraph_Build 0x63CB90` = W4).
- Front-door indices `entry+0x18/+0x1C`: `0x6318B0` (`IC_World_SetLotFrontDoorImpl 0x788380`), `0x632320` (`RebuildLotRouting`), `0x636130` (from `0x80CB40`, `0x82ABB0`, `0x82D2E0`). `0x80CB40` runs on the worker inside W6g and on the sim in F-A.
- Portal id `portal+8/+0xC`: set when the portal is made [inferred].

**Hidden writes in the families' follow-on code** (the real blockers):
1. **Portal refcount.** Portal class vtable `0xFED048`: AddRef `0x64E8E0` is a plain `add [ecx+0x70], 1`; Release `0x64E8F0` is a plain decrement that calls slot `+8` (delete) at a count <= 1 [verified]. `PortalsForObject` AddRefs every portal it copies (`0x62F7E5`, or slot 0 in the vector insert `0x8B70E0` at `0x8B7115`); `0x631800` AddRefs and Releases the door portal (`0x63187F`, `0x63189A`). The worker AddRefs the same portals during a job when it runs `0x80CB40` (W6g) or `0x636330` (W4) [verified edges; that W6g runs on the worker in jobs is docs/83's claim]. Two plain read-modify-writes on one count lose an update: a later delete of a live portal, or a leak.
2. **F-A is a writer, not a reader.** `0x80E5B0` sets the level's valid byte (`0x80E5CB`), frees the old polygons (`0x61EE20` -> `EA_Free`) and zeroes the bounds before it calls slot `+0xF8` (`0x80E5F6`) [verified]. The gate-12 wait comes later, inside `0x80CB40`, so for the whole wait (~9 ms) a job can read that footprint level as valid and empty [inferred]. This is an existing race of async mode, which the gate wait makes long; it is not something a lock-free path could fix.
3. `Q+0x48` and the flush in the query families (F-F `0x631FD0`, F-G `0x631F10`), as in §3.1 and docs/83.
4. F-D writes portal fields the job reads (`+0x2C` cost, read by `Portal_LockState 0x64F2C0` in the planner).

**Verdict:** `Contains` plus the `GetOrInsert` hit under QL shared: **safe**. Without QL: **unsafe** (rehash). By family: F-C a no-refcount clone under QL is safe; F-B and F-E are safe under QL only once the refcount question is settled (T-L3); F-A has no lock-free path (it writes); F-D are writes (defer, as design D); F-F and F-G need the §3.4 read-only query.

### 4.4 Design L

**L1, read-only front door (build first).** Detour `0x631800`, bytes `8B 44 24 08 56 8B F1` (7: `mov eax, [esp+8]`, `push esi`, `mov esi, ecx`; no relative operand) [verified], `thiscall(P)(lotLo, lotHi, type, Portal** out)`, `ret 0x10`, result `EDX:EAX`. RO path when all hold: sim thread; a job runs; this thread does not own `+0x918` and is not serving the job (`g_inInvoke`); no QL held on this thread (`t_qlDepth == 0`); `[0x11ECBC4] != 0`; `TryAcquireSRWLockShared(QL)`. Steps: the key rejects of `Contains`; our own copy of the `0x627E00` walk plus the end-slot and `node+0x10/+0x14` checks; entry = `node+0x10`; `n = ([entry+0x48] - [entry+0x44]) / 4`; index by type as the original (0: `+0x1C` if not -1 and < n, else `+0x18`; 1: `+0x1C`; 2: `+0x18`; other: return 0); index -1 or >= n: 0; portal = `[[entry+0x44] + 4*i]`, NULL: 0; `*out = portal` when `out`; return `[portal+8]`, `[portal+0xC]`; release QL. **No AddRef/Release** (the original's net change is 0; the clone does not touch the count). Any failed condition: release QL if held and run the trampoline (today's wait). Calls no game function; closure hop 0 [verified: the original's only callees are `0x628A90`, `0x62EAB0` (hit), the portal slots 0 and +4].

Why QL is enough: every worker writer of the read set holds QL exclusive: W5 (table), W4 (`0x636330`), W6g (`0x80CB40` -> `0x636130`); every other writer is on the sim thread. L1 needs QL plus **W4, W5, W6g** of docs/83 (W6g bytes `55 8B EC 83 E4 F0`, 6, `ret 8`), not the whole S2 set, so it can ship before S2.

Shadow (`[LotRo] Shadow=1`, sim, no job): call the trampoline, then the clone under QL (uncontended), compare `EAX`, `EDX` and `*out`. Counters: `vfLtRoFdTaken`, `vfLtRoFdFb[reason]` (not sim, no job, owner, invoke, nested QL, no active lot, try failed), `vfLtRoFdUs` (sum, max), **T-L4** `vfLtRoShadowMismatch` = 0. **Gain:** up to **2.0 ms/s** (14% of gate 12 in `bp-env-on`) [inferred upper bound].

**C-A, F-A correctness fix (no gain).** A sim-thread branch in docs/83's W6a detour on `0x80E5B0` (`53 8B 5C 24 08`, 5, `thiscall(fp)(level)`, `ret 4`) [verified]: sim thread, a job runs, the level is invalid (`[[fp+0x38] + level*0x24 + 0x20] == 0`, the original's own test at `0x80E5B9..0x80E5BF`), and `[fp]` is one of the vtables `0xFEB848`, `0xFEB970`, `0xFEBD10`, `0xFEBE38` (the classes whose rebuild reaches the lot table): take `+0x918` first (the `RgEnter` enforce wait, keyed `0x80E5B0`), call the original, release on return. The wait moves to before the level is emptied, so a job never sees a half-built level. Same wait time as today. Ship observe-only first: **T-L5** `vfFpRebuildSimInJob[class]` (entries that would wait) and how many were followed by a gate-12 wait with key `0x62F782`/`0x62FB74`. S2 never reaches `0x80E5B0` under QL (it falls back on an invalid cache, §3.4), so C-A never waits while this thread holds QL; count `vfFpRebuildQlHeld` = 0 to prove it.

*C-A built in 0.13.0 (`steerro.cpp` `CaEnter`, off by default):* `[FpRebuildLock] Enabled=1` (needs `[RouteGate] Enforce=1`; installs the W6a stub alone when `[SteerRO]` is off), `Mode=0` counts only, `Mode=1` takes `+0x918` (runtime `caMode` +0x1110, `--ab fprebuildlock`). Conditions as above (sim thread, job running, level invalid by the original's own test, one of the four vtables), and not when the thread already owns `+0x918`, has a gate frame open or serves a job callback (borrowed). The wait is the gate entry's (`g_rgOffSimOpen` published, `LockAcquireHook` pumping, P0 key `0x80E5B0`); the frame releases on return. Counters (v31): T-L5 `caSimInJob[4]` (per class), `caWaits`, `caWaitUs`, `caQlHeld` (= 0; with QL held it counts and does not wait). Proof offline: selftest (lock taken in the stub with the level still invalid, released at the leave; QL held -> no wait; owner, callback, valid level, other class, no job -> no wait) and steerro-test (the game's `0x80E5B0` on the sim thread during a job: the fake `Lock_Acquire` runs while the level is still invalid, the rebuild slots see the lock held and no QL) [verified]. The second F-A `Contains` inside the same rebuild then finds the lock held by this thread (no second wait) [inferred from §4.1; T-L5 against the gate-12 keys checks it].

**L2, portal readers F-B and F-E (only if P1b gives them a real share).** At gate 12 with key `0x62F782` and second frame `0x76F15D` (`0x76F0A0`) or `0x6317A3` (`0x631720`): try QL shared, swap that second frame's return slot (`slot[7]`) with a release thunk (the `RgLeaveThunk` pattern) so QL is held until the outer function returns, and let nested gate-0/12 entries in the hold pass after our own read-only find says "hit" (a miss would insert under shared QL: **T-L1** `vfLtHoldMiss` = 0, and that entry falls back to the wait). **L4, F-D writers.** `SetPortalCost` and `SetPortalAgeGenderFlags` join design D's FIFO (records: object id, value); they return 1 when deferred (the `Door` callers ignore the value [verified C#]). **Lock order and composition** (§5): QL is one lock for S2, S4, L1, L2; the sim takes it shared and try-only, never across a wait, a managed call or a `+0x918` acquire, and never twice on one thread (SRW locks are not recursive: a nested shared acquire can block behind a queued writer; nested users reuse the outer hold through `t_qlDepth`). ## 5. Shared pieces and lock order

- One QL (docs/83): worker exclusive in W1-W6 only; sim shared and try-only in S2, S4, L1 and L2 (§4.4), never across a wait, a managed call or a `+0x918` acquire, and never twice on one thread (`t_qlDepth`). D adds no QL use. Lock order unchanged: `+0x918` -> QL on the worker; the sim never blocks on QL. C-A (§4.4) takes `+0x918` on the sim only with no QL held.
- The discourage drain runs with `+0x918` held and no job, so QL is uncontended then; the S2/S4 clones never run while the sim owns `+0x918` (no job runs then).
- `[Verify]` style rule: every new detour address goes into docs/68 and `tools/hook-sites.ts --check` before a build.

1. **D** (largest share, smallest code, no QL): D1/D2, FIFO, drain points, counters; A/B `Defer` and `Gate` switches in one load (bundle rule). Repro and `repros.json` entry.
