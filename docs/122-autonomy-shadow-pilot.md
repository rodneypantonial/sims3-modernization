# 122. Autonomy meta-scoring shadow pilot: build design (`[AutShadow]`)

Written 2026-10-20. Static design only: no ts3native build, no game run. It builds on M5 (the second Mono thread, docs/120, docs/30 P1-P4) and turns the docs/121 IC closure into a concrete pilot: a worker thread scores meta autonomy in **shadow** (results compared with the sim thread's, never used). Model: the routing snapshot (docs/94: cut, records, shadow compare classes, phased gates). Mono stays parked behind routing (memory "Mono parked"); this is the ready-to-build design, not a start.

Inputs: docs/118 (plan M0-M6, gates G0-G6), docs/119 (offline host, §8-§9), docs/120 (M5 static check), docs/121 (closure incl. §8) and `docs/data/autonomy-proxy-ics.csv`, docs/59 §2.5 and §3, docs/75, docs/97, docs/30 §5, docs/76 and docs/79 (change hooks), docs/94 §4-§5. Tags: **[verified, docs/N]** = verified there, not re-read; **[inferred]** = reasoning still to confirm (ledger docs/51 §146, I-122-*); **[design]** = a choice made here. Effort in CLAUDE.md units (wall-clock for Claude with agents; game runs and clean nights listed apart).

Naming: the Mono plan already uses M0-M6 for steps, so the shadow match classes here are **A0-A5** (docs/94 calls its routing classes M0-M5). Gates are **G-A0 to G-A6**.

## Summary

- **What runs on the worker:** the meta phase only (80% of manager-task scoring, docs/75 §1), for an allow-list of 13 meta definition types and the 7 `IMetaObject` implementors (docs/121 §8.2). A ts3fixes driver `AutShadow.ScoreMeta` replays the game's B14/C1/C2 loop (docs/59 §1.2) per meta object into its own result arrays: no `BestScores`, no `InteractionCheckTable` static pools, no yield, no stopwatch.
- **Two compare modes [design]:** **Mode R** (reference): at the cut, the sim thread runs the same driver on live data, then the worker runs it on the snapshot in the quiescent window; the managed state is the same for both, so every score must be bit-equal (A0) and any difference is a snapshot or shim bug (the docs/94 option G logic: equal by construction). **Mode W** (worker only): the worker result is compared with the game's own meta search (records from a C1 hook); differences there measure staleness for a later go-live, not bugs.
- **Snapshot (per cut, sim thread):** object rows (~100-250 x 80 B), lot table (~150 lots x 24 B), per-lot (id, class, ref) lists for the scored lots with generation counters, world constants, and a learned-key memo for session-lifetime ICs. Rows are filled by calling **the game's own IC bodies** on the sim thread, so answers are bit-equal by construction. Change tracking reuses routesnap's `World_FireEvent` detour and object-event nodes (docs/76, docs/79) as one more consumer. Budget: cut p95 ≤ 0.3 ms, ≤ 2 ms/s at the sampled rate, snapshot memory ≤ 256 KB.
- **Shims:** every EA IC slot gets a guard thunk (sim thread: tail jump to the game body; worker: the shim or abort). 28 snapshot/memo shims, 6 tooltip stubs (one rooted empty string), aborts for the RNG, slot positions, `Slots_CanAttachToSlotImpl` and `Query_GetObjects` (until I-121-7), abort for every IC not on the list. Three managed worker shims in ts3fixes: `Sim.IsAllowedInRoom` (hit = read, miss = abort, never store), `Sim.NumSimsDoingGardening` (read-only), `Localization.LocalizeString` (empty string, no RNG draw).
- **Gates:** G-A0 static checks, G-A1 offline shim selftest, G-A2 offline two-thread run in `native/monohost`, G-A3 in-game count and audit (Mode 0), G-A4 Mode R bit-equal, G-A5 Mode W stability, G-A6 cost A/B and the measured break-even (§7).
- **Effort:** ~17-29 h for this pilot on top of M5 (docs/120 §6: 9-14 h), so **~26-43 h** from today, **7-10 game jobs and 2-3 clean nights** (§9). docs/121 §5 said 19-35 h; the extra is Mode R and the incremental-vs-full audit, which buy a bug-level signal before any cost run.
- **G-A0 static checks done (2026-10-20, §12):** 78 binder bodies are in the closure (no engine reads; 59 enter the interpreter through `0xD8A8E0`'s global call-record list, one writes `[0x11F2D84]`): new worker path F1 and abort F2. Three more managed W sites (online-dating records, punishment manager, reflection desire function): hooks H4-H6. 7 of the 8 extra definitions in, `VisitWithDefinition` out. No hook owner conflict; mod guard per method, not per session. +4-5 h.
- **Part 1 built offline (2026-10-20, §13), G-A1 passed:** guard thunks on every provider-table slot, a generic snapshot (answers from the game's own IC bodies, A/B versions, learned keys, audit), change tracking as one more consumer of routesnap's event layer, F2 at `0xDA9790`; selftest T1/T2/T4 pass. Part 2 (cut, worker, ts3fixes driver, compare) waits for M5 F1.
- **Part 2 built offline (2026-10-20, §14), G-A2 passed in monohost:** cut and window on `[MonoThread]`'s slot stub, sim-thread reference with the RNG restored, worker dispatch through `MtSubmit`, `AutShadowNative` ICs, rooted answer column and array allocator (part 1's MonoArray length offset was wrong: fixed), `simstale`; ts3fixes driver, H4-H6, worker hooks, per-method mod guard, Mode R/W compare. Host: 200 requests x 50 objects, 8,400 of 8,400 A0 with the main thread interpreting, allocating and collecting. Next: Mode 0 and Mode R in game (`autshadow-first.json`).
- **Sim-thread ICs answered (2026-10-20, docs/125):** RNG by per-unit MT streams (driver `RngUnit` marks, contract Version 3), slot positions and `Query_GetObjects` as learned keys re-asked at every cut; monohost G-A2 now A0 10,000 of 10,000 with 0 `rng` aborts. Only `Slots_CanAttachToSlotImpl` still aborts by design.
- **Biggest risks:** EA native method bodies (the binder's 1,085, docs/119 §9.4) inside the closure bypass IC shims; hidden managed writes from the driver's closure into shared objects; the quiescent-window premise; the cost of guarding every IC and of the M5 lock (§10).

## 2. Snapshot

### 2.1 Cut point and versions

- **Cut:** one per pending request, at the return of `0xD81840` [design]. Between this point and the next `Simulate` entry the sim thread runs native animation, locomotion, publish and frame waits (docs/59 §3.5 [inferred, to measure]); the native state keeps moving there (docs/121 §6 item 2), which is why object answers are copies.
- **Versions:** two snapshot buffers (A/B), the worker reads the one published at its cut; the next cut writes the other. A buffer is reused only after the worker released it (worker sets `done` with `Interlocked`). Native memory (`VirtualAlloc`, 2 x 128 KB reserve); the managed-reference column lives in a `GC_malloc_uncollectable` block (root by kind, docs/120 §1.2), never in `malloc` memory.
- **Epoch:** routesnap's world epoch (docs/76 §2: world events 2, 3, 5, 7, 9, 0x0A, lot events 0x0D-0x10, build/buy boundary slot swaps of `World_LotClusterTreesImpl` slot `0x11623B0` and `RouteManager_OnExitBuildBuy` slot `0x1160DA8`) forces a full rebuild and drops any in-flight run (A5).

### 2.3 Size and cost budget [inferred]

| Part | Size | Cut cost |
|---|---|---|
| Rows: 100-250 x 80 B | 8-20 KB | Sims always dirty: ~50-150 Sims x ~8 IC bodies x ~0.2-0.4 µs = **~80-480 µs** on a full Sim refresh; non-Sim rows only when dirty |
| Per-lot lists: ~30 scored lots x 50-300 objects x 12 B | 18-108 KB | dirty lots only: typically 0-3 lots x ~20-60 µs |
| Lot table, doors, constants, memo | < 10 KB | < 20 µs |
| **Total** | **~30-140 KB per version, 2 versions ≤ 256 KB** | **target p95 ≤ 0.3 ms per cut** |

The Sim refresh dominates. Pilot rule [design]: refresh only the Sims the request can reach (actor, Sims on the scored lots via the per-lot lists, Sims within the `BakeSaleTable` radius) and mark the rest stale-with-abort (a worker read of a stale Sim row aborts with reason `simstale` and adds it to the learned set). At `Sample` = 4 and ~10-30 meta searches/s [inferred; the rate is a G-A3 output], 2.5-7.5 cuts/s x ≤ 0.3 ms = **≤ ~2 ms/s**. docs/94's routing cut has the same 2 ms/s cap (G3).

### 2.4 Invariant and audit (docs/94 §4.2 pattern)

- **Invariant S-A:** at every cut, the incremental snapshot equals a full rebuild from live data (rows, lists, lot table, constants).
- **Audit** (`Audit=N`, default 50): every Nth cut also builds a full snapshot into a scratch buffer and compares field by field; a mismatch logs the part, id, field, and the last 32 change events for that id. Classes as docs/94: S1 missed event (coverage gap), S2 lazy state, S3 off-sim writer, S4 epoch race.

## 3. Shim layer (ts3native `autshadow.cpp`)

### 3.1 Guard thunks at the binding table

- EA ICs are P/Invokes resolved lazily by name through Mono's `icall_hash` `[0x11F436C]`, filled once in `MonoScriptHost_Init` from each provider's `{function, name}` table; native method bodies bound by `0xE3E570` read IC pointers at bind time (docs/119 §9.1, §9.4 [verified there]). So the swap must happen in the provider tables **before** `MonoScriptHost_Init`, as routesnap's 39 slot swaps already do (docs/94 §10) [design: same mechanism, same install point].
- `Guard=all` (pilot default): one 10-byte thunk per exe IC name (`push index; jmp guard`, the docs/119 §9.1 P3 layout, 1,775 names). `guard` compares `fs:[0x24]` (thread id) with the worker id: sim thread -> `jmp original[index]`; worker -> `shim[index]` if set, else **abort** with reason `ic:<index>` and the neutral value for the IC's return type (from `methods.csv` signatures: `float`/`double` via `fldz`, the docs/119 risk 2). Sim-thread cost ~2-3 ns per IC call [inferred; G-A3 measures it]. Fallback `Guard=closure` (only the 129 ICs of `tools/mono-host-ics.ts`, docs/121 §8.5) if the Mode 0 A/B shows > 1 ms/s.
- **One owner per slot** (docs/68 rule 3): slots routesnap already swaps (portal, lock-key, route ICs) are guarded from inside routesnap's stub, not swapped twice. `tools/hook-sites.ts --check` gets the new rows.
- Mono runtime (corlib) ICs are not EA provider entries and stay unguarded; they are covered by the M5 rules (allocation under the P3 lock; no `GCHandle`, weak reference, reflection, `Monitor` reliance; docs/120 §3.3) and by static step S1 (§8).

### 3.3 Abort semantics

The guard sets `abortReason` (first one wins) and returns the neutral value; the managed code keeps going and may throw (null result). The driver's per-object `try/catch` and its check of `AutShadowNative.Aborted()` after each meta object mark that object A4 with the first reason and reset the flag. A stop flag from the sim (window closed) makes the next guard call and the next object boundary abandon the whole run (A5). No wait, no exception thrown from native code [design: avoids `mono_raise_exception` from the worker and game `catch` blocks that would swallow it, docs/119 risk 1].

### 3.4 RNG

The worker never draws: `Random_NextDoubleImpl` aborts (docs/121 §4.1 option a). Mode R's sim-thread reference run copies the Mersenne Twister state at MonoScriptHost `+0xC30` (624 words + index, docs/27 §1.1 [verified there]) before the run and restores it after, so the reference leaves the sim's RNG stream unchanged [design]. Draws inside the reference run are still counted, and the matching worker objects are A4 `rng`.
**Superseded 2026-10-20 (docs/125 §2):** the worker draws from per-unit Mersenne Twister streams seeded from (cut seed, unit) with the game's own `0x4FA990`/`0x4FAA70`; the reference re-seeds the host MT per unit inside the same save and restore, so both sides draw the same values per unit and Mode R stays bit-equal (monohost: A0 10,000 of 10,000, 0 `rng` aborts).

### 3.6 What the driver must not do (static step S1 checks it)

`AutShadow.ScoreMeta` replaces B14/C1: it walks `MetaAds`, applies the commodity filter, and calls C2 (`InteractionObjectPair.TestAndCalculateScore`) on a **pair object it allocates itself** unless S1 shows C2 writes nothing into the pair [design; I-122-2]. It never touches `InteractionCheckTable` (static pools, C1a), `BestScores`, `CacheValuesToOptimizeTestFunctions` (C0 writes the actor), `YieldIfPossible`, `StopWatch`, events or delegates other than the allow-listed `Predicate` lambdas and scoring functions.

## 4. Dispatch

### 4.1 Allow-list check (per meta object and ad)

1. Implementor: exact runtime type in the 7 (`Lot`, `RabbitHole`, `HomeMetaObject`, `WorkMetaObject`, `GardeningMetaObject`, `WorldPondHelper`, `BakeSaleTable`) and its assembly MVID equal to the allow-list file; else the object is `skip` (not compared).
2. Definition of each meta ad: exact runtime type and MVID in `autonomy-allow.csv`; else `skip` for that ad.
3. Scoring function (if tuning names one): method + MVID in the allow-list; else abort `sf`.
4. Session guard (docs/104 mod guard, docs/59 §3.6): game assembly MVIDs differ from the file -> `[AutShadow]` off for the session, reason logged. A loaded run-time patcher (`MonoPatcher.asi` is on the reference install) does **not** switch it off: per-method docs/104 checks over the closure mark the affected definitions `skip` (G-A0 §12.4).

### 4.2 Hand-over

Request and results are managed arrays rooted in ts3fixes statics (`sReq`, `sRef`, `sWork`, `sGame`), allocated on the sim thread at warm-up and reused; the native side only sees the request id and the window/stop/done/abort words (native globals with `Interlocked`, since managed `lock` is a no-op in this build, docs/120 §3.3). Result layout per (meta object, ad): `float score`, `int code` (0 pass, 1 Test failed, 2 skip, 3 abort + reason index), plus per object `float metaScore` (`HowMuchItWantsSimToCome`). One worker, one request in flight; a new request while busy is dropped (`asBusy`).

|---|---|---|---|

## 5. Compare

### 5.1 Mode R classes (bit-level, per (meta object, ad))

| Class | Meaning | Rule |
|---|---|---|
| A0 | same code, scores bit-equal, meta score bit-equal | pass |
| A1 | same code, score differs by ≤ 1 ULP | must be 0; each case explained (same interpreter, same data: it should not happen) |
| A2 | same code (pass), score differs beyond 1 ULP | **0** |
| A3 | code differs (pass vs fail) | **0** |
| A4 | worker aborted (reason) or skipped | counted by reason; target < 20% of allow-listed pairs in the pilot |
| A5 | overrun, epoch bump or guard trip (sim entered managed code in the window) | not a mismatch; counted to size the window |

A record per A1-A3 (JSONL): request (actor id, meta object id, definition type, target), both scores and codes, snapshot version, change events since the cut, and with `DumpOnMismatch=1` (cap 20 per run) the snapshot buffer, so the IC answers can be checked offline against the row builder (§6 T2).

### 5.2 Mode W report (L, informational)

Per sampled search: pairs both scored, equal-score share, Test agreement, and **top-1 agreement** (the worker's best allow-listed pair vs the game's best among the same pairs). The game scores some objects before the cut and some in later ticks (B13 yields every 5 objects and 1 ms, docs/59 §1.3 Y2), so differences mix staleness and bugs; Mode R has already separated out the bugs. L feeds the go-live decision (docs/118: separate, after G6), not a gate.

The memo ICs (`AO_MEMO`: `DeviceConfig_GetOption`, `UserToolUtils_*`, `World_GetLotName*`) record one row per distinct key on every sim-thread call and were never dropped (only the lot-name rows on an epoch). They filled all 1,024 rows during the load, before the first cut: the `/native` dump taken before play already shows `memoRecords` 1,024 and `full` 4,486 (BP; IP 1,024 and 4,290). After that every insert was refused (`full` +1,286,936 BP, +990,722 IP), so:
- no worker miss was ever learned (`learned` 0 on both worlds), and the learn ring (64 records) overflowed on every run (~944 misses per run BP, ~1,483 IP): `learnDropped` 672,605 BP, 871,285 IP;
- the request's own rows (`AsAddRowKind`) and the world constants (zero-argument `AO_CUT`/`AO_WORLD` rows) could not be inserted either, so `refreshed` stayed at 2,296 BP and 1 IP.

Worker aborts by reason (`abort[]` deltas, `mono-cost-report.ts` now prints them): BP `row` 715,520 (98.8%), `pos` 4,382, `desirefn` 2,410, `list` 1,599, `stop` 166; IP `row` 728,330 (79.5%), `other` 180,273 (19.7%: `GameUtils_GetWorldType`/`GetWorldName`, `World_GetMoonPhaseImpl`, world constants that were never listed), `stop` 3,360, `desirefn` 1,810, `pos` 1,595. The first 64 abort log lines name `Slots_GetParentIdImpl` (`row`) on both worlds.

**Fix (0.36.110, `autshadow.cpp`):**
- Sizes: `AS_CAP` 8,192 rows (index 16,384, array pool 32,768 dwords). `AsMem` (master + two published versions + temp pool + sets) is 3,858,512 bytes (~3.7 MB) [measured: selftest `sizeof`], one `VirtualAlloc` at DllMain only with `[AutShadow] Enabled=1`: address space, not just RAM, but allocated early while large blocks are free; nothing changes with the switch off.
- Memo quota: memo rows never take more than `AS_MEMO` = 2,048 rows (a quarter); at the quota the oldest eighth of the memo rows is evicted. A sim-thread memo call that finds its row marks it used.
- LRU eviction (`AsEvict`): when the table is full, the eighth of the rows least recently used by the sim or the worker is dropped (age histogram, one O(n) pass plus a reindex per eighth of the table); zero-argument rows stay. "Used" = a worker hit (folded at the cut), a sim memo hit, or the request re-adding its row; an object row in use also touches its parent row (re-added if it was evicted), so the dirty propagation (docs/79) never loses a parent. Counted in v7 `evicted` / `evictedMemo`.
- Aging: learned rows (as before) and now memo rows unused for 100 cuts are dropped (`memoAged`), so the table holds what the last ~100 cuts (~75 s at 1.3 cuts/s) used, not the whole session.
- Learn ring 1,024 records (was 64); the cut takes at most 256 new keys (each is one body call at that cut), the rest wait for the next cut (`learnBacklog`); ring overflow is counted apart (`ringDropped`, still in `learnDropped`).
- Audit (`Audit=50`) checks a rotating slice of at most 1,024 rows per audit cut instead of every row.

**Cut cost.** Body calls per cut stay bounded by what changed (dirty objects, list generation, the per-cut rows, at most 256 new keys), not by the table size: an idle cut at a full 8,131-row table made 1 body call [measured, selftest]. The linear part is the table passes and the publish copy (~120 bytes per row): 262-311 us per cut at a full table vs ~58 us at 1,024 rows in mono-cost5 [measured: selftest vs game, so ~35 us per 1,000 rows, inferred]; at 1.3 cuts/s a full table costs ~0.4 ms/s of sim time [inferred]. An epoch cut (world/lot events, ~1 per run) still refreshes every non-memo row once.

**Sizing data (v7, read by agent.js into `/native`):** `entriesMax` (high-water of rows), `learnWantMax` (most new keys asked at one cut), `memoRows`, `refreshMax` (most body calls at one cut), `learnBacklog`, `evicted`. mono-cost5 cannot give distinct-key demand (aborts cut every run short, ~1,230 BP / ~1,540 IP guard calls per run); mono-cost6 measures it. If `entriesMax` stays well under 8,192 with `evicted` 0, the table can shrink; if `evicted` is high and `learnWantMax` sits at 256, look at the per-cut cap.

**Selftest T6 (`TestAutShadowFull`):** 4,096 distinct memo keys (twice the quota) keep `g_asMemoN` <= 2,048 with no refused insert; 12 floods of 1,024 junk keys fill and evict the table (`entriesMax` 8,192, `full` unchanged, `learnWantMax` 256); a 900-key working set is learned within a few cuts and then answered 900 of 900 despite the full table, and still 900 of 900 after the next 1,024-key flood.

### 14.16 Cut cost: change-only lists and Sim tiers (ts3native 0.36.114, not run)

**Where mono-cost7 put the time** [measured, v8 counters, `node tools/harness/mono-cost-report.ts --tag mono-cost7`]: BP 2.58 ms per cut = list rows 1.98 ms (49 `Query_GetObjectsOnLot` / `CountObjectsOnLot` body calls per cut at ~40 us each) + object rows 0.14 ms (404 calls, ~0.34 us each) + ~0.46 ms of table passes (learn 26, prep 83, refresh loop ~190, age 112, audit 10, publish 28 us); IP 1.47 ms = lists 1.11 + objects 0.01 + ~0.35 passes. `ColdIc=1` already cut the object rows; the lists are refreshed at every cut because the global list generation moves ~1,100 times a second (world event `0x11` 537k of 599k bumps on BP: object lot/room updates `0xC8A290` [verified: `snWev_17`], events 4/6 the rest).

**Design picked: change-only lists by input print (`[AutShadow] CutLean=1`).** The two list ICs are a walker `0x7499B0` (ids) plus one host call (+0xC0 array / +0xC4 count of the ids' managed objects of `type`) [verified disassembly `0x749D30`, `0x749BC0`, `0x7499B0`]. The walker reads only: the lot by id (`0xC62D40`, `ret 0xC`), the lot's object vector (`lot+0x14`, ids at object `+8`), with a room argument the world component's room (`0x935770` bit `[0x11ECF08]`, `+0x20`), then the world lot's vector (`[0x11ECBC4]+0xB0`, `+0x14`) filtered by the component's lot (`+8`). At the cut, a list row whose generation moved is refreshed only when a 64-bit FNV print of exactly those reads, in walk order, differs from the print stored at its last refresh (one print per lot and cut, two variants: room -1 calls hash ids only, room calls ids + rooms). So a walking Sim's room change (most `0x11` events) leaves every room -1 list alone, and an object added, removed or reordered on the lot, or a Sim entering or leaving it, refreshes it. Why this one: it is exact for everything the walker reads (no event semantics inferred: the event only says "look", the print says "changed"), needs no new hook (calls only, sim thread, at the cut where the bodies run anyway), and the per-row cost drops from a 40 us body call to a share of one walk per lot. Rejected: per-lot generations from events (`0x11` carries only the new lot `comp+8` after the store [verified `0xC8AC70`/`0xC8A290`], the old lot is gone, and events 4/6 at ~100/s would still bump globally); refresh caps with a staleness bound (more `list` aborts, A4 is already ~20%); per-row cold lists (the same abort cost). Residual gap [inferred]: an id that keeps its place but gets another managed object or class (host +0xC0's id -> object map); none known, and the audit (Audit=N) plus Mode R A1-A3 catch one.

**Pass trims (`CutLean=1`, and two refactors always on):** parent rows are copied once per cut into a compact array (the child propagation passes and the Sim-parent scan run on it instead of rescanning the table); the stale marks and the rooted column are set in the refresh loop (one table pass fewer); with `CutLean=1` aging (and its reindex) runs every 8th cut (`ageRuns`), so learned rows live up to 7 cuts longer. The audit now skips stale rows as it skipped cold ones (never answered; tier-2 waits made it count them).

**Sim tiers (`[AutShadow] TierMs=N`, maintainer's design input 2026-10-29).** Tier 2 = a far unseen Sim by the existing native unseen rule (`unseen.cpp` `AsTierOf`: off screen by the game's frustum, beyond the camera reach max(80 m, 2 x camera height), no active-household Sim within 80 m in ts3fixes' viewer table (`UnseenViewers.cs`, GetOption2 `0x82`; the table now also feeds `TierMs` with `[UnseenThrottle]` off; no fresh table = tier 1)); everything else, and always the request's actor, is tier 1. A tier-2 Sim's rows (reachable, promoted or other Sims) are refreshed at most every N ms; at the cuts in between they are published stale, so a worker read aborts `simstale` and the game scores that pair itself: never an old answer. Lots and objects are not tiered (rows shared by both tiers stay tier 1). Tier classification is cached 500 ms per Sim. shortcut: the native rule has no household, seen-lot, social-target or "near a visible Sim" test of ts3fixes `UfWhy`; serving tier-2 actors' requests only every 1-2 s needs a ts3fixes change (the request is posted there), next build.

**1. Drop only the removed object's rows? Not exact as stated.** A list answer is the managed objects of the row's type for the walker's ids in walk order (§14.16). Dropping the destroyed object's element from the stored answer needs two things native code does not have: the destroyed object's script object (the answer holds managed objects, the event gives the native one; no native map between them is known), and the order rule of the lot vectors' erase (an erase that swaps the last element in would reorder the others). The second is the same inference the Sim-free list kinds already rest on (§14.18, I-391-1: a Sim leaving a lot does not change a Sim-free row), and two exact Mode R runs with `ListAudit=1` and ~2 Sim-free rows kept a cut did not refute it. Reading the erase in the disassembly needed a Ghidra session during a timing A/B, so it stays an inference [inferred, I-396-1].

**Design picked: typed marks.** The rule that is exact under I-391-1 / I-396-1 is the one by type: an object that is none of a row's type can neither enter nor leave that row's answer, and its add or removal leaves the others in order. So a mark carries the list types its object can be, and a list row is dirty only when its type is among them.
- Classes: each object-lot map row keeps a 32-bit class (bit i = the object is of list type i, in the order ts3native first saw the types) and the number of types it was tested against. An object is queued for classification at its add event (event 4: it is classified at the next request, before the cut that would mark it `new`) and whenever a mark finds it unclassified (that mark stays untyped; its later `gone`, `lot`, `room` and `lost` marks are typed). ts3fixes takes one batch of 32 ids per request, newest first (`ObjClassTake`), gets each script object (`Simulator.GetProxy(id).Target`) and tests it against each list type with `Type.IsInstanceOfType`, the test the list ICs apply [inferred, I-391-1]; no script object yet = unknown, queued again at its next mark. Types past the 32nd are never classified and count as possible.
- Marks: a classified object's mark goes into a per-cut lot table (types for membership, types for room rows) instead of the plain lot sets; a row of that lot is dirty only when its type bit is set (room rows also read the room bits). Unknown objects, Sims and a Sim's child keep the plain marks (§14.17-14.18 rules unchanged).
- Lot-vector prints: a print change (or a lot with no baseline) is marked with the classes of the cut's unplaceable objects (no component, placed again after none, destroyed before any cut placed them). Every other lot-vector change came with an event and was marked, typed, at its own cut, and every earlier unplaceable change ran the prints at its own cut, so only this cut's unplaceable objects can be behind it [inferred: the I-391-2 event coverage]. If none of them is of a list type there is no mark (`liteTypedNone`); an unknown one makes it the plain mark.
- Audit: every other cut that kept a row by type, one of the `ListAudit` rows is such a row instead of the next rotating one (same cost). A difference counts `typedAuditMis` and `listMissed` and trips the session to prints like any miss (§14.17). Mode R A1-A3 stay the end check.

**What this means for go-live (new, important).** The worker runs only in the quiescent window, from the cut's end to the next Simulate entry, and that window is ~9-10 us on every run (`windowUs` / runs: BP 8.4 / 9.5, IP 8.9 / 10.2) [measured]. Mode R reaches a result only because the sim waits up to `WindowWaitUs` at the next Simulate entry (`windowWaitUs` ≈ `workUs` on every run). docs/124 §2 assumes the worker scores during "the native tail of t"; at cut site 2 that tail is ~10 us, so go-live in the same window has two outcomes: no wait = nearly every job falls back to the game's B13 (no gain, plus the cut), or the sim waits for the worker as Mode R does, which costs about what the worker saves (worker 4.4 ms vs reference 5.2 ms per request on IP). `mono-cost-report.ts` now prints that case as the "worker window" line [inferred]: net with the wait BP -10.2 / -10.9 ms/s, IP -6.6 / -5.1 ms/s on the four mono-cost11 runs, against +14 / +31 ms/s without it. So the fallback rate (or the wait) eats the whole gain until the worker can run while the sim runs the next tick's script work, i.e. until the window premise of docs/124 §3.4 (G-A5) holds for a window that is actually long: a cut site with a long native tail after it, or a worker that reads a copy instead of managed state in place. This is a go-live design question for docs/124, not a cut-cost one; the cut work in this section stays worth doing (the cut is paid either way). **Which window, checked again (2026-10-30).** Two different spans are called "window" in docs/124. (a) Post to resume (docs/124 §5.2, line "Window = from the B13 post in tick t to the resume in t+1"): the requesting task yields at the post and resumes in its next slot, about one Simulate tick later. From the mono-cost11 counters (`simTicks` over the report's 10-minute window) a tick is BP 28.9 / 31.9 ms and IP 26.5 / 29.1 ms (run / rerun), almost all of it inside Simulate (the gap is ~10 us), so the post-to-resume span is ~26-32 ms [inferred: the task order inside a tick is not recorded; the span is the rest of tick t after B13 plus the start of t+1 up to the task's slot, ~one tick]. A 3.3-4.6 ms job (max ~5-9 ms) fits that span about 5 times over. (b) The worker window (docs/124 §2 table, row "t+1 top of Simulate: window close: worker done = result ready; still inside = stop, overrun"; §3.4 "The worker reads managed state in place in the quiescent window"): the worker may run only while the sim runs no script, i.e. from the cut at the Simulate return to the next Simulate entry. The "worker window" line measures (b), the gap between Simulate calls: 8.4-10.2 us mean, max 45-56 us. That is the window the design as written uses: the consume does wait for the task's resume, but the worker must already be done and stopped at the top of t+1, because from there the sim's script (all the other tasks first) writes the managed objects the worker reads in place. docs/124 §2's "native tail of t" (animation, locomotion, publish) does not run between Simulate calls on this build [measured: ~10 us]. To give the worker the full span (a), its reads must stop depending on the sim being quiescent during t+1's script: (1) the worker reads only cut-time state, i.e. every managed field its closure reads is snapshotted at the cut like the IC answers, or proven unwritten before the task's resume (a docs/124 §5.2-style write-set closure over every task that runs in t+1, not only actor fields); (2) a copied heap / world image (docs/123); or (3) keep in-place reads and let the sim run t+1 while the worker reads, with Mode R measuring the races (not exact by construction). With (1) or (2), the window becomes ~26-32 ms and overruns ~0 at today's job times; the remaining go-live costs are the cut, the guard thunks, the lazy GC lock and the consume (docs/124 §15).

### 14.21 Cut round 3: where the cut runs, run skip, delta publish (ts3native 0.36.123, not run)

**Where the cut time runs** [verified by reading the code]: the whole cut is native C++ on the sim thread (`AsCut`); no part of it runs in the mint interpreter. The managed side of a request (ts3fixes' B13 prefix: `AddRow` loops over the actor, the meta objects and `LotManager.Actors`, `PreWarm`, list type and object classification, `Post`) runs before the cut and is not in the cut timers; only the object classification is timed (`clsUs`, §14.20). Inside the cut, the IC bodies are the game's native code: object rows call native ICs (0.13 ms BP), and a list row calls the native walker `0x7499B0` plus the host call `+0xC0`/`+0xC4`, which is Mono runtime C (type test, a new managed array, GC allocator entries under `[MonoThread]`'s lock), not interpreted script [inferred from docs/122 §14.16 and docs/130's runtime map; the split between walker and host call per body is not measured]. So "move managed field reads to native" has no target in the cut; its target is the request prefix, which is cheap per request next to the scoring and is the worker's own input. After §14.20 the list bodies should be ~1-1.5 a cut; replacing the host call with native code (EA's id-to-script-object map, `mono_object_isinst`, `mono_array_new`) is the next step only if they stay high.

**What is left after typed marks** (mono-cost11 BP phases minus §14.20's expected list-body cut, per cut): row loop ~0.24 ms, prep ~0.19 (tier classification 0.067, placing 0.045, lot-vector prints 0.027), object bodies 0.13, ListAudit 0.07, publish 0.055, learn 0.03, list bodies ~0.07-0.1. The row loop and the publish copy are the native hot loops; both scale with the table (~5,000 rows of 128 bytes), not with what changed.

**1. Run skip (`[AutShadow] RunSkip=1`, default 0).** An object's rows sit together in the table (`AsAddRowKind`, `AsLearnObject` insert them in a row), so the loop now walks runs: one object's consecutive rows, or consecutive rows of other kinds. A walked run keeps a summary: plain (object rows only, no payload, none fresh), any row stale, its cold-row counts, the IC hot-state stamp it was walked under, its parent row. At a later cut a plain, non-stale run is skipped whole when its object is in none of the sets the loop reads (`work`, `t2skip`, `sims`), the cut is not full, and, if it has cold rows, the IC hot states with ColdIc and RowHot are unchanged (a 64-bit print of the hot bits, `icStampMoves`), no worker read of one of its cold rows came in (`readCold`, filled at the fold) and the object is not an actor. Then every row would take the path it took when the run was last walked and write nothing new: a hot row has `why` -1 and keeps its flags, a cold row is cold again, and its cold counters are added again; the parent row is still copied into the parent array. Rows moving (eviction, epoch filter, aging) bump a generation that rebuilds the runs; appended rows get new runs. A prefetch of the next run's first row hides part of the walk's memory latency. [verified by reading the loop; selftest below]

**2. Delta publish (with RunSkip).** Each published version remembers the cut, the row generation and the row count of its last publish. If no row moved since, the publish copies only the runs walked after that cut and the rows appended since (rows and rooted column); a skipped run's rows are bitwise what the version already holds. The index, pool and used flags are copied as before. Fields only the sim thread reads (`lastUsed`, `lastRead`) may lag in the version.

**3. Not done, and why.** Hand-written x86: the loop's cost is memory and branches per row, which the skip removes for most rows; the MSVC `/O2` output of the loop was not inspected before the build gate (no compiler while the timing A/B ran), so no asm was written; read `dumpbin /disasm` of the run loop only if `rowSkips` is high and the refresh phase is not down. SSE2: the row data is not wide (one 128-byte struct per row, mixed fields); the publish copy is `memcpy` (already vectorised by the CRT). Per-object version stamps (item 3 of the request): the run summary plus the per-cut sets are that stamp; a separate stamp per object would need every writer of the sets to bump it. Overrun fix (item 4): none in the cut. The overruns come from the window (§14.20 point 3): the worker only has the sim's ~10 us between Simulate calls, so a deadline or an earlier start inside the cut cannot help; go-live needs the docs/124 design change.

**4. Consume-side counters for docs/124 §15 (contract Version 8).** (a) Pass share: in the Mode R compare, every classified allow-listed pair counts in `classPairs` and, when the worker scored it as passing `Test`, in `passPairs` (ts3fixes adds them through the new `Stat` IC, so no ts3agent change is needed). p = passPairs / classPairs per world replaces the p = 0.25-1 range of docs/124 §15.3. (b) Stale-score check (`[AutShadow] FreshEvery=N`, default 0, queue 8): 1 in N Mode R finishes scores the same request again on the sim thread with the same driver, bracketed like the reference (`Fresh(1/0)`: script RNG saved and put back, per-unit streams with the cut's seed, the gardening count read again), and compares with the worker's cut-time result: pairs both answered (`freshPairs`), pairs whose code or score bits differ (`freshDiff`), searches whose top passing pair or top-10 passing pairs (identity and order, by pair score) differ (`freshTop1`, `freshTop10`), time `freshUs`. Limit: the finish runs at a Simulate return >= 1 tick after the cut, not at the B14 call inside the next tick where go-live consumes, and pairs are ranked by their own score without `BestScores`' rules; so it measures how much the world moves in about a tick, an upper-side proxy for go-live's staleness [inferred]. The bit-exact A0-A3 compare is unchanged (a separate result array). Cost: about one reference run per N finishes on the sim (BP ~4.2, IP ~5.2 ms), a test cost like `refUs`.

**5. IP overruns: keep the finished objects (`[AutShadow] KeepPartial=1`, default 0, queue 1).** Cause (§14.20 point 3, both IP runs): the worker's job (4.4-4.6 ms average, reference 5.2-5.6 ms) runs past the 5 ms the sim waits at the next Simulate entry on 17-44% of IP searches; the share swings with how heavy the requests are, not with machine load; no single definition can be named from the data (no per-job times). Until now an overrun dropped the whole search (A5), although the meta objects scored before the stop are complete. Fix: ts3fixes checks the stop flag after each meta object; an object counts only if the flag was still clear after its last read (x86 keeps loads in order and the sim sets the flag before it writes anything, so every read of that object came before the sim resumed) [inferred from the memory model, I-397-3]; the object it was inside of and the rest abort with reason `stop` (A4), and the finished objects are compared in Mode R (`partialKept` counts such searches; an epoch drop stays dropped). In go-live terms (docs/124 §15) an overrun search then moves the objects finished in time instead of nothing: on IP, with jobs averaging ~4.5 ms against the 5 ms cap, most of an overrun search's pairs [inferred, I-397-4]. It does not change the window finding of §14.20: with no wait at all go-live still gets ~10 us. Rejected: an earlier start (the worker needs the cut, and the cut is at the Simulate return), a later stop (raises the sim wait one-for-one), skipping slow definitions (no per-definition times yet).

**Counters (autshadow v14, +0x970):** `runSkip`, `runN`, `runSkips`, `rowSkips`, `runBuilds`, `icStampMoves`, `pubDelta`, `pubRows`, `runCheckMis`, `passPairs`, `classPairs`, `freshReqs`, `freshPairs`, `freshDiff`, `freshTop1`, `freshTop10`, `freshUs`, `freshEvery`, `partialKept`, `keepPartial` (docs/registry.md); `mono-cost-report.ts` prints a "run skip" and a "consume side" line.

**Expected** [inferred, I-397-1]: on BP ~3,000-3,500 of ~5,000 walked rows a cut are in skippable runs (clean object rows; Sim rows, dirty objects, lists, memo and new rows are walked), loop 0.24 -> ~0.09-0.13 ms (walked rows plus ~3 set lookups per skipped run); publish 0.055 -> ~0.03 ms. BP cut ~0.12-0.18 ms below mono-cost12's, i.e. ~0.68-0.78 ms with §14.20's expectation; IP ~-0.06..-0.1 ms (smaller table). Mode R answers unchanged by construction; in game, `auditMis` (Audit=50 compares master rows with fresh bodies) checks the skip and Mode R A1-A3 the delta publish.

**Selftest:** every autshadow test (T1-T12) now runs with RunSkip on in check mode: a run judged skippable is walked anyway and must come out bitwise unchanged with the same cold counts (`runCheckMis` must stay 0), and the delta publish treats those runs as skipped. T13 `TestAutShadowRunSkip`: the real skip (no check walk) with ColdIc, RowHot=16, Sim rows and actors: a clean cut skips runs and publishes deltas, a changed object is published in both versions in turn, then 3 x 2,000 random steps (moves, rooms, learned keys, worker reads of hot and cold rows, Sim rows, list rows, epochs): published rows equal fresh bodies (`AfCheckPublished`), answerable rows too, audits 0. T5 checks the ini default (off).

### 14.22 Satb: the worker reads the cut while the sim runs on (ts3native 0.36.125, not run)
