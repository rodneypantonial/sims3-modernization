## 2. Overlap

### 2.1 Code sites [verified]

34 TS3W addresses are named by both Apex 3.0.0 and ts3native rc1111 (`node tools/hook-sites.ts` at 5c33abfe, native/ is
unchanged since). **None is new since 2.17.1**; 32 have a class in `docs/data/apex-sites.csv` (2.15.3 map, still right
because the feature code at those sites did not change). Two have no class yet:

| Address | Apex 3.0.0 | ours (rc1111 state) | Who installs first | Class |
|---|---|---|---|---|
| `0x78AE40` World_BuildRoutingDataImpl | `TransitionCalls` observer (framework/transition_calls.cpp, added after 2.15.3, starts on every Steam run): Detours entry hook after a 37-byte whole-function signature check | `[RouteGate] Sites=1` prologue-checked entry detour (`rtsites.cpp`, 7 bytes) and `[RouteSnap]` E19 IC slot 0x01162C28 (`routesnap.cpp`): **both off in rc1111** | ours (DllMain) before Apex (features start) | C1: each side checks bytes; the second one skips with a log line (Apex: "unavailable or already changed"; ours: "differing prologue"), only Apex's transition timing is lost |
| `0x4EC0A0` RefPack helper | named only in Apex `tools/refpack_test` (not in the shipped asi) | `[SaveCompress]` hash (off) | - | C0 |

`0xAAC110` (save write entry): Apex MemoryGuard (Room to Save, default on) now accepts a `jmp` from that entry into
ts3native.asi (`memory_guard.cpp` ~line 431) and puts its early save preparation in front of it. Only `[RouteGate]
Sites=1` (test only, off in rc1111) puts that jmp there. Our `[SaveWrite]` still yields the call `0xAB12AF` to MemoryGuard
when that switch is on (`apex.cpp` / `savewrite.cpp:544`, unchanged rule).

**Load order** [verified, docs/148 §2 + apex.cpp]: the ASI loader loads in file-name order, so `ApexRadiance.asi` (then
MonoPatcher, Sims3Performance, Sims3SettingsSetter) is in before `ts3native.asi`. Apex's DllMain only takes its mutex; it
writes game code after `GameAddr::Resolve()` in its feature start (apex_main.cpp ~line 203), long after our DllMain
installs. So at a shared entry we are in first and Apex's byte checks would refuse: that is why `ApexStandDown` keeps our
module off the sites Apex owns (§2.2).

**ScriptMath vs `[MonoThread]`** (rc1111 is the first release ini with `[MonoThread] Enabled=1 Mode=1`; rel0210 and the
user's 0.36.168e had it off): ScriptMath (on, unchanged since 2.17.1) rewrites the interpreter's `_isnan` compare blocks
(its signature A/B) plus the entries `mono_type_get_object 0xEA8A00` and `mono_domain_free`. A scan of our TS3W.exe copy
finds 76 such blocks in `0xE09358-0xE58322`; none overlaps any address we name, `[MonoThread]`'s eight sites
(`0xD71820 0xD81840 0xE4CEE0 0xE4D520 0xE4D9DC 0xE4EF90 0xE51070 0xE51350`) included [verified scan]. ScriptMath writes
with every other thread suspended outside the bytes; a lock interaction with our GcLock / ArenaFix is not visible
statically [inferred: none, test live].

### 2.2 Stand-down logic [verified]

- Detection still works on 3.0.0: Apex still creates `Local\ApexRadiance.<pid>` (`framework/s3ss_detect.cpp:205`), the
  config is still `Documents\Electronic Arts\The Sims 3\Apex Radiance\ApexRadiance.toml` with `[patches.<Name>] enabled`
  tables, and the user log shows `compat: Apex Radiance found at start (ApexRadiance.asi mutex) ... ApexStandDown=1`.
- `kApexSwitch` (ObjectLookupIndex, FastCacheCompression, MemoryGuard, ResourceLookupCache, FileListCache, the five Lot
  switches, defaults on/on/on/on/on/off x5) matches the 3.0.0 feature list and defaults exactly. **No new Apex feature to
  stand down for, none removed to take back.** The user's toml had MemoryGuard off (absent from the found line).
- Modules that stand down with Apex loaded: `[IdCache]`, `[SaveCompress]`, `[FootprintIndex]`, `[LotStream]`, `[Verify]`
  probes, `[SaveWrite]` call 0xAB12AF (per switch); `[LotPool] Trim`, `[ResourceCache] TrimAfterCleanup` and `[MemDiag]
  AllocSites` (blanket: memory is Apex's area). **So the rc1111 memory fix `[LotPool] Trim=1` does nothing for Apex
  users** (by design, docs/541): the release notes must say so.
- Not covered, unchanged: `[Alloc]` vs FastMemory (ours off in rc1111) and `[MonoThread]` vs ScriptMath (ours now on, no
  site overlap, §2.1).

### 2.4 Script side [verified]

Apex 3.0.0 ships no `.package`, writes no `Resource.cfg` and does not touch Mods. Its Mono code is ScriptMath (interpreter
compare blocks, type object cache) and the developer-only Frame Profiler. Nothing changes how script DLLs load, so it
cannot stop ts3fixes from loading. The report with zero ts3fixes lines was a duplicate ts3fixes.package (earlier triage).

### 2.5 The handled AV storm inside ApexRadiance.asi

- [verified, log + disassembly] In the report log, `ApexRadiance.asi+0x14E92F` (main thread) faulted 303,023 times
  between t=189 s and t=462 s, about 1,100 a second; eight Apex addresses together 310,667. 3.0.0's issue-55 fix (3
  classes, skip values under 0x10000) is in the release binary, yet slot class 2 / map 3 (manager +0x1F8) held 0x00091000,
  which passes the guard and faults under `__try`. **The issue-55 storm is not fully fixed in 3.0.0** (Apex's code).
- [verified, `ts3native.cpp:266-316`, `crashfx.cpp:179`, `castrim.cpp:1084`] Our crash log VEH (`XcptLog`, first in the
  chain) never swallows: it always returns `EXCEPTION_CONTINUE_SEARCH`, so Apex's `__except` handles its own reads; Apex's
  VEH (`RecordThrow`, last) only records. The filter chain with Apex on top is covered by selftest (`apex-test.h` case 5).
- Cost per Apex AV in our VEH: three owner checks, `CfOnFault` -> `CtOsFault` (since 3b13974b, in rc1111: copies 1 KB of
  the faulting stack and scans it on **every** AV in any module), then the 8-entry repeat table. [inferred] well under
  1 us, ~0.5-1 ms/s at 1,100 AVs/s, small next to the WOW64 exception dispatch and SEH unwind Apex pays itself.
- Misattribution [verified]: each new Apex AV address takes one of our 16 first-chance log lines (the report used 11 of
  16: eight Apex addresses, two C++ throws). A later first-chance AV in TS3W.exe can then go unlogged by `XcptLog`; the
  `[CrashForensics]` dump (before the cap) and the unhandled-crash report and ledger are not affected.
