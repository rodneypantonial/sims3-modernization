# 526. IL patcher, native half: `[IlPatch]` applies the docs/506 specs at Mono's IL transform

Written 2026-11-02 (contributor round 8, B1 native half; the offline half is docs/521). Static + disassembly + the native
selftest; the live smoke is listed in §6 with its state. Nothing here ships on: `[IlPatch] Enabled=0` and every fix switch 0.

## Summary

`native/ts3native/ilpatch.cpp` (next version, counters v907 `ilp*`) detours the Mono IL transform entry `0xE643B0`. For a
method one of the armed specs names, it reads the IL body through the method's cached header, hashes it, and on an exact size
and SHA-256 match with a build the spec knows (EA 1.67 or simler90 UPDATE242, docs/506 §1) splices the spec's instructions into a
copy of the body: the relocator of `tools/ilpatch-convert.ts` ported (every branch re-encoded long, switch tables re-targeted,
exception clauses moved, max stack raised by the spec's figure). The copy's SHA-256 must be the converter's `patchedSha256`
for that build; then the header's size, code pointer, max stack and clause records point at the copy for that one transform
call and are put back after it, also when the transform faults. Any other body (another core mod, Tiny UI Fix, an unknown
build) is left alone and logged once. The specs are compiled into the asi as a C table (`ilpatch-specs.h`, generated by
`node tools/ilpatch-convert.ts --emit-native`: opcode kinds, names, hashes, tokens and our instructions; no EA bytes).

The three fixes of docs/506 §5 are in the table: `ilp_fixupnoinventory` (core build 89, `SimDescription.Fixup`),
`ilp_remotechatnoeverydayoutfit` (build 80, `Sims.DoOneRoundOfRemoteChat`), `ilp_scavengersleep` (build 87,
`ScavengerOpportunity.OnAdded`).

## 1. The transform and the header [verified: capstone listing of `TS3W.exe` 1.67 in `game-copy/bin`, 2026-11-02]

- `0xE643B0` is `void* __cdecl transform(RuntimeMethod* rm, void* ctx)`, prologue `55 8B EC 83 EC 78` (6 bytes, the detour's
  copy). `edi = rm+8` is the MonoMethod, `ebx = rm`. satb.cpp's cold site 0 (`kSatbCold[0]`, docs/206 §7) is the same entry:
  with both on, ilpatch owns the detour and calls `SatbColdEnter(0, rm)` first (`g_ilpColdEnter`); Satb installs nothing there.
- It calls `mono_method_get_header 0xE85390` (cdecl, MonoMethod*), which returns the header cached at `MonoMethod+0x20` and
  fills it under the loader lock `0x11F43A8` only on a miss. `GenerateCode 0xE5CA90` (MonoPatcher's site, docs/06) reads the
  same cached header one call later.
- Header layout: `+0` code size, `+4` code pointer, `+8` max stack (16-bit: `imul dx,dx,0xa` at `0xE6494C` scales it),
  `+0xC` bits 0-14 clause count (`test [edi+0xC],0x7fff` at `0xE5CBED`; bit 15 is a flag the swap keeps), `+0x10` locals
  count, `+0x14` clause array (24-byte records: flags, try offset, try length, handler offset, handler length, class token or
  filter offset; the loop at `0xE5CC06`-`0xE5CC7C` steps `0x18`), `+0x18` locals.

So the swap of `+0`, `+4`, `+8` and the clause records for the call is what I-506-1 asked for: the transform reads nothing
else of the body. The header stays cached, so a later transform of the same method (MonoPatcher's ForceJIT) sees EA's fields
again and gets the same swap (`ilpReused`).

## 2. Flow (`ilpatch.cpp`, 364 lines)

1. `ApplyIlPatch(ini)` at start-up, before `ApplyMintCall` and Satb: `[IlPatch] Enabled=1` and at least one fix switch, SHA-256
   through bcrypt, the 6-byte prologue intact, `InstallDetour` at `0xE643B0`. Log `OK   il patch (docs/506 §2, docs/526): N
   of M fixes armed; ...`, one `il patch: <id> armed ([IlPatch] <switch>=1): <method>, N known build(s), N edit(s)` per fix;
   `SKIP il patch: ...` when bcrypt or the prologue is not as expected (another mod or probe owns the entry: no fix applied).
2. `IlpXform(rm, ctx)`: the Satb client first, then `IlpMatch` (namespace, class and method name read as monohost's
   `JitMethodName` does: `rm+8 -> MonoMethod`, `+8 -> class`, class `+0x34` name / `+0x38` namespace, method `+0x18` name,
   under `__try`). No armed spec: straight through to EA's transform.
3. First time for a matched method: `IlpBuildPatched` hashes the body (`ilpSkipHash` when no build matches: logged once with
   the size and 8 hash bytes), runs `IlpApply` (refusals in §3: `ilpSkipCheck`), checks the result's SHA-256 against the
   converter's (`ilpSkipMismatch`: "relocator mismatch, report it"; the fix stays off for that method). The patched body, its
   clause copies (EA's and ours) and sizes are kept per spec.
4. `IlpTransformPatched`: swap, `__try { EA's transform } __finally { restore }`, `ilpApplied` on the first call,
   `ilpReused` after; one `il patch: <id> applied to <method> (<build>, N -> N bytes, max stack N -> N, N clauses, patched
   sha256 ... as the converter's)` line.
5. A fault anywhere in the patcher's own reads (`ilpFaults`): the fix is off for the session and the call goes to EA's
   transform untouched.

## 3. Relocator checks (the converter's rules, ported)

Refused, with the reason in the log: a body that does not decode; more than 64 clauses or 16 edits; an edit offset that is
not an instruction start; opcodes at an edit offset that are not the spec's `expect`; a branch target inside a replaced range
or not an instruction start; our branch into or out of the exception region of its edit (I-506-3: Mono does not check it, so
the patcher does); a branch to a line the edit has not got; a token index past the build's list; an operand kind the table
does not carry. Insertions move the clause boundaries after them and an insertion at a boundary keeps the original side
(`incoming`), as the converter.

## 4. Counters (v907, `docs/registry.md`; the probe's `nativeCounters` lists them from version 907 on)

| Field | Offset | Meaning |
|---|---|---|
| `ilpOn` | `0x5C14` | the transform detour is installed |
| `ilpArmed` | `0x5C18` | fixes with their switch on |
| `ilpApplied` | `0x5C1C` | methods transformed with a patched body (first time each) |
| `ilpReused` | `0x5C20` | repeat transforms of a patched method that reused the body |
| `ilpSkipHash` | `0x5C24` | listed methods whose body is not a build the fix knows |
| `ilpSkipCheck` | `0x5C28` | bodies refused by the decoder or the relocator, or with no header |
| `ilpSkipMismatch` | `0x5C2C` | patched bodies whose SHA-256 is not the converter's |
| `ilpFaults` | `0x5C30` | faults inside the patcher (fix off for the session) |

## 8. Batch 3 live: smokes 22 to 25 (2026-11-02) [measured: `probe-out/queue/ilpatch-smoke10-local-*`]

Three runs on the pure UPDATE242 core with all 21 specs armed found two defects of the patcher, neither visible offline:

1. **Nested classes (smokes 22, 23, asi 3384648): 12 of 21 applied.** The nine missing were the nested ones
   (`Door+PrankDoorbellDitch`, `HorseshoeCourt+WaitToThrow`, ...). `IlpClassIs` walked the enclosing classes through
   `nested_in` at `+0x2C` of MonoClass, the offset of the public Mono 2.x layout. A monohost probe of this Mono's MonoClass
   (temporary code in `GuardSweepTest`, removed) showed `nested_in` at `+0x28` (`+0x2C` is another pointer; the name at
   `+0x34`, the namespace at `+0x38`). Fixed in 3d05b33 (`ilpatch.cpp`, the fake class of `ilpatch-test.h`). Smoke 24 with
   it: 20 of 21 applied.
2. **A block's own branch to its "at" (smoke 24, asi 3d05b33): a hang at 8.3 min.** The agent's heartbeat froze, the harness
   killed the game; the hang capture's sim thread is in `Pool.ReactToSkinnyDippers` (b69) under `Lot.Simulate`. The core
   patch ends its block with `brtrue.s IL_007d`: continue with EA's instruction at `0x7D`, which is also the block's `at`.
   The offset map (the converter's `map()` and the patcher's `Map::of`) sent a branch to an insert's `at` to the block's
   first line when the branch came from that same edit, so the block looped on itself whenever `CreatedSim` was not null,
   the common case. b17-1 (`bge @0x8`) and b90 (`brfalse @0x4BB`) had the same shape; smokes 22 and 23 had ended in the same
   silent hang, read then as an agent stop. Fixed in b22f82b: that clause is gone from both maps, a fallthrough insert's
   `@at` means the original instruction after the block (an incoming insert's or a replace's `at` still means our first
   line); converter self-check and selftest case D cover it, the three specs and the native table regenerated. docs/521 §6
   point 4.

Touch semantics, seen in these runs: `method_touch` queues the call and answers at once; the outcome line
(`touched <path>: <method>: returned | <exception>`) appears only in a later `async_log` reply, so a touch whose outcome never
shows is unknown, not failed. b73 `EggHuntController::IsValidEggPosition` was touched in all three runs (`queued 1`) and
never logged an outcome or an `applied` line: still open. b75-2's `ProcessLifeEvent` has a 194-byte overload that is logged
as "not a build this fix knows, left alone": `IlpMatch` matches by name and has no signature check, the other overload
applies, the line is the designed answer. The smoke queues' forbidden rule now allows that one line (`not a build this
fix knows, left alone` at most 1); `refused`, `not the converter's` and `fault` still fail the job.

**Smoke 26 (asi b22f82b, 2026-11-02 19:58, the harness logging touch outcomes whole, 83b1176): b73 explained.** The touch
of `EggHuntController.IsValidEggPosition` ran and reported `EggSpotHook::Boolean IsValidEggPosition(Single, Single,
Single, Single): returned`: the method the game runs under that name is ts3fixes' `eggspot` hook (`EaFixes.cs`:
`Patch(typeof(EggHuntController), "IsValidEggPosition", typeof(EggSpotHook), "ValidHook", "ValidOrig")`, docs/508, the
same core Build 73 fix as a script hook). The header swap at ts3fixes start-up moves EA's body to `EggSpotHook::ValidOrig`,
so the transform of `EggHuntController::IsValidEggPosition` never sees the body b73 matches; no `il patch:` line is the
expected trace. No assembly names an `EggSpotHook` type (EA's and both UPDATE242 cores checked), which is why the name
did not match a spec. Consequence: with ts3fixes installed b73 is unreachable; the fix is the same either way. Open:
either ts3fixes skips its `eggspot` patch when `[IlPatch] ilp_eggsplacedonthehuntlot=1` is armed (ts3native would have
to publish the armed set to managed code), or b73 leaves the IL set and docs/508's hook stays the one owner. Until one
of those lands, a smoke with ts3fixes installed cannot show b73 `applied`; the required line stays so the row says so.
Smoke 26 otherwise: 20 of 21 applied, no hang, no fault, 10.3 min.

Smoke 25 (asi b22f82b, queue `ilpatch-smoke11-local.json`, 17:59 to 18:09): **20 of 21 applied, no hang, no crash**, the
10 min of play after the touches ran clean (stuck Sims 0, game alive); the harness verdict is FAIL only for b73's missing
`applied` line. b73 is the one method that no run has ever seen at the transform hook: every skip path of the patcher logs
once (no readable body, unknown hash, refused, relocator mismatch) and none did, so its transform never happened while
armed; the touch is queued (`queued 1`, the method is an instance one, 52 bytes, found by name) and the harness log cuts
the `async_log` replies short, so its outcome is unread. Open: read the touch outcome in full (a filtered `async_log`, or
the agent returning the outcome of the previous touch), then decide whether the smoke requires b73.
