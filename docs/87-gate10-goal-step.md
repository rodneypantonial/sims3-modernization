## 1. Summary

- **What the goal step does [verified, decompile of `0x75C2D0`].** Called once per plan, from one site only: `Route_PlanCommon` at `0x760BFA` (return `0x760BFF`, the gate-10 wait key since P1; P0 keyed it by site, `0x100000A`). It filters the plan's candidate goal records (64 bytes each) into an accepted and a rejected vector. Per goal: lot lookup (`World_LotLookup 0xC68990`), lot-local point checks (`0xADD7A0`/`0xADD800`, `0xB015B0`, `0xB01060`, `0xB01550`), room reachability between the start and the goal room through the lot planner (`LotPlanner_GoalRooms 0x63F490`, cached per call in a stack hash map "Routing/LotRoomRecordToReachabilityMap"), an optional physics range query (`Routing_PhysicsRangeQuery 0x83B3A0`), an obstacle query under `+0x918` (`RoutingWorld_ObstacleQuery 0x82EDB0`) with a per-footprint type switch, terrain type and height checks (`IC_World_GetTerrainTypeImpl 0x789890`, `0xB793F0`, `Terrain_GetHeight 0xC6A540`), and a goal footprint gather under `+0x918` (`RoutingWorld_GoalFootprintGather 0x82F0B0`) with point-in-polygon tests through footprint slot `+0xB8`. No managed or remote entry within 5 direct hops (§3).
- **Who calls it on the sim thread [verified callers, rates from run files].** `Route_PlanCommon` has two callers, `Route_StartPointsFromPosition 0x7641D0` (from `IC_Route_Plan 0x765160` and `IC_Route_Replan 0x765490`) and `Route_StartPointsBuild 0x7642C0` (from `IC_Route_PlanFromPoint 0x765240` and `IC_Route_ReplanFromPosition 0x765550`); the four ICs are referenced only from the script binding table (`0x11608E0..0x11608F8`). With async on, `IC_Route_Plan` runs on the worker inside the job (owner, never a gate wait). What stays on the sim is the **synchronous plans**: `Replan`, `PlanFromPoint`, `ReplanFromPoint` (docs/18 kept them sync by design) and `Route.Plan` calls that did not go async (no START, refused START). Clean `bp-env-on`: 10,245 sim goal steps (17/s) and 13,094 sim-thread `Route_PlanLocked` calls, 37.9 s of plan time (63 ms/s), next to 16,952 async jobs; `ip-env-on`: 5,261 and 4,387, 74.8 s (125 ms/s) next to 6,483 jobs. Every logged unlocked entry of the site came from `0x760BFF` (34 log lines, 0 other callers).
- **The wait is a real dependency, twice [verified code, overlap inferred].** (1) Data: the goal step writes the same shared routing state a job writes: the lot planner's single A* object Q (`AStarSearch_Reset 0x61E320`, node clear `0x61C020`, generation stamp `0x61E360`) and the lazy lot and room graph (`LotGraph_Build 0x63CB90`, `RoomGraph_FirstUse 0x63D2F0`, `RoomToRoomAStar 0x6339F0`), lot table find-or-insert (`0x62EAB0`), quadtree pin and deferred flush (`0x667480`, `0x666A40`), the lot index rebuild (`0xC68680`, lock `[WM+0x228]`), and plain (non-atomic) footprint refcounts `+1`/`-1` around its own footprint loop. This is exactly crash 3 (docs/re/dead-ends.md). (2) Lock: when the goal step accepts a goal, `Route_PlanCommon` calls `Route_PlanLocked 0x82C6E0` at `0x760DE1`, which takes `+0x918` at `0x82C733` for the whole search. Removing the gate-10 wait would only move it to that acquire, and the goal step would race the job. Unlike gate 0 (docs/86), this is **not gate policy**.
- **Live size [verified run files].** Key `0x760BFF`: clean `bp-env-on` 279 waits, 2.15 s (3.6 ms/s, 3.7% of the sim wait), mean 7.7 ms against a mean job of 5.1 ms; `bp-s2-on` 275, 2.19 s; `bp-s2-shadow` 288, 1.93 s; h6 `bp-env-on` 190, 1.76 s; `bp-d-async-3/-4` 176/230, 1.65/1.71 s; P0 `bp-p0-async` (`0x100000A`) 175, 1.62 s (3.7%). `rgJob_goalStep` equals the wait count in every run (each job-live entry waits once). Isla Paradiso: 4-10 job-live entries per run, under 0.1 ms/s. Only 2.7% (BP) and 0.2% (IP) of sim goal steps meet a job although jobs run 14% / 11% of the time: most job time passes while the sim is already blocked on that job (57.3 s of the 85.7 s job time in clean `bp-env-on` is sim wait), so a sim-side sync plan rarely starts during one [inferred, I-87-4].
- **H2 (docs/86) does not remove it [verified reach, effect inferred].** H2 holds job starts during `Locomotion_Update 0x83CED0`. The goal step is reached only from the four script ICs, and `Locomotion_Update` has no managed reach within 5 direct hops (docs/86 §3), so no goal step runs inside the H2 window. Held jobs start right after the pass; if more job time then overlaps the script stage, gate 10 grows a little (I-87-5).
- **Recommendation (§5): measure the sync-plan family first (probe P10), then make `Replan` asynchronous like `Route.Plan` (design A10), `PlanFromPoint`/`ReplanFromPoint` after that if P10 ranks them.** The 3.6 ms/s gate-10 wait is the visible part of 13k synchronous plans per 10 minutes (63 ms/s BP, 125 ms/s IP sim plan time, lower bound). A10 reuses the existing `PlanAsync` handshake and job queue. **Gain cap** [inferred]: gate 10 itself ≤ 3.6 ms/s BP; with the plans themselves ≤ 63 ms/s BP / 125 ms/s IP if every sync plan were yieldable `Replan`-family work; realistic 10-30 ms/s BP once P10 gives the yieldable share. **Effort** ~0.5 d for P10, ~2 d for A10 `Replan` (same IC signature as `Plan`), +1.5 d for the two point variants. A cheap side option, G10-C (one coarse frame on `Route_PlanCommon` instead of the goal step), removes only the second waits of a sync plan (≤ ~1 ms/s, 0.5-1 d).

Script callers [verified grep, `game-copy/decompiled`]: 197 `.Plan(`, 34 `.Replan(`, 27 `.PlanFromPoint(`, 24 `.ReplanFromPoint(` call sites; the `Replan` family sits in 33 files, most in `SimRoutingComponent` (14), `Sim` (10), `GameObject` (5) and the route actions (`FollowSubPathRouteAction.ForceReplan`, `ObstacleEncounteredRouteInterruptAction`, `DestinationObstructedRouteInterruptAction`, `ChangeDestinationRouteInterruptAction`, `ReplanRouteInterruptAction`, vehicle/boat follow actions). The managed profiles rank "DoRoute replans" at 16% of plan script time (docs/04a §8, PLAN). `PlanFromPoint` also comes from `SimEx.IsPointInLotSafelyRoutable` in a FunctionTask (Overwatch stuck check, `mods/ts3fixes/src/OverwatchStuck.cs:10`), which is not the Sim's own task.

**What follows the goal step in `Route_PlanCommon` [verified, `0x760BFF..0x760F92`].** Accepted vector empty: return a failure status (`0xA`, or `0x12` when the first rejected goal has `+0x30 == 1`) without planning. An x/z bounds test over the accepted goals (`0x760D21..0x760D68`, constants `0xF98964`, `0xFAA210`, `0x100412C`; the meaning of the test is not decoded) can also return status `0xA` without planning. Otherwise `Route_PlanLocked` (`+0x918` at `0x82C733`, then `RoutingWorld_ApplyPendingUpdates`, `RoutingJob_Execute`), `Route_MapStatusToResult 0x752620`, and per path `RouteFollow_EditPathForRoute 0x85FF30` -> `RouteFollow_EditPath 0x85F5A0` -> `GoalFootprintGather` (`+0x918` again; the P0 key `0x85FFC7`, merged into `0x85F6CB` since 0.11.5, docs/83). A sync plan can therefore meet a job three times: at the goal step (gate 10, the job was running at entry), at `Route_PlanLocked` (a queued job started in the gap after the goal step's frame closed), and at each EditPath tail. No keyed wait slot in clean `bp-env-on` lies in `Route_PlanLocked` (`0x82C738`) or at `0x760DE6` (183 waits unkeyed in total), so the gap after the goal step is rarely hit [verified absence, rate inferred].

## 5. Design options

Rules as in docs/80/83/84/86: sync reads the sim needs now cannot move to the worker; lock-free only where no job-written state is read; managed reach stays on the sim; gains do not add.

| # | Option | What | Risk | Effort | Gain cap [inferred] |
|---|---|---|---|---|---|
| R | **Lock-free goal step** | run `0x75C2D0` without the gate while a job runs | reintroduces crash 3 (Q, lazy graph builds, lot table insert, plain refcounts written by both threads); and `Route_PlanLocked` right after waits for the same job | - | none: not feasible |
| S | **Snapshot answer** (cache accepted/rejected goals per route) | answer the filter from a copy taken when no job ran | the answer depends on live footprints, rooms and Sim positions; stale answers change routes; and the plan still needs `+0x918` next, so the wait moves to `0x82C733` | 3+ d | ~0 net; only early-return plans (no `Route_PlanLocked`) would gain, share unknown |
| G10-C | **Gate policy: one coarse frame on `Route_PlanCommon`** (move the site-10 detour from `0x75C2D0` to `0x7606E0`, same prologue `55 8B EC 83 E4 F0` [verified bytes]; the goal step entry becomes a nested, uncounted frame) | a job running at entry is waited for once and `+0x918` is held for the whole sync plan; no queued job starts between the goal step, `Route_PlanLocked` and the EditPath tails | job starts wait for the whole sync plan (mean 2.9 ms BP, 17 ms IP, long tail): async Sims' READY polls take a tick or two longer (latency, not sim time); the worker spins `Sleep(0)` meanwhile; hold-time watchdog needed; the frame also covers worker-side PlanCommon (owner skip, as today) | 0.5-1 d (site table entry, counters, selftest, docs/68) | the second waits only: ≤ ~1 ms/s BP (P0 `0x85FFC7`), plus rare `Route_PlanLocked` gap waits; gate 10 itself unchanged |
| **A10** | **Queue to the worker: async `Replan` (then `PlanFromPoint`, `ReplanFromPoint`) (recommended after P10)** | extend `RouteBackoffHook` (`mods/ts3fixes/src/RouteBackoff.cs`) from `Route.Plan` to the three methods (Route.cs:930-1000: each is one internal call whose result is stored and returned), same eligibility (follower is a Sim, `Simulator.CurrentTask == sim.ObjectId`, `MayYield()`), same START / READY / CANCEL handshake; native: a job kind per slot so `ServeAsync` calls the matching original (`IC_Route_Replan` has `IC_Route_Plan`'s signature; the point variants store the point in the slot), `IcPlanHook`-style collect detours on the three ICs | as async `Plan` (docs/18 crash list): nested yield (existing `CanYield` / `kNoYield` probe), result read right after (the hook waits inside the method), route freed during a job (AddRef pattern verified above), the same route asked again while its job is queued (`JobFor` + `DropJob` rule); new: replans from route actions may run inside native->managed callbacks (then `NoYield`, they stay sync), FunctionTask callers (Overwatch) are not eligible; more worker load (job duty 14% -> up to ~20% BP), so more steering overlap (gains do not add) | P10 0.5 d; `Replan` 2 d (C# hook, job kind, collect detour, counters, selftest, harness switch); point variants +1.5 d | gate 10: ≤ 3.6 ms/s BP; plus the moved plan time: ≤ 63 ms/s BP / 125 ms/s IP (all sync plans, lower bound); realistic 10-30 ms/s BP after the yieldable and by-IC split |

| H2 | **docs/86 H2** | holds job starts for the locomotion pass | no goal step runs inside the pass (§1); held jobs start right after it | 0 (already planned) | 0 for gate 10; may raise it slightly (I-87-5) |

**Recommended: P10 first, then A10 for `Replan`, then the point variants if P10 ranks them; G10-C only if P10 shows second waits per sync plan above ~1 ms/s.** A10 is the only option that removes the gate-10 wait instead of moving it, and it moves the much larger sync-plan time with it. It composes with H2 (different stage), S2, D and L1 (no new lock; jobs are ordinary `ServeAsync` jobs under `+0x918`).

A10 details:
- Switch `[RouteAsync] Replan=0|1` (and `PlanFromPoint=0|1`), runtime mode for `--ab asyncreplan`; ts3fixes shortcut name `asyncreplan` next to `asyncroute`.
- Job slot gets `kind` (0 Plan, 1 Replan, 2 PlanFromPoint, 3 ReplanFromPosition) and the point; `ServeAsync` dispatches on `kind`; collect detours on `0x765490`, `0x765240`, `0x765550` copy the stored 0x48-byte result when armed, as `IcPlanHook` does; a collect for a different kind than the job's drops the job and plans synchronously.
- Counters (reserve in docs/registry.md first): `arStarted[4]`, `arRefused[4]`, `arCollected[4]`, `arJobUs[4]`, `arSyncUs[4]` (sim-thread time of the plans that stayed sync, by IC), `arKindMismatch`.
- Tripwire: a `kind` mismatch or a collect without a job logs once with the IC return address.
