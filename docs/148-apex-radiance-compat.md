## 2. How Apex Radiance works

**Entry and init order** [verified `apex_main.cpp`]. `DllMain(ATTACH)`: process check (`TS3W.exe`/`TS3.exe`), instance mutexes `Local\ApexRadiance.<pid>` and `Local\S3SSApex.<pid>` (a second copy, or an old `S3SSApex.asi`, idles), a Detours detour of the `Direct3DCreate9` export of the already loaded `d3d9.dll` (DXVK here), then an init thread. Init thread: log, game version, background HLSL precompile, S3SS detection (module strings), feature objects, config load; then **waits for the first Present plus 1 s** (20 s timeout) so official S3SS has installed its patches; then resolves game addresses (fixed table on Steam 1.67.2, masked signature scan elsewhere), installs the enabled features, installs its crash filter, and becomes a 10 ms pump (feature `Update()`, autosave, once a second `CrashReport::Refresh`). Consequence for us: ASI loader order is file-name order, so `ApexRadiance.asi` loads before `ts3native.asi`, but its game-code writes always come after our `DllMain` writes. It never sees "vanilla" bytes where we patched.

**Config** [verified `apex_paths.cpp`]: `<Documents>\Electronic Arts\The Sims 3\Apex Radiance\ApexRadiance.toml`, one `[patches.<Name>]` table per switch, a missing key reads as the default (on), an explicit `enabled = false` stays off; `apex_radiance_imgui.ini`, `ApexRadiance_LOG.txt`, `ApexRadiance_Crash.txt/.dmp`, `Diagnostics\`. It reads `S3SS\S3SS.toml` read-only (migration, S3SS intent).

**Hook mechanism** [verified]. Microsoft Detours is statically linked (`.detourc`/`.detourd` sections in the binary). Game-code sites use three layers: (1) `MemPatch::WriteBytes/WriteDWORD` with an `expected` byte array (call rel32 retargets, immediates); (2) `entry_chain` (5-byte `jmp` over a function entry, layered between Apex features; fails with "the entry bytes ... changed (hooked by another module?)" and never overwrites foreign bytes); (3) `slot_chain` (vtable slot swap; fails with "the vtable slot ... holds X, expected Y (replaced by another module?)"). A mismatch makes **that one feature** stay off with a status line and a log line; it does not abort Apex or the game. Write errors on game code run under `WriteCodeSuspended` (other threads stopped). D3D9: 15 `IDirect3DDevice9` methods detoured at the first EndScene; their doc says Detours chains compose in either order.

**Threads** [verified by `CreateThread`/`std::thread` search]: init/pump, log writer, HLSL cache worker, Room to Save watcher (64 KB stack), allocator big-block release worker, codec pools (DXT, CAS, RefPack), two lighting workers (`lot_light_bridge`, `lightmap_smooth`); developer mode adds the address-space observer and the Frame Profiler sampler/writer.

**Build flavour** [verified `build_flavor.h`, binary]: `game_alloc_categories` (hooks `0x4E3F70/90/B0`) is development-build only and its addresses are not in the release binary. Frame Profiler code is in the release binary but only runs in developer mode (off by default).

**Imports of note** [verified PE parse]: `SetUnhandledExceptionFilter`, `AddVectoredExceptionHandler`, `GetAsyncKeyState` (hotkeys), `Get/SetWindowLongW` (window subclass), `VirtualProtect`, `LoadLibrary*`, `ShellExecuteW`. No network imports (no WinInet/WinHTTP/sockets). No exports.

### 7a. `[SaveWrite]` at `0xAB12AF` next to Room to Save, and the filter chain

Sources read: ours `savewrite.cpp`, `crashreport.cpp`, `routegate.cpp` site list; Apex 2.15.0 `features/memory_guard.cpp` (`Start`, `SaveDispatchHook`), `framework/crash_report.cpp` (`Install`, `Refresh`, `Uninstall`).

| | Fact | Mark |
|---|---|---|
| 1 | Room to Save's early save preparation is installed only if `CallsTo(0xAB12AF, 0xAAC110)` holds, the 9 bytes before the call match, and `0xAAC110` is either the game's entry or a `jmp` that lands inside `ts3native.asi`; else it logs "Early save sites differ; existing world-save preparation retained" and keeps the older path at `0xAAC320` | [verified `memory_guard.cpp` `Start`] |
| 2 | Its hook (`SaveDispatchHook`) releases Apex storage, trims the allocator, lets the reserve go, then calls `0xAAC110` itself, so our `[RouteGate]` count-only jump at that entry still runs | [verified] |
| 3 | Our hook at `0xAB12AF` (`SaveWriteHook`) only times the call into `0xAAC110` (`saveLastWriteUs`, the `write` part of the save log line). The backup offload hangs on `0xAB10F6` (job start) and `0xAB134E` (promote), the other timings on `0x742A95`, `0xAB1363`, `0xAB1410` | [verified `savewrite.cpp`] |
| 4 | Chaining "ours calls their prepared path" is not possible: Apex writes its call after ours and refuses unless the rel32 still goes to `0xAAC110`; it exports nothing we could call | [verified] |

**Decision (built):** with Apex found and `MemoryGuard` on, `[SaveWrite]` patches five of its six call sites and leaves `0xAB12AF` to Apex (`SaveSitesFor`). Lost: the timing of the call itself; the write is then the span from our `[RouteGate]` entry at `0xAAC110` (else the info step's end) to the next step, logged `write ~N (gate span)` / `(info span)` (docs/25 §10); kept: the backup offload, `[SaveFlush]` and every other phase time. Apex's early preparation then sees the game's call and goes on [inferred from 1-3: not seen in an Apex log yet]. Late case (`zzApexRadiance.asi`): the late thread puts the original rel32 back (`SaveWriteYieldToApex`) if the site still goes to our hook: one locked 4-byte store at `0xAB12B0` (4-byte aligned [verified]) before Apex's first-Present check; no save can run before a world is loaded, so no thread is inside the call then [inferred]. `ApexStandDown=0` keeps today's behaviour (ours on all six, Apex's early preparation off), for the A/B `apex-ab-saveprep`.

**Filter chain (#8):** Apex calls `SetUnhandledExceptionFilter` through its own import (never the exe IAT slot `0xF9517C` we swap) once at install and again every second in `Refresh`, where it keeps the filter it replaced only if that is not its own, then calls it after its report; `Uninstall` puts the previous one back unless someone replaced Apex's [verified `crash_report.cpp`]. Ours never re-sets the kernel32 filter after start, so nothing fights: the chain is Apex -> ours -> EA's (EA's arrives through our IAT stand-in). Built: `CrFilter` skips itself as its own next and returns `EXCEPTION_CONTINUE_SEARCH` when it is re-entered on the same thread (a cycle ours -> Apex -> ours), instead of recursing until the stack overflows [selftest; no such cycle seen live].

**Tests (selftest `TestApex`, `apex-test.h`):** detection with a stand-in module name (bits 1/2) and the real mutex name created by the test (bit 4), absent = 0; toml parse (defaults, `false`/`true`, CRLF, other tables, a longer name with the same prefix, comments); every stand-down decision, the four module entries returning before any write, the `[Verify]` site owners; `SaveSitesFor` five vs six sites; late give-back once, not when not ours, not when `[SaveWrite]` is off; filter chain Apex -> ours -> next once each, cycle and self-next end. ## 10. Save matrix with Apex (2026-10-22, chain111)

`apex-save-matrix` (11:42 PHT, Apex 2.15.0 + `[SaveWrite]` on 6 sites, the tested asi has no `[Compat]` stand-down yet): control PASS (saves 15.7 / 12.0 s, result 0); `identical` FAIL only because `cachedreflection`, `footprint`, `compress`, `flush` were not available to switch (release ini), not a byte difference. Apex itself does not break the matrix [verified, job log].

`apex-ab-saveprep` (11:47 PHT, same plus `[SaveWrite] Enabled=0`) failed control and identical with "no save line in ts3native.log" on both saves. Cause: **harness** [verified]. `save-matrix.ts` took a save as done only on the `save: result ...` line, which `savewrite.cpp` writes only when `[SaveWrite]` is on (`ts3native.log`: `save write disabled (Enabled=0)`, no `save:` line); the game did save: the second save was named `off-16` because `nextName` found `Matrix-NewDowntownWorld-off-15.sims3` on disk, written after the first call, and `game_state` showed no save in progress at both 30 s guard checks. Not Apex, not the `0xAB12AF` retarget (it was not patched in that run). No Apex log was captured (§9 gap 1), so whether Apex's early preparation started is still unseen.

Fix: with `save write disabled` in the log, a save is done when its folder changed after the save call and the game reports no save in progress, after it was seen saving or one idle guard period (`savedWithoutLine`, self-check); the result check then passes with "no result code" and the save time is the wall time only (no `total`/`write` split, no compress or flush lines). Rerun `apex-ab-saveprep`; expect `identical` to fail as in `apex-save-matrix` until those fixes are available. Ledger §247 (docs/51).

Why the four were not available [verified, job ts3native.log + source]: `footprint`, `compress`, `flush` = release ini `[FootprintIndex]`/`[SaveCompress]`/`[SaveFlush]` Enabled=0 (log `footprint index disabled`, `save compress off`, `save flush off`), so nothing was installed to switch (with Apex `MemoryGuard`/`FastCacheCompression` on and Enabled=1, the §6 stand-down would drop the first two as well); `cachedreflection` = ts3fixes refused its three patches because `PersistedClass.Init`, `PersistedClassDB.GetPersistedClass` and `Persist.GetPersistedTypeCode` were already compiled when `Fixes.Apply` ran (same since 2026-10-16; tuning `kCachedReflection` off as shipped). Not renamed switches, not fixes.json, not Apex. Fix (harness): fix-on cases switch only installed fixes and print `fixes skipped (not in this build/ini)` with each reason; SKIP/FAIL lines, a failed cachedreflection probe or a missing fastreftable still fail; `--fixes shipped` (release-validate) unchanged and strict. In these jobs `identical` now compares fastreftable on vs off (`[SaveWrite]` as the job ini sets it, both sides).
