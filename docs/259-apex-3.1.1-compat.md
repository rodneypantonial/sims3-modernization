## 2. Overlap

### 2.1 Code sites [verified]

The literal scan of rc1111g's `native/ts3native` (f979d8ed) against Apex 3.1.1 gives the same 34 shared addresses as
3.0.0 vs rc1111 (docs/254 §2.1): none new, none gone. **One new shared site is found only by pattern**, because Apex
names it in a comment, not a literal:

| Address | Apex 3.1.1 | ours (rc1111g) | Who installs first | Class |
|---|---|---|---|---|
| `0xD70FB2` (call `0xD70FB6`) in the delegate check `0xD70F90` | `DelegateSigFix` (`features/delegate_sig_fix.cpp`, always on): scans `8B 7E 10 57 E8 ?? ?? ?? ?? 83 C4 04 66 83 7E 04 01 75 ?? 83 F8 1D 75`, checks the call leads to `mono_type_get_type 0xF4AC60`, rewrites the call to a stub that returns 0 when `param_count != 1` | `[MonoSigGuard] Enabled=1` (release on, docs/539 §20, `monosig.cpp`): 19-byte check, then `jmp` + 4 `nop` over `0xD70FB2-0xD70FBA` | **ours** (DllMain, before Mono) before Apex (`InitBody` after `GameAddr::Resolve`, apex_main.cpp:211) | **C1**: our `jmp` removes the pattern's first 4 bytes, so Apex logs `[DelegateSigFix] Delegate check not found in this game build: off` and writes nothing |

- The pattern has exactly one hit in TS3W.exe 1.67 (`0xD70FB2`), the address of our `MSG_SITE` [verified, scan of
  `game-copy/bin/TS3W.exe`]. Both strings are in the release asi [verified].
- Both fixes are the same fix (Apex's doc: "Works beside sims3-modernization"): for `param_count != 1` both skip the
  read and return EA's own false; for 1 both run the original call. So with both loaded the game behaves as with ours
  alone (release-verify rows); with ts3native's guard off, Apex's covers the site. No stand-down is needed.
- If the order ever flipped (Apex first), our 19-byte check fails on Apex's `E8` target and logs
  `SKIP mono sig guard: bytes at 0x00D70FB2 differ: not installed`: still one fix, ours off. §6 forbids that line.
- Added as class C1 to `docs/data/apex-sites.csv` and `docs/data/apex-hooks.csv`; `node tools/hook-sites.ts --check`:
  1098 addresses, 0 not in docs/68, 32 named by Apex, 0 without a class.

Other new writes in 3.1.1 [verified]: `screen_control` rewrites the rel32 of S3SS's frame limiter call (pattern
`3E 56 E8 ?? ?? ?? ?? 5E EB`, 0 hits in vanilla TS3W: it exists only after S3SS patched it), and only while an Apex
frame limit is set; `atrium_hold` / `d3d9_extra_hooks` detour d3d9 methods. We have no d3d9 hooks and do not touch
S3SS's limiter. Apex now stays loaded (idle, no hooks) in `Sims3Launcher.exe`; our `[LauncherFix]` patches
`TSLHost.dll` in the launcher host only, so the two do not meet [verified source; inferred no runtime effect].

### 2.2 Stand-down logic [verified]

- Detection unchanged: mutex `Local\ApexRadiance.<pid>` and `ApexRadiance.toml` `[patches.<Name>] enabled` tables are
  as in 3.0.0 (source and the same strings in both release binaries).
- `kApexSwitch` (ObjectLookupIndex, FastCacheCompression, MemoryGuard, ResourceLookupCache, FileListCache, five Lot
  switches) still matches the feature list and defaults: **no new Apex feature to stand down for, none to take back.**
  `DelegateSigFix` has no switch and needs none (§2.1).
- Unchanged consequence (docs/254 R5): `[LotPool] Trim`, `[ResourceCache] TrimAfterCleanup` and `[MemDiag]
  AllocSites` stand down with Apex loaded; the release notes say so.

### 2.3 Shared resources

As docs/254 §2.3, plus: the Display page can change the game's resolution through the game's own request
(`0x77D1A0`) and device-lost path; the frame limiter waits on the render thread; the low-memory note reads MemoryGuard's
address-space samples. None of it touches the sim thread, routing, Mono or our ini [verified source]. The ASI loader
still loads `ApexRadiance.asi` before `ts3native.asi` (file-name order).

### 2.4 Script side [verified]

3.1.1 ships no `.package` and does not touch Mods or `Resource.cfg`; `DelegateSigFix` changes only the native check
in front of `ScriptHost_InvokeDelegate 0xD75FA0`, which ours already guards.

### 2.5 Issue-55 AV storm and our VEH

- `StoryMapsInclude` (`features/level_light_share.cpp`) is byte-for-byte the 3.0.0 function [verified diff]: the
  `w >= 0x10000` guard still lets the 0x00091000 slot value through to the `__try` read. **R1 is not fixed in 3.1.1.**
- Ours: the foreign-module AV cap (PR #120, 8 remembered addresses, repeats on the minute counters line) is in rc1111g,
  so R3 is closed. `CtOsFault` still runs on every AV in any module (`crashfx.cpp:188` at f979d8ed): R2 stays open as a
  should-fix; the 3.0.0 live rows showed no cost worth a rebuild. §6 job 6 reads the AV count again.
