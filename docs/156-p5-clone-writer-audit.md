# 156. P5 clone writer audit: is the clone's answer the game's answer

Written 2026-10-22. Static only: the game was not run, no probe, no queue, no native code changed. Downstream side of P5 (`[RouteSnap] Mode=2`, docs/94 §22): for every input the clone search reads, every native writer, and whether the replay clone sees what it wrote. Inputs from docs/91 §2, docs/94 §17.2 and §21.2, docs/98, docs/99, docs/101 §2.3; recorder and clone from `native/ts3native/routesnap.cpp`, `snap.cpp`, `replay.cpp`, `p4clone.cpp`.

Tools: capstone 5 over the Steam 1.67 `TS3W.exe` with `functions.csv` (inclusive ends, docs/101 tool fix); a raw rel32 scan of `.text` for every `E8`/`E9` edge; a 4-byte data-reference scan of the whole image (vtables, tables); a per-function sweep of indirect calls `call [reg+disp]` and `mov reg,[reg+disp]; call reg` in the routing ranges `0x600000-0x680000`, `0x740000-0x7A0000`, `0x800000-0x840000`, `0x940000-0x960000`; direct closures (6 hops) of the lock-key ICs; `docs/data/routing-indirect-sites.csv` (docs/102, docs/109 live pass 2). Scratch scripts stay in the session scratchpad.

Tags as in AGENTS.md: **[verified]** = read in the disassembly (address given); **[inferred]** = reasoning, with a ledger row (docs/51, `I-156-*`) and the check that closes it.

## 1. Summary

- **One verified unrecorded writer that changes the clone's answer: the lock-key set pointer `fp+0x20` of an inserted footprint (U1).** `Footprint_SetLockKeyObject 0x807110` (slot `+0x8C` of all 10 footprint classes, no direct caller) swaps `fp+0x20` in place [verified]. It is reached from the four lock-key ICs through `RouteManager_FootprintLockKeyApply 0x82B2B0` (site `0x82B3AC`) on the footprint already in the lot (`LotRouting_FindFootprintByKey 0x62F600`), with **no** W1/W2, quadtree insert/remove, footprint leaf or `+0x918` anywhere in their 6-hop direct closures [verified]. The replay copy of that footprint keeps the pointer it had at its INS; `PcKeysApply` (p4clone.cpp) re-points only non-NULL pointers and skips NULL (`if (!set) continue;`), and the lot signature (`RpSig`) has no footprint field. So a footprint that gets its first lock-key set after its INS keeps answering "no keys" in the clone until it is re-inserted, its lot is fully rebased, or the epoch moves [verified source]. A swap from one set to another mostly ends in a refusal instead (`PcKeysApply` returns false when no live footprint still holds the old set: `mat`), and a set released to NULL leaves the clone on the old set's copy only while another live footprint still holds that set [verified source; the set-per-object rule of `0x947700` inferred]. The in-room class of portal, terrain, lot-edge and polygon footprints reads `fp+0x20` (`0x807090`: 6 or 0 by the agent's allow/deny pass, docs/98 §5): a door portal footprint can be passable in the live answer and closed in the clone, or the reverse. Mode=1's D5 lock-key family only marks a write inside one live/shadow window (M5); after that window the difference is permanent.
- **Polygon caches (the I-94-381 hypothesis): no unrecorded refill path found.** The valid byte of a cache level (`[fp+0x38]+n*0x24+0x20`) is cleared in exactly one instruction of the whole image, `0x80E0C8` in `Footprint_InvalidatePolygons 0x80E0B0` [verified scan of every `mov byte [r+r+0x20],0` next to a `+0x38` load]; every fill (W6a `0x80E5B0`, W6b `0x80E610`, W6c `0x80E980`, W6d `0x80EC30`) fills only invalid levels [verified]. `0x80E0B0` has no direct caller and is referenced only as slot `+0x18` of the 9 cache classes [verified]; none of the 65 `[vtable+0x18]` call sites in the routing ranges has a footprint receiver (`0x958643` is the slot-matrix getter of `Transform_GetParentWorld`, 0 live targets in probe pass 2; the rest are script-host, A\*, resource and listener objects) [verified per site; outside the routing ranges inferred, I-156-2]. Since the INS copy and every lot copy force the live caches valid first and copy them (memcpy, not refill), live and clone hold the same points unless `0x80E0B0` runs on an inserted footprint. So the "cache refilled from changed data" path of I-94-381 has no static caller; the obstacle difference of plan 2337 is better explained by U1 or by an unrecorded footprint swap than by a cache refill [inferred, I-156-3].
- **No game writer refreshes an inserted footprint's geometry in place** (relevant to I-94-510): W6d `0x80EC30` (in-place point transform) runs only from `0x80E0E0` (first insert, insert count `+0x34` bits 26-30 going 0 to 1) and `0x80E130` (last remove), i.e. inside W1/W2, and from `PathPlanner_AddHangingFootprint 0x636BF0` (grid add, marked) [verified, docs/94 §21.19.1]; W6f `Footprint_SetLevelPolygons 0x80F6A0` is called only on freshly constructed footprints before their insert, at all six sites (`0x639DE0`, `0x63A1C0`, `0x63CB90`, `0x831710`, `0x831BA0`, `0x8321F0`: constructor, W6f, then `0x6376D0`/`0x62F8A0`+`0x666C50`) [verified call order]. A clone copy "refreshed in place" between an INS and its REM (the I-94-510 residual) therefore has no game-side source of different bounds; if the audit shows the "I-94-510 shape", the source is the replay's own INS reuse (`RpFpCopyInto` on a block clone FMEs still hold) [inferred, I-156-4].
- **The worker writes live footprint caches during a clone run (U3).** Footprints the clone run reaches but does not own (grid records: `PcGridCopy` copies records and polygons, not footprints; request objects) are filled by the worker's W6b when a level is invalid (§22.26.2 log "W6b on a live footprint in a clone run", seen once in each of two BP runs) [verified source; frequency measured]. No clone answer changes (the fill uses the same data the sim would), but it is a write to live routing state from the route worker without `+0x918`, racing the sim's own reads and fills of the same vector [inferred, I-156-5].
- **Everything else the search reads is recorded, copied at the cut, live with a skew rule, drained, or static in play** (§3). Every tree, leaf and map writer is direct-call only (no data reference to `0x665C50`, `0x666750`, `0x6653A0`, `0x666010`, `0x628220`, `0x628F00`, `0x62E680`, `0x62F8A0`, `0x63CB90`) [verified], so no indirect path bypasses the W1/W2/W3/W4/W5 leaves. In-place footprint field setters (slots `+0xCC`, `+0xB0`, `+0xD0`, `+0x4C`, `+0x74`, `+0xA0`, `+0xAC`) are called on routing footprints only at construction sites before the insert, or between a W2 and a W1 (`0x632460` portal-lock flip: remove `0x63257E`, `+0xCC` at `0x63258E`, insert `0x632595`) [verified sites].
- **Ranking and fixes (§4, §5):** U1 first (wrong answer, persists for the session part; fix F1 = 7-byte entry stub on `0x807110` that forces a full rebase of the footprint's lots when the pointer changes on an inserted footprint, ~1-1.5 h); U3 second (live-state race; F3 = the cut forces `+0x70` EnsureAll on every live footprint the clone points at, ~1 h); U2 third (no caller; F2 = per-row W6e counter with a lot force and return-address log in the existing P1 stub, ~30 min). Optional F4: a point hash in `RpLotHash` so the sampled audit sees any remaining polygon difference (~1 h, audit cost).
