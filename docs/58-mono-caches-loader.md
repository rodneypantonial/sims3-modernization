# 58. Mono caches, class init and the loader for a second managed thread (T-MONO-c, input to `[MonoThread]` step 3)

Static analysis only: Ghidra headless on a copy project (copied from the T-MONO-a project, symbols CSV imported first), Steam `TS3W.exe` 1.67, image base `0x400000`. The game was not run. Scope: the lazily filled caches of the embedded Mono 1.2.3 runtime (class, method, vtable, class init, generic and array classes, strings, internal calls, GC handles) and the locks around them, asking for each: who creates and fills it, which lock guards it, and whether the sim thread can fill it in advance so a worker only reads. It builds on docs/29 §5.1 (loader lock), docs/30 §5 (worker entry rules) and docs/56 (per-call globals).

Tags: **[verified]** = read in the disassembly, an operand or immediate scan, or a Mono assert string for this note; **[inferred]** = Mono 1.2.3 source knowledge (`metadata/{class,loader,object,gc,icall,metadata}.c`, `interpreter/interp.c`) matched to the code shape, not confirmed instruction by instruction.

## Method

1. Function profiles (scratch Ghidra script): callers, callees, referenced strings, direct global reads and writes, and every `Enter/LeaveCriticalSection` or `mono_loader_lock`/`unlock` call with the two instructions before it (shows the section pushed).
2. Immediate scans (`tools/ghidra/ScalarRefs.java`) for each critical-section address, to find users that the reference database misses (sections passed as `push imm` or `mov reg, imm`).
3. Lock coverage by address order: for a lazily created global, the write address compared with the lock and unlock call addresses in the same function.
4. The critical-section census of docs/56 §3 (direct `push imm; call [EnterCriticalSection]`), re-read for sections passed in a register.

## Summary

- **Almost every Mono cache is locked.** The class, method, name, array, generic-class and generic-instance caches sit behind the global `loader_mutex` `0x11F43A8` for both lookup and insert [verified: each owner calls `mono_loader_lock` `0xE85020` before its `g_hash_table_lookup` `0xE45F00`]. Vtables sit behind the per-domain lock (`MonoDomain+0`), class constructors behind `type_initialization_section` `0x11F4574` plus a per-class lock, interned strings behind `ldstr_section` `0x11F45A0`, marshal wrappers behind `marshal_mutex` `0x11F43E4`, interpreter `RuntimeMethod`s behind `0x11F4130` [all verified].
- **Three real gaps (no lock at all):** (1) the **GCHandle table** `gc_handles` `0x11959E0`: alloc, free and get run with no lock, and the `handle_section` set up for it (`0x11F42F0`) is initialised and deleted but never entered [verified: immediate scan, only `0xE78DA0` and `0xE78DE0` hold the address]; (2) the **trampoline thunk hash** `0x11F4128` (docs/56), now narrowed: the interpreter calls `tramp_create_thunk` `0xE51400` only when `RuntimeMethod+0x10` is still NULL and caches the result there [verified store after both call sites], so pre-warming each internal-call method removes the worker from it; (3) the **reflection hash** `0x11F46F0`, created after the loader lock is released in all four creators [verified addresses]; reflection stays banned on the worker. Plus the known `mono_stats` counters and `GC_make_descriptor` (docs/56).
- **Two docs/56 rows corrected:** the marshal hash `[0x11F43D8]` is created and filled inside `marshal_mutex` in all three writers [verified addresses], and the interface-id bitmap `[0x11F4264]` is written only from inside `mono_class_init` while it holds the loader lock [verified call-site order] (second path through `0xE6A6A0` under `mono_class_create_from_typedef`'s lock [inferred]).
- **GCHandle lock found (docs/30 §3, docs/56 §3 open item):** it exists but this build never takes it. Two more sections are initialised and never entered: `0x11F44EC` (init `0xE9F810`) and `0x1220FE0` (init in `0xE66240`) [verified immediate scans].
- **Warm-up covers everything a worker needs.** Running each worker method once on the sim thread (docs/30 §5 step 6) creates the vtables, runs the class constructors, transforms the method (which resolves strings, method tokens, internal-call addresses and native wrappers at transform time) and fills `RuntimeMethod+0x10` for internal calls. After that the worker's hot paths are unlocked reads of published pointers or flag bits: `mono_class_vtable` `0xEA2AD0` (runtime-info fast path), `mono_runtime_class_init` `0xEA3370` (`vtable+0x18` bit 1), `mono_class_init` `0xE6EE20` (`class+0x14` bit 0), `mono_method_signature` `0xE85040` and `0xE85390` (cached field checked before the lock) [verified first instructions].
- **Step-3 actions:** worker rule "no `GCHandle`, no weak references" stays (now with a reason: unlocked bitmap `or`/`and`); optional detour that takes the unused `0x11F42F0` around `0xE78780`/`0xE78BF0`; a lock around `0xE51400` is belt and braces only; a Verify-mode check that the worker never enters `0xE85020`, `0xEA1E30`, `0xEA3370` past its fast path, `0xE51400` or `0xE78780`.

## 2. The loader lock `0x11F43A8`

- **What it guards** [verified owners above]: class creation and setup (`0xE6DD30`, `0xE6EE20`, `0xE69F70`, `0xE6A030`, `0xE6A480`), name, method, array and generic caches, method signatures and headers on a miss, the internal-call and JIT-icall hashes, the `runtime_info` store of vtable creation, marshal type info (`0xE92150`) and several marshal builders. 61 functions call the wrappers `0xE85020`/`0xE85030` (docs/29 counted 62 with a different function split); 5 more take it inline (`0xE85040`, `0xE85390`, `0xE85810`, `0xE85CB0`, `0xE85DF0`).
- **Hit paths that still lock** [verified]: `mono_class_from_name`, `mono_get_method_full`, `mono_generic_class_get_class`, `mono_bounded_array_class_get` and `mono_class_create_from_typedef` take the lock even for a cached entry. They are binding-time and transform-time calls, so a warmed worker does not reach them; native code (EA binders, ts3native) that calls them on the worker would serialise with the sim thread and add to the contention measured in docs/29 §5.1.
- **Lock order seen in the code** [verified sequences]: domain lock -> loader lock (`0xEA1E30`); `0x11F4130` -> domain lock (`0xE53070` -> `0xE74CF0`); loader lock -> `marshal_mutex`; `type_initialization_section` -> per-class lock. The Boehm GC lock (P3) is innermost: Mono's GC-aware hashes allocate while holding Mono locks. A worker that holds none of these when it calls managed code cannot add a new order. The one rule: our P3 hooks must never call back into Mono while holding the GC lock.
- **Recursion:** it is a Win32 critical section, so recursive entry on one thread is fine; `0xEA1E30` relies on that (holds the domain lock, `mono_class_init` takes the loader lock, which can call back into vtable creation for a parent) [inferred].

## 3. Missing locks (step-3 list)

| # | State | Writers without a lock | Reached from worker code? | Action |
|---|---|---|---|---|
| 1 | GCHandle table `0x11959E0` | `0xE78780`, `0xE78BF0`, `0xE78C80`, `0xE78D20` (reads in `0xE78A70`, `0xE78AE0`, `0xE78B60`) | only through `GCHandle` / `WeakReference` icalls (`0xE79000`-`0xE790E0`) [verified: no direct callers elsewhere] | rule "no GCHandle, no weak references" (docs/30 §5); optional detour using the dormant `handle_section` `0x11F42F0` |
| 2 | Thunk hash `0x11F4128` | `0xE51400` | first call of an internal-call / P/Invoke method only | warm-up (docs/30 §5 step 6); optional lock; Verify counter |
| 3 | Reflection hash `0x11F46F0` | `0xEAC710`, `0xEB1E60`, `0xEAD420`, `0xEAD5B0` | reflection only | rule stays |
| 4 | Extended GC descriptors (docs/56 §4) | `GC_make_descriptor` `0xE50F90` from vtable creation | vtable creation only (sim thread after warm-up), but a worker collection can run while the sim thread is inside it | P3 detour on `0xE50F90` (docs/56 step 2) |
| 5 | `mono_stats` | many | yes | leave (counts only) |
| 6 | Dormant sections `0x11F44EC` (`0xE9F810`), `0x1220FE0` (`0xE66240`), `0x11F42D4`, `0x11F4314` | initialised, never entered [verified] | unknown role | open: find what Mono 1.2.3 guards with them before step 3 relies on the matching code |

Not missing (checked): the marshal hash `[0x11F43D8]` and the interface-id bitmap `[0x11F4264]` (both locked, §1), the runtime-method hash, interned strings, class init, every image-level cache.

## 4. Effect on `[MonoThread]` step 3

- Keep docs/30 §5 step 6 as the main tool: call every worker method once on the sim thread, with arguments that reach every internal call, array type and generic instantiation the worker will use. Add "every internal-call method" explicitly (fills `RuntimeMethod+0x10`).
- Verify mode (ts3native, worker thread only): count entries into `mono_loader_lock` `0xE85020`, `mono_class_create_runtime_vtable` `0xEA1E30`, `mono_runtime_class_init` `0xEA3370` past its fast exit (`0xEA3382`), `tramp_create_thunk` `0xE51400`, `0xE78780` (GCHandle alloc) and `0xE53070`. Any non-zero count means the warm-up missed a path; the first four are safe but slow or unsafe-by-content (cctor), the last two are races.
- No new lock is required for the first proof (Mode=1, pure managed code on copied input). Locks for #1 and #2 are cheap optional hardening (one critical section each, called rarely).

## 5. Limits

- Lock coverage by address order assumes straight-line flow between the lock and unlock calls; the early-exit unlocks were checked to sit before the stores, but not every branch was traced.
- Names marked [inferred] follow Mono 1.2.3; EA changed this build (thunk table, dormant sections, yield opcode), so confirm before code depends on a name.
- The role of the internal-call stubs at `0xE79000`-`0xE790E0` (which GCHandle method each is) is inferred from the per-type switch; Ghidra has no functions there.
