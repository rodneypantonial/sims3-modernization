## 2. Apex's sites on EA 1.69.47

### 2.1 How Apex finds them, and the list

On any build other than Steam 1.67.2, Apex resolves every game address by signature in its own process memory after the
first Present + 1 s (`GameAddr::Resolve`, `docs/engine/game-versions.md` "How addresses are resolved"), never by a
fixed EA address [verified source]. So the EA site list was rebuilt here from two sources:

- **339 ids from the live 2.17.1 EA log** (one per `[Addr]` line, multi-id lines split). The 2.17.1 -> 3.1.1 table diff
  only adds lines (`git diff v2.17.1 v3.1.1 -- framework/game_addresses.cpp`: +73 / -0) [verified], so these signatures
  and their EA results are the same in 3.1.1 [inferred: same bytes, same rules].
- **36 ids by a scan of the decrypted image** with Apex's rules (unique match, or one value from several; `InRange`,
  `Target`): the 35 ids new in 3.0.0/3.1.1 (GameResolution 4, SceneModel vtables 5, GPU room lamp blockers and test
  constants 16, room probe bind 3, light object attach/move 2, counter config 2, WorldActiveLotGetter, LampLeftMarkCall,
  ProbeAllStages) all resolve; plus RefPackDecompress (below). Scanner check: it re-derives 159 of the old `Sig` ids
  from the image and all 159 equal the 2.17.1 log's EA address [verified].
- **Pattern sites outside the table** [verified scan]: `DelegateSigFix` pattern: 1 hit at `0xD70F92` (Steam `0xD70FB2`),
  its call `0xD70F96` leads to `0xE9DD80`, whose 9 bytes are the `mono_type_get_type` body Apex checks, so on EA
  DelegateSigFix installs when nothing else patched the site (Apex's own comment "EA 1.69.47: unverified" is now
  answered statically). `ScriptMath`: 25 interpreter float-compare handlers `0xE54D6B..0xE58372`, one `_isnan` import
  slot `0x00FDF6C0`, the same count as Steam. `screen_control`'s S3SS limiter pattern: 0 hits in the vanilla image
  (exists only after S3SS patched it; S3SS is not installed on this laptop).

Result: `docs/data/apex-sites-ea169.csv`, **401 rows** = 375 table ids (374 found by Apex's own rules) + 1 DelegateSigFix
+ 25 ScriptMath handlers, each with its Steam address, EA address, source, and our v0.2.10 EA address when it is the
same or within 16 bytes.

### 3.3 C1 on EA: DelegateSigFix vs [MonoSigGuard]

- EA site [verified image]: the delegate check is `0xD70F70` (Steam `0xD70F90`), its only caller `0xD76233` (return
  `0xD76238`, Steam `0xD75FD8`). At `0xD70F92` the 19 bytes equal our `kMsgSite` except the rel32 of the call
  (`E5 CD 12 00`, target `0xE9DD80`, vs Steam `A5 9C 1D 00`); `MSG_CONT` = `0xD70F9B`, `MSG_FAIL` = `0xD70FCB`
  (`5F 32 C0 5E C3`, as on Steam), `MSG_GETTYPE` = `0xE9DD80`. Our 19-byte check with the rel32 masked has exactly one hit, the
  same as Apex's pattern.
- **v0.2.10 EA has no [MonoSigGuard]** (the switch is newer; `monosig.cpp` is on `release/v0.2.11-ea169`, not on the
  hotfix branch) [verified]. With v0.2.10 EA + Apex 3.1.1, Apex's DelegateSigFix alone covers the site.
- With v0.2.11 EA, if the port maps these five constants and carries the EA bytes for the check (ts3bytes row at
  `0xD70F92`, length 19): ours writes first in DllMain (`.text` is decrypted when the asi loads, docs/232 first smoke),
  Apex's pattern then fails and it logs `Delegate check not found in this game build: off`; the same single fix as on
  Steam [inferred until §8]. If the port leaves it unmapped or off, ours logs SKIP (or nothing) and Apex installs at
  `0xD70F96`; still one fix. The queue requires `OK   mono sig guard` and forbids SKIP; drop that pair if the v0.2.11
  EA rc ini turns the switch off (§8).

## 4. Stand-down on EA

### 4.1 Process name: Apex runs only in TS3W.exe or TS3.exe

`apex_main.cpp:257-271` (3.1.1): `IsGameProcess()` accepts only `TS3W.exe` and `TS3.exe`; in any other process DllMain
returns TRUE and does nothing, **without taking its instance mutex** [verified source; the release asi holds the
UTF-16 strings `TS3W.exe` and `TS3.exe` and no `Sims3Launcher.exe`]. 2.17.1 had the same check (returning FALSE).

- **Players** (EA app starts `TS3.exe`): Apex runs; the ASI loader loads `ApexRadiance.asi` before `ts3native.asi`, Apex's
  DllMain takes `Local\ApexRadiance.<pid>`, and our `ApexProbe` sees module + mutex at our DllMain, as on Steam
  [verified source both sides; inferred live].
- **Our EA harness** runs the game as `Sims3Launcher.exe` (TS3.exe copied over the launcher, docs/230; this laptop's
  `TS3_EXE=Sims3Launcher.exe`) [verified env]. The release asi would stay idle there, and our log would correctly say
  `compat: Apex Radiance not loaded at start`: a run that tests nothing. The 2026-11-06 EA runs used a 2-byte test copy
  (`game-copy/apex-2.17.1-eatest`, `xor bl,bl` -> `mov bl,1` after the TS3.exe compare, sha256 `33c89305…`; release
  `cc0ef3a3…`) [verified byte diff; the queue log says "patched Apex"].
- Same patch made for 3.1.1 (Apex is MIT; local test copy only, never shipped or posted):
  `game-copy/apex-3.1.1-eatest/ApexRadiance.asi`, file offset 533936 (0x825B0) `32 DB` -> `B3 01`, sha256
  `1bf3dc2ae973318c…` [verified: the only 2 bytes that differ]. Its version resource stays 3.1.1.0.

### 4.2 Detection and toml [verified source]

- `Local\ApexRadiance.<pid>` and the module names are build-independent; the toml path is
  `<Documents>\Electronic Arts\The Sims 3\Apex Radiance\ApexRadiance.toml` on both editions (Apex 2.17.1 EA log
  `[Main] Files: <Documents>\Electronic Arts\The Sims 3\Apex Radiance\`; ours `UserSims3Dir` + the same suffix).
- The `kApexSwitch` features (ObjectLookupIndex, FastCacheCompression, MemoryGuard, ResourceLookupCache, FileListCache,
  five Lot switches) are all available on EA (§2.2), so the stand-down list is right for EA as it is.
- `[LotPool] Trim`, `[ResourceCache] TrimAfterCleanup`, `[MemDiag] AllocSites` stand down as on Steam (docs/254 R5).

### 4.3 Two EA differences in our code

- **[Verify] probes never stand down on EA** [verified, `origin/hotfix/v0.2.10-ea169`]: `ApexVerifySite`
  (`apex.cpp:128`) compares against Steam literals in `case` labels, while `kVf[].at` is `TS3A(...)`-mapped to EA
  addresses in the EA build (`verify.cpp:66-67`), so it returns 0 for every EA probe. Impact: none in play ([Verify] is
  off in the release and rc ini); with [Verify] on and Apex loaded, both would detour the ObjMap / ResourceCache /
  Lot entries. Fix for the EA port (owner: the v0.2.11 EA lane, not edited here): wrap each case label in `TS3A()`
  (constexpr) or compare against `TS3A` values.
- **[SaveWrite] gives up `0xAB12AF` on EA for nothing**: `SaveWriteYieldToApex(TS3A(0x00AB12AF))` runs when Apex
  MemoryGuard is on, but Apex's early save, the only user of that call, is Steam-only. Cost: the write-phase timing is
  lost on EA with Apex; no behaviour change. Low; could check the exe edition before yielding.
- Log texts name Steam addresses (`call 0xAAC320`, ...) in the EA build: cosmetic.

**Stand-down verdict: OK on EA for players** (detection, toml, switch list, shared sites as on Steam), with the two
low items above. **For the harness only with the eatest copy.**

## 5. RTX Remix bridge on this laptop (Intel iGPU, no NVIDIA)

- This laptop: one adapter, `Intel(R) Graphics`, driver 101.8991; `vulkaninfo --summary` (64-bit) shows an integrated
  GPU with Vulkan 1.4.356, conformance 1.4.0.0 [verified]. It already runs 32-bit DXVK in-process for the game.
- The bridge zip [verified files and strings]: client `d3d9.dll` (32-bit), `.trex\NvRemixBridge.exe` (x64 server),
  `.trex\d3d9vk_x64.dll` (x64, DXVK: `DXVK v3.` string, DXVK class names), two identical `bridge.conf` (sha256
  `9acbee6a…`) with `server.useVanillaDxvk = True`, `dxvk.conf` spoofing vendor `10de` device `1080` to the game. The
  server's strings include `Loading standard Non-RTX DXVK d3d9 dll.` and `Non-RTX standard d3d9vk_x64.dll loaded`.
  Apex's README: "NVIDIA's RTX Remix bridge with patches for The Sims 3, set to plain DXVK (no path tracing)".
- The Remix path-tracing runtime (the part that needs an RTX GPU) is not in the zip; the server loads plain 64-bit DXVK,
  which needs a Vulkan 1.3 device, not NVIDIA. No vendor check appears in the server's strings [verified strings;
  absence of a check inferred].
- **Verdict: bridge arm testable here: yes [inferred]**, proven or refuted in the first minute of the bridge smoke
  (`NvRemixBridge.exe` running, Apex log `d3d9: RTX Remix bridge (DXVK in another process)`, `rtx-remix\logs\bridge64.log`
  device line naming the Intel GPU). Correctness only; iGPU frame rate says nothing about the bridge's cost.
- **targetProcess:** the release notes and README say `client.targetProcess = TS3.exe` for the EA app, which is right
  for players. In our harness the game process is `Sims3Launcher.exe` (§4.1), so with `TS3.exe` the client would not
  bridge [inferred from the setting's purpose; check `bridge32.log`]. Plan: harness runs set `Sims3Launcher.exe` in
  both files; a player-style check with `TS3.exe` needs a real `TS3.exe` launch (open item 3). Rodney decides.
