# 51. Inference ledger (mapping waves, docs/32-50 and 52-62)

Every claim marked [inferred] in docs/32-50 (§3) and docs/52-62 (§3b), plus [verified] static claims that a runtime check should back before a fix depends on them, with how to test each one. Rows that group many alike claims say so. Tags as in AGENTS.md.

## 1. How the rows get a verdict

- **Run:** `node tools/harness/queue.ts tools/harness/queues/verify.json` (two jobs, BP and IP, one load each, ~8 min of play each; 0.10.8: repro `verify-v22`, `minCounters` 22, `ThreadedObjects` 0). Each job loads `game-copy/ts3native.asi.verify` with `[Verify] Enabled=1` and every sub-switch on (`Threads`, `Races`, `Costs`, `Memory`), samples the main thread (`mainstack: "main"`) and runs the `verify-sweep` repro (moodlets, bulk outfit change, CAS open/fill/close, thumbnails + save, camera pan). A job refuses before the game starts when the asi is missing, and after the load when `/native` reports counters older than v21 (`minCounters`). The dump after the load also zeroes the `[Verify]` maxima (`/native?vfresetmax=1`), so the run has a live window.
- **Fill:** `node tools/harness/verify-verdicts.ts --run verify-<date>-bp-verify --run verify-<date>-ip-verify [--write]` reads each job's full `/native` dump (`probe-out/queue/<run>-native.json`) and main-thread stacks (`probe-out/profile/<run>-mainstack.jsonl`), applies the rule column over the live window (counts and `*Us` = after - before, maxima since the reset at load; docs/15 [Verify]) and writes `confirmed` or `refuted` with the numbers into empty verdict cells. `review` rows (no rule, or a rule that cannot decide) stay empty for a human.
- **Static only:** the claim cannot be measured at run time (names, versions, roles of uncalled code, licence facts); it stays open until a decompile settles it. **sampler:** existing samplers in a normal profile run (`simstack`, `managed`); repro mode skips them, so these are not part of verify.json. **fix build:** the claim is the expected gain of a candidate, measured only by building it (A/B).

## 2. vf counter names (contract with the [Verify] module)

The rules match `/native` keys by a target and a suffix: `vf<Group><Target><Suffix>`. Target = the function or global address in hex without `0x` (`D5D910`), or a short token (`Device`, `R1`, `Scene`, `SpeedTree`). Thread-role suffix `Main`, `Sim`, `Other` (`Job*` and `Off` count as Other) for call counts by thread; race keys end in `Race` or `Overlap` (two threads inside the guarded pair or overlap group at once; a key that only contains the word, such as `vfRaceC2A840Calls`, is no race key); cost keys end in `Us`, `Calls`, `MaxUs`; memory keys are `vfMem<Target>Bytes`. Counters are cumulative from game start; the helper takes the live window (after - before) when the dump has both. If the module names keys differently, adjust `keysFor` in `verify-verdicts.ts`, not the ledger.

v22 groups (0.10.8): `vfMono` (Mono warm-up entries, arena, GC_free, managed entries), `vfRt` (docs/60 §2 routing sites), `vfEv` (pump passes, remote calls, script message drain, lot-add context); the thread-slot suffixes are the same.

Rules: `main:T` / `sim:T` (only that role hit T), `offmain:T` (Sim + Other > 0), `both:T` (Main and Sim both > 0), `race:T` (any race key > 0), `max:T<N` / `max:T>N` (largest MaxUs below / above N us; the `>` form since 2026-10-16), `seen:T` (any role key > 0; 0 = review), `none:T/D` (T's role keys 0 while D's > 0; T > 0 refutes), `mem:T<N` (below N MB), `stackmain:A[-B]` (main samples in function A or range A-B), `mainshare:A-B>P` (share of main samples in percent), `roles:T` / `cost:T` (print only). Full list in the script header.
