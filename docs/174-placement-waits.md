## 2. What the sim waits on at F-G

Call path [verified disassembly]: script `World.FindGoodLocation*` -> `IC_World_FindGoodLocation 0x78AE70` / `AtCustomDepth 0x78B0A0` -> `0xB10A30` / `0xB0E130` -> `0xB470C0` -> placement test `0x634F10` (call at `0xB477D3`) -> `LotRouting_FootprintsNearPoint 0x631F10` (call at `0x635013`). `0x634F10` has 4 more callers (`0x63FAB5`, `0x654F7E`, `0x65EDBB`, `0xC73905`); `0x631F10` has one more, `RoutingWorld_ObstacleQuery 0x82EF6D`, which holds `+0x918` itself.

- `0x634F10` = thiscall(lot planner P; lot, x, z, level, radius, record), `ret 0x18`. It builds the same stack context as `0x82EDB0` (vtable `0xFEC0C4`, hash `0x114C900`, `ctx+0x50` = 0) with `ctx+0x40` = its record argument (0 from the FindGoodLocation path, `push 0` at `0xB477AF`) and `ctx+0x54` = the lot, a point `{x, z, level}`, an empty footprint set, mode 1 (`push 1`); it returns `!0x631F10(...)` and only frees the set afterwards (`0x6282F0`).
- `0x631F10` = thiscall(P; ctx, pt, radius, set, mode), `ret 0x14`: no lot or lot id 0 -> 0; `LotTable_Contains 0x628A90` (return `0x631F40` = the wait key) -> 0 if absent; cell graph `0x62FB10`; lot transform `0x62ED40` (gate 0); no cell -> 0; `QueryPoint 0x667480`: flush `0x666A40` when `Q+0x48 < 1`, `Q+0x48` plain +1, walk `0x663E20` with visitor `0x662DD0` (mode 1) into the set, `Q+0x48` -1, return set count != 0.
- **Holder:** the gate-12 leaf is one of `[RouteGate]`'s sites; with `Enforce=1` a sim entry while an async route job runs takes the job's lock `g_async.lock` (= `world+0x918`) with `LockAcquireHook` (`routegate.cpp` `RgEnter`), so the sim waits for the **route worker's async job** until it releases `+0x918` at its end (`J_DONE`) [verified code]. The job holds `+0x918` from its START cut through the plan, the IC tail and the post pass; TailUnlock lends it only to the sim's steering calls during passes 16-19 of the post pass `0x64E380`, and since docs/155 §8 an F-G acquire in an open window is held out (`p5bFgHeldOut`). In this run `p5bFgHeldOut` = 18 [measured]: at least 18 F-G acquires arrived while a job was in its TailUnlock window (post pass, passes 16-19) and then waited for the rest of the job; which of the 18 longest-key iterations they were is not recorded [inferred match]. The ~110 ms per wait matches the remaining hold of a typical IP job (docs/152 §1: the wait is bounded by the job's hold) [inferred].
- **Why `[SlotEnabledRO]` (F-B) does not cover it:** SH is an entry detour on the slot position helper `0x76F0A0`; it opens a QL-shared hold (`t_slHold`) in which `RgEnter` admits that function's own gate-12 / gate-0 leaves (docs/90). F-G is never reached through `0x76F0A0`. Running `0x631F10` itself under QL shared would not be read-only either: its tail pins `Q+0x48` with a plain read-modify-write that the job's own queries also do, and can flush the deferred quadtree inserts (writes, docs/84 §3.4, docs/155 §4). F-G needs a clone of the query, not an admission.

## 3. `[PlacementRO]` (built offline, `native/ts3native/fgro.cpp`)

- **Hook:** one call-site retarget, `0x635013` (`E8` to `0x631F10`, checked first; `PatchCalls`). All five callers of `0x634F10` go through it; `0x82EF6D` and the gate inside `0x631F10` are untouched.
- **When it answers:** sim (async owner) thread, `g_async.state == A_RUNNING`, not the `+0x918` owner (lent or recursive hold), no job callback, no gate frame open (`AvMayRun`), `fgMode` 1.
- **Clone:** `0x631F10`'s early outs (no lot, lot id 0), then under QL shared, try only, with S2's protocol (tripwires armed, `g_qlSeq`, epoch and generation re-checked; obstructro.cpp `OrLocked`): `SrQuery` = `LotTable_Contains` rules, cell graph, transform (bit-exact `SrXform`), the game's walk `0x663E20` with `SrVisit` in place of the collector `0x669CD0` (no pin, no flush, no refcounts), visitor flag 1 (as AvoidRO) and the record's `+0x28` options object (SrCollect bit 2, as RouteToObjRO's gather; `SrQuery` gained a `flagOr` argument). Answer = any footprint collected. The set stays empty; the caller only frees it.
- **Exact or fall through:** QL busy, lot miss, deferred flush pending (`Q+0x4C` with `Q+0x48 < 1`), pin moved during the walk, unknown footprint class, buffer limit, tripwire, job ended during the clone, mode 0 -> the game's `0x631F10` (today's wait), counted in `fgFb[6]`.
- **Shadow** (`fgShadow`, no job running, job starts held off by `g_rgOffSimOpen`): the game's call, then the clone, compared (`fgShadowMismatch` must stay 0).
- **Switches:** ini `[PlacementRO] Enabled=0` (default off), `Mode=1`, `Shadow=0`; runtime `fgMode` +0x42CC (`--ab placementro`, `native_set placementro`), `fgShadow` +0x42D0 (`placementroshadow`). Counters v100 (docs/registry.md), `tools/probe/agent.js` names, `tools/harness/native-switches.ts`, docs/68 row.
- **Selftest** `TestPlacementRO` (`fgro-test.h`, dummies: fake `0x631F10` and fake point query): layout, switch off / other thread pass through, in-job answers 0/1 with the frame's lot, level, point, radius and record, early outs, each fallback reason, `+0x918` owner, job end, QL busy, shadow compare and a skewed shadow. No threaded case: the QL protocol is S2's, covered by the steerro, obstructro and rtoro threaded tests. **Not compiled or run yet** (time rule).

## 5. What removes the freezes

Each read-only or deferred path removes its own key; while a job runs, the next `+0x918` taker in the same tick then waits for the rest of the hold (docs/152 §1, I-152-0; 2-15 waits per freeze iteration here). `[PlacementRO]` alone is therefore expected to move the ~110 ms F-G waits to another key, not to remove the freeze [inferred]. The freeze goes only when every taker of that tick passes (bundle B0 of docs/152 §4: steerro, avoidro, slotenabledro, lotfdro, obstructedro, deferfootprint, destroypark, plus deferfootprint2, gate0ro, routetoobjro and now placementro) or when the hold itself is shorter (FbJobCapMs, PlanDeadline, P5b/P5c). Next measurement after the single-switch check: one IP freeze-measure job with the whole bundle on vs off (`--ab` list), reading publish gaps >= 300 ms.
