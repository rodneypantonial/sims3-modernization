# 203. Thread affinity and spin loops (Mjolnir_IV check)

Written 2026-10-29. Static only: no game run, no build. Inputs: TS3W.exe 1.67 Steam (`game-copy/bin/TS3W.exe`) scanned with Capstone 5 + pefile over `game-copy/analysis/functions.csv` (scratch scripts, not committed); S3SS source `sims3fiend/Sims3SettingsSetter` @5eb2c65 (`cpu_optimization.cpp`, `patches/adaptive_wait_patch.cpp`, `patches/smooth_patch_precise.cpp`); our installed `S3SS.toml` and `S3SS_LOG.txt`; `tools/setup/fixes.json`; `native/ts3native/*.cpp` (read only); the sim-budget run of 2026-10-29 (`probe-out/queue/simbudget-v024-report.txt` and the three `*-simbudget-v024-native.json`). Ledger: docs/51 §388. Tags as in AGENTS.md.

Idea source: Mjolnir_IV for GTA IV (docs/24, idea only). It found (1) the main thread pinned to core 0 with `SetThreadAffinityMask(thread, 1)` and (2) an engine wait loop (`cmp`/`je`, no yield) burning a core, and fixed both (NOP the pin, `SwitchToThread()` in a code cave). This doc checks whether TS3W.exe has either.

## Verdict in short

- **No GTA IV-style pin.** TS3W.exe does not import `SetThreadAffinityMask` at all [verified: import table]. The only affinity writes are `SetProcessAffinityMask` in a startup CPU-topology probe that restores the mask, and a `-SP` command-line switch that pins the whole process to its lowest CPU (not used by default) [verified]. Nothing constrains the sim, main or worker threads in normal play.
- **The sim thread asks for ideal processor 1** (hard-coded in `ScriptThreadService_Init 0x76B610`), the second logical CPU of physical core 0 on an SMT CPU; every other EA thread gets a round-robin ideal processor. Ideal processors are hints, not masks. S3SS `CPUOptimization` passes them through unchanged on the i7-11800H (not hybrid, not AMD) [verified source].
- **No `cmp`/`je` busy-wait in EA code on the hot paths.** The exe has **zero `pause` instructions**, does not import `SwitchToThread`, and the only pure memory-poll loop the scan found is a `switch` default artifact [verified scan]. EA's waits block in the kernel (`EnterCriticalSection`, `WaitForSingleObject`, `Sleep(>=1)`).
- **The spins on this install are added by mods and by us:** S3SS `AdaptiveWait` (on in our install: spins 50-500 us before every blocking `INFINITE` wait in TS3W.exe), S3SS `SmoothPatchPrecise` (QPC busy-wait of up to ~1 ms per tick / per frame, no `pause`, only when ahead of its cap), and our own `[RouteAsync]` worker `Sleep(0)` loop plus the sim's 1 ms lock-pump poll.
- **The sim-budget "other" bucket is not explained by a spin** [inferred]: its top entries are real work (`0x4E5E40` = EA allocator `MallocCore`, `0x4AA1B0` = package index find, `0x67E2B0` = height raycast); in heavy play the sim runs at 46-91 it/s, far under S3SS's 480 TPS cap, so the Precise limiter never waits; S3SS's module is not among the top "other" contributors (each >= 4.5 ms/s on BP). The `ntdll.dll` 62 ms/s stays unattributed (§4).

**Hyper-threading and the laptop.** The i7-11800H runs 45 W with an all-core clock well below its 4.6 GHz single-core boost [community]. A spinning logical CPU costs the sim thread in two ways: on its SMT sibling it takes issue slots (a QPC loop without `pause`, S2/S3, is worst; `pause` loops, S1, take fewer), and anywhere on the package it spends the shared power/thermal budget, lowering the clock the sim core can hold. Both are [inferred]; neither shows in the sim-budget buckets, which measure time, not clock. The machine load line in `*-machine.jsonl` gives the clock per run.

## 3. Patch designs for the best candidates

### C1. S3SS AdaptiveWait off (A/B, config only)

- **Change:** `[patches.AdaptiveWait] enabled = false` in `S3SS.toml` for one arm. No code. If it wins or is neutral, set it off in `tools/setup/fixes.json` (`optionalPatches.AdaptiveWait`), done by whoever owns setup.
- **Why it may help [inferred]:** it spins on idle EA job threads and every blocking EA wait; on a 45 W laptop that spends package power the sim core could use, and on core 0 it can land on the sim thread's sibling (ideal 1). **Why it may hurt:** a short sim wait for a JobManager job wakes later without the spin (kernel wake ~5-50 us with the 1 ms timer).
- **Expected [inferred]:** process CPU -2..-30% of one logical CPU; sim it/s 0..+3% on a thermally limited run, ~0 on a cool one; p99 hitch unchanged.
- **Measure:** one queue, 2 arms x 2 orders x 10 min, BP + IP (natural play), plus a 5 min smoke that reads the arm back from `S3SS_LOG.txt` (the patch list line). Per-thread CPU: `typeperf "\Thread(TS3W*)\% Processor Time" "\Thread(TS3W*)\ID Thread" -si 1` alongside the run (no code), or later a ts3native probe that samples `QueryThreadCycleTime` for every thread once per second (counters per thread name). Also process CPU, CPU clock from the machine load line, sim it/s, `hitch-ab.ts` p99/p99.9. Gate: AGENTS.md A/B rules.

### C2. Event-driven route waits (ours)

- **Change (ts3native, later, not now):** (a) the worker's job-start loop waits on an auto-reset event `g_rgOffSimEv`, set by the sim when `g_rgOffSimOpen` drops to 0 (and by `G0wDrop`), with a 1 ms timeout as a safety net instead of `Sleep(0)`; (b) the sim's lock pump adds a third handle, `g_rgReleasedEv`, set by our `Lock_Release` hook (`g_rgRelOrig` callers, P5b retake/lend, replay consumer) whenever `+0x918` goes free while `g_rgOffSimOpen > 0`. Same pattern for the S10 loops if those paths ship.
- **Expected [inferred]:** worker CPU -30..-90 ms/s while jobs queue; sim lock-wait latency -0.5..-1 ms per pump wait that ends by a non-job release, ~-5..-15 ms/s of sim time on BP (an upper bound: most pump waits end on `asyncDone`, which already wakes the pump at once).
- **Counters (reserve `native` slots first, docs/registry.md):** `pumpWakes` (WFMO returns per wait), `pumpRelLatUs` (QPC from release to the pump's successful acquire), `workerSpinUs` / `workerSpins` (today's `Sleep(0)` loop time and iterations, as a probe build before the fix). The probe alone tells whether C2 is worth building: if `pumpRelLatUs` < 2 ms/s and `workerSpinUs` < 20 ms/s, drop it.
- **Measure:** loop repro (`route-ownjob-yield-loop` or the IP crowd repro) with the probe, then `--ab` runtime switch in one load (memory: bundle testing), sim it/s + per-thread CPU as in C1.

### C3. Sim thread placement (probe first)

- **Probe (ts3native, later):** once per second read `GetThreadIdealProcessorEx` and the current processor of the sim, main, `JobThread0/5`, route worker and replay consumer (`GetCurrentProcessorNumberEx` in their own hooks, or the thread's context in a sampler), and from `GetLogicalProcessorInformationEx` which logical CPUs share a core. Report: share of sim samples whose SMT sibling was running one of our busy threads, and the sim's processor migrations per second.
- **Change if the probe shows sharing:** set the sim thread's ideal processor to the first logical CPU of a core other than core 0, and give the busy helper threads (route worker, replay consumer, `JobThread0`) a CPU set (`SetThreadSelectedCpuSets`) that excludes both logical CPUs of that core. No hard affinity masks (the scheduler must still move the sim away from a busy core).
- **Expected [inferred]:** 0..+5% sim it/s when sharing was measurable, 0 otherwise.

## 6. C2 part (a) built: `[RouteAsync] WorkerWait` (ts3native 0.36.124, off, not run)

- **What:** the S5 job-start wait moved into `RwStartWait` (ts3native.cpp). `WorkerWait=0` keeps the `Sleep(0)` loop. `WorkerWait=1` keeps the `Sleep(0)` loop for 50 us (short blockers: RO answers, gate leaves), then parks on the auto-reset event `g_rwWakeEv`. Every `g_rgOffSimOpen` decrement goes through `RgOffSimDrop` (21 sites in 15 files), which sets the event when the count reaches 0 and a worker is parked. The three `g_g0Win` clears in locowin.cpp (`G0wDrop`, pass end, `HxClose`) call `RwWake` too. The wait has a 1 ms timeout as a safety net, which also covers the H2 250 ms watchdog. This is the wait docs/203 §2 measured. The idle wait for new jobs (`WorkerMain`, `WaitForMultipleObjects` on `g_jobReady`/`g_asyncReady`, `INFINITE`) was already event-driven [verified code]. Part (b), the pump's release event, is not built.
- **No lost wake-up:** the worker publishes `g_rwParked` and then reads both blockers again before it waits. A dropper clears its blocker and then reads `g_rwParked`. Both steps are interlocked (full barriers), which is the Dekker pattern. Selftest `TestRouteWorkerWait` (rwait-test.h) checks four things. First, mode 0 counts. Second, it runs 4,000 rounds of two droppers with mixed hold times (0-20 us, 40-70 us around the spin edge, 100-400 us) while the safety timeout is raised to 2 s, and asserts `rwTimeouts == 0` (every park ended by a signal). Third, the H2 window clear wakes a parked worker. Fourth, a dropper that skips `RwWake` still frees the worker through the 1 ms timeout, so no path can hang the worker. The worker is not joined at detach, before or after this change: process exit ends it.
- **Counters v142 (`rw*`, docs/registry.md):** `rwBlocked`, `rwBlockUs`, `rwSleep0` and `rwMaxBlockUs` count in both modes, so the off arm measures today's loop. `rwSpinExits`, `rwWaits`, `rwWakes`, `rwTimeouts` and `rwSignals` count only in mode 1. The runtime switch is `workerwait` (+0x54B0), used as `--ab workerwait`.
- **Expected [inferred, not measured]:** in mode 1, worker CPU drops by about the blocked time minus the spin share. That is up to ~74 ms/s on BP and ~81 ms/s on IP. Job start latency gets worse by 0 to ~15 us per park (event wake-up) and stays unchanged for blockers under 50 us. Sim waits behind jobs should not change. **Effect on the Mono worker:** `[AutShadow]` scores on its own thread. The busy loop holds a logical CPU, and on the i7-11800H that can be the SMT sibling of the core the AutShadow worker or the sim runs on. Freeing it should leave the AutShadow worker more core time and turbo headroom when the route worker is blocked, and so fewer AutShadow overruns (docs/122 §14). Treat this as inferred until `route-worker-wait.json` reports per-thread CPU and a Mono cost run compares overruns with the switch on and off.
- **Queue:** `tools/harness/queues/route-worker-wait.json` (not run). It runs a 5 min smoke (switch read-back, arm split) and then BP + IP `--ab workerwait` 10 min with per-thread CPU. Judge it on `rwBlockUs` vs worker thread CPU per arm, job start latency (`rwMaxBlockUs`, `asyncPumpUs`), sim job waits (`sw*`) and hitch counts (`hitch-ab.ts`).
