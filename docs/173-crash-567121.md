## 2. What 0x00567121 does [verified: disassembly + registers]

`0x5670A0` (no symbol yet; working name `SequenceController_OnTrackFinished`) is listener slot 0 of an animation SequenceController. Its `this` is the controller + `0x28`.

- **Constructor:** `0x5674B9` sets the list anchor at controller `+0x30` to itself (next and prev). It then stores `mov [esi+0x38], 0xFC1A78`, a pointer to the EASTL allocator name `"Animation/SequenceController/NodeList"`.
- **Node layout:** `+0` next, `+4` prev, `+8` refcounted object pointer, `+0xC` key (track), `+0x10` flags, `+0x14`/`+0x18` floats.

The function works in three steps:
1. `0x5670BB`: it returns if the list is empty. Otherwise it looks for a node whose key is the finished track (`arg1` = `ebp` = `0x58965620`) and whose flag 4 is set, and returns if there is none.
2. `0x5670EF`: it clears flag 4 on every node with that key.
3. `0x567103` loop: it takes the first node.
   - If key == track and flag 2 is set, it goes to `0x5671BF`, which handles the node and ends.
   - Otherwise it unlinks the node, frees it (`0x4E3F70`) and calls `0x566650(ctrl, 1)`. That call stops the node's track if flag 2 is clear (`0x576D00`), removes the listener (`0x576D40`), calls `obj->vtable[+4]` and releases the object. Then the loop runs again.
   - **The loop never checks for an empty list.**

Step 3 assumes that a node with key == track and flag 2 is still in the list. When none is left, the loop pops every node, then reads the anchor as if it were a node:

- `eax = [edi] + 8` = anchor + 8 = `0x39473D28`
- `ecx = [eax]` = the allocator-name slot = `0x00FC1A78`
- `0x567121 add dword ptr [ecx+4], 1`, the refcount bump, writes to `0x00FC1A7C`.

The registers match this exactly:
- `edi` `0x39473D20` = anchor
- `ebx` `0x39473CF0` = controller = `edi - 0x30`
- `eax` = `edi + 8`
- `ecx` `0x00FC1A78`
- `ebp` = track `0x58965620`

The stack slots just below `esp` still hold the last `0x566650` call frame (`0x567190`, `0x39473CF0`, `1`). So the loop had just popped a node and run its callback.

**0x00FC1A7C is in `.rdata`**, 4 bytes into the string `"Animation/SequenceController/NodeList"` (`0xFC1A78`). That string is next to `".../TemporaryNodeList"` at `0xFC1A60`, and its only code reference is the constructor at `0x5674BC`. The faulting write is the game's own refcount increment on a pointer that the game's own constructor stored. The pointer is not a corrupted pointer, not a freed or recycled object (the anchor and the name slot are intact), and not a redirected call.

## 5. Causes, most likely first

The house rule applies: our build crashed, so the cause is our bug until proven otherwise.

1. **Changed game state reaches an EA invariant that is not guarded.** Our behaviour switches leave a SequenceController where a track finishes with a flag-4 node but no flag-2 node for that track. EA's loop then drains the list. The prime suspects drive Sim route-follow and locomotion, whose clips are queued per actor:
   - `ReplanDedupe` (serving; a replan answered from the dedupe cache instead of a new plan)
   - `[UnseenThrottle]`
   - `FallbackAsync` (async plans finish on later ticks)
   - the ts3fixes `legreplanskip` and `bouncerskip`

   The last two hitches were route-follow tasks. [inferred; the crash mechanism is verified, the trigger is not]
2. **Re-entry inside the loop.** `0x566650` calls `obj->vtable[+4]` and the object destructors while the loop runs. If such a callback removes the target node from this controller, the drain follows. This would be an EA latent bug that our timing exposes more often. [inferred]
3. **Cross-thread change of the list or the refcounts** by a worker: route jobs, decompress, or the slot RO thread. This is unlikely:
   - the anchor and the name slot are clean, with no torn pointers;
   - the routing worker closures (docs/60, docs/93) do not reach animation.

   [inferred]
4. **Profiler Frida hooks** (stage hooks on `0x571AD0`/`0x571B90`, task hooks, CModule). They time function entry and exit and read nothing in this list. They are the lowest-ranked cause and would only matter through timing. [inferred]

Refuted:
- a corrupted pointer or a freed object (§2) [verified];
- a ts3native detour or patch on this path: none of the detours in log lines 19-83 is in `0x565000-0x578000` or on the chain, and docs/68 lists no S3SS or S3PP site there [verified for ts3native, by docs for S3SS/S3PP];
- PlanDeadline and FailMemo (off, §1) [verified];
- ForegroundRender: its main-thread sites `0xECA9E2`/`0xEC9FD1` are on the other thread [verified thread].

## 6. Cheapest next step

1. **One exact rerun of `bp-profcost-on-2`** (same save, seed 12345, same switches), as a correctness run with no timing value. If it crashes at the same place again, the bug is deterministic, and the bisect below can use the same run. If it does not crash, it is rare (1 in 3 so far: off-1 and on-1 passed).
2. **Split run:** turn off `ReplanDedupe` and `[UnseenThrottle]` (the two native switches that change route-follow and locomotion state) and keep everything else, profiler included. Then turn off the ts3fixes `legreplanskip`/`bouncerskip` in a second run. Turning off the profiler stage hooks is the off-job setup, so `bp-profcost-off-2` already covers it.

## 7. EA hang 2026-11-24: the same state as a freeze, and the `[SeqWatch]` detector (2026-11-25)

Job `ip-ubrel-hbstart-repro-rc1119` (queue `release-verify-rc1119-door-m1124d2-ea`, EA app 1.69.47, asi 0.36.305-eam1124d2) froze after three `sim_go_home` sends; the harness dumped the game (`probe-out/dumps/ts3w-42520-20261124T155959.dmp`, local only). ### 7.1 What the dump shows

- **EA addresses of the chain** [verified: `tools/sigmap.ts` gen on Steam 1.67 + match on the decrypted EA image `probe-out/ts3-ea169.bin`, every site unique; the EA bytes at the loop and the drop call read by hand]: `0x5670A0` -> EA `0x566C40` (same body, shift -0x460), loop head `0x567103` -> `0x566CA3`, `0x567121` -> `0x566CC1`, drop call `0x56718B` -> `0x566D2B` (`E8` to `0x5661F0` = Steam `0x566650`), its return `0x567190` -> `0x566D30`, listener dispatch `0x576B30` -> `0x5765A0` (return `0x5765CE`), end-of-pass drain `0x577060` -> `0x576A70`, `0x571B90` -> `0x5714C0`, pose call `0x571C3C` -> `0x57156C`, `0x940430` -> `0x9409D0`, pass call `0xD81C73` -> `0xD82033`, time step `0x942C00` -> `0x9431A0`, controller constructor store `0x5674B9` -> `0x567059`. The `[UnseenAnim]` rows of `ts3addr-ea169.h` / `ts3bytes-ea169.h` agree with these: the EA port of the pass hook is not the cause.
- **The sim thread is inside a drop call of the node loop** [verified: return address `0x566D30` at sim esp+0x308, its frame read from the dump]: arguments controller `0x28B0CA30`, stop 1; the caller frame holds the listener `this` = controller + 0x28 and the finished track `0x24485B50` (OnTrackFinished's arg 1, at loop esp+0x30 = the node copy + 0x18); the node copy is already cleared by `0x566650`.
- **The controller's list is empty** [verified]: anchor `0x28B0CA60` points at itself (next and prev), refcount 2, name slot `0x100BCA0` = `"Animation/SequenceController/NodeList"` in `.rdata` (PAGE_READONLY in the dump). So the dropped node was the last one and no (key == track, flag 2) node is left: when the call returns, the loop reads the anchor as a node and bumps a refcount in `.rdata`, the `0x567121` access violation of §2 (EA `0x566CC1`). The freeze comes first.
- **The drop call never returned** [return addresses verified; which of them are live frames is inferred from a stack scan]: `0x566281` (EA; = Steam `0x5666E1`, after `call [obj->vtable+4]` of the dropped node's object), then `0x565800`, `0x56552D` / `0x56E06D` three levels deep (a recursive teardown of nested sequence nodes), the allocator (`0x4E41D4`, `0x4E5BB4`), `0x852650`, `0x85133C`, `0x846FDE`, `0x84EE5F`, `0x83D085`, `0x83C709`, and the sampled eip `0x568F12` (a refcounted pointer setter at actor `+0x5D8`, EA `0x568EF0`). The other sample (`0x5770C8`) is a small getter. Both are leaves of a busy thread, not the spinning loop itself; which loop spins is not known from one dump.

### 7.2 Can `[UnseenAnim]` hand the node loop an empty or changing list?

Not directly [verified, `unseenanim.cpp`]: it never touches tracks, controllers, listeners or the drain. It only (a) skips EA's own pose call `0x940430` for an unseen Sim's actor and (b) later passes the summed dt (here up to max(250 ms, 4 x pass dt), never above 1.5 s) to EA's pose call for the same live actor in EA's walk. The slot keeps an actor pointer, the owner id and the owed time, and is never dereferenced on its own.

Indirectly, one path is plausible [inferred, I-610-1]: a Sim that owed time and is then placed in a boat (`boattrip: place: BoatSpeedBoat`, the last feature line) gets a parent hold (`AAH_PARENT`): the whole debt is paid in one pose call right after the placement rebuilt its sequences. A large dt can finish several tracks in one call; the end-of-pass drain then reports finishes for a controller whose nodes were already replaced, which is the "flag-4 node, no flag-2 node" condition of §2. Against it: the same state crashed a Steam run on 2026-10-22 (§1-§5), ten days before `[UnseenAnim]` existed (0.36.153, 2026-11-02), and the Steam copy of this job passed 7 of 7 with the same switch. So the state is EA's own unguarded loop (§5 cause 2: a drop callback that empties or edits the list), and our switches at most change how often it is reached. Confidence in the `[UnseenAnim]` trigger: low.

Debt tear-down paths and what covers them (the no-gaps rule) [verified, `unseenanim.cpp`]:

| Path | Debt | Counter / line |
|---|---|---|
| actor destroyed or leaves the list (Sim reset, delete, travel, lot unload) | never paid (EA only poses live actors); dropped after 2 x Every passes | `aaStale` (main counters), no line |
| same address, another Sim | dropped | new `aaReuse` + `seq watch: unseen anim reuse-drop` |
| same actor, new TrackManager (rig rebuilt) | paid to the new TrackManager | new `aaRigChg` + `rig-changed` line (log only: not dropped) |
| same actor, sequence replaced at a parent hold (boat / vehicle / horse placement, carried) | paid in one call | new `aaOwedPar` + `owed-parented` line (log only) |
| same actor and TrackManager, sequence replaced without a parent (teleport, interaction cancel, reset in place) | paid in one call | **gap**: no sequence epoch is known on the actor; not detected |
| world load / unload (new actor list) | table cleared | `aaSlotReset` |
| switch off | flushed | `aaFlushOff` |

### 7.3 `[SeqWatch]` (built 2026-11-25, 0.36.305-eam1124d2hbdet, log only, default off)

`[SeqWatch] Enabled=1` retargets the drop call at `0x56718B` (EA `0x566D2B`) to `SqDropThunk`, which always calls EA's `0x566650` with the same arguments. Before the call it checks the controller's anchor (controller + 0x30): if the list is empty, the loop will read the anchor next (`emptyNext`). It counts drops per (controller, track) per nesting level (`longLoops` at `IterN`, default 10000) and keeps the nesting depth, the deepest nesting and the current controller / track in the export, so a hang capture shows them. One report per controller (64 controllers, 64 lines a session):

- `seq watch: list empty before the drop (loop reads its anchor next): controller C track T, dropped node key K flags F obj O (vtbl V), stop S, depth D, run R; [UnseenAnim] on|off pass P, N owed pays this pass; ...`, then `  seq watch: controller ...` / `track ...` hex lines and the last 8 `[UnseenAnim]` events (`  seq watch: aa event -i: ...`).
- `seq watch: long drop run: ...` (same fields).
- `seq watch: unseen anim reuse-drop | rig-changed | owed-parented: actor A Sim H:L owed U us, TrackManager X -> Y, pass P`. The three counters count always; the TrackManager read (and so `rig-changed`) and the lines need `[SeqWatch]` on.

The controller -> Sim link is not known (no verified field), so the line names the Sims that were paid owed time in the same pass instead.

Export `ts3native_seqwatch` (own block, not in `Ts3nCounters`, docs/registry.md): `version` 1, `on`, `iterN`, `calls`, `emptyNext`, `longLoops`, `depthMax`, `depth`, `curCtrl`, `curTrack`, `lines`, `aaReuse`, `aaRigChg`, `aaOwedPar`. Retail 1.67 has no rows for the two sites (0 = SKIP).

No guard was built: the empty list is proven, but the freeze is inside the last drop's own teardown, which an empty-list check at the loop head would not reach, and the trigger is not proven. A guard waits for the detector run.
