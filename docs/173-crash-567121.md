## 2. What 0x00567121 does [verified: disassembly + registers]

`0x5670A0` (no symbol yet; working name `SequenceController_OnTrackFinished`) is listener slot 0 of an animation SequenceController. Its `this` is the controller + `0x28`.

- **Constructor:** `0x5674B9` sets the list anchor at controller `+0x30` to itself (next and prev). It then stores `mov [esi+0x38], 0xFC1A78`, a pointer to the EASTL allocator name `"Animation/SequenceController/NodeList"`.
- **Node layout:** `+0` next, `+4` prev, `+8` refcounted object pointer, `+0xC` key (track), `+0x10` flags, `+0x14`/`+0x18` floats.

The function works in three steps:
1. `0x5670BB`: it returns if the list is empty. Otherwise it looks for a node whose key is the finished track (`arg1` = `ebp` = `0x58965620`) and whose flag 4 is set, and returns if there is none.
2. `0x5670EF`: it clears flag 4 on every node with that key.
3. `0x567103` loop: it takes the first node.
   - If key == track and flag 2 is set, it goes to `0x5671BF`, which handles the node and ends.
   - Otherwise it unlinks the node, frees it (`0x4E3F70`) and calls `0x566650(ctrl, 1)`. That call stops the node's track if flag 2 is clear (`0x576D00`), removes the listener (`0x576D40`), calls `obj->vtable[+4]` and releases the object. Then the loop runs again.
   - **The loop never checks for an empty list.**

Step 3 assumes that a node with key == track and flag 2 is still in the list. When none is left, the loop pops every node, then reads the anchor as if it were a node:

- `eax = [edi] + 8` = anchor + 8 = `0x39473D28`
- `ecx = [eax]` = the allocator-name slot = `0x00FC1A78`
- `0x567121 add dword ptr [ecx+4], 1`, the refcount bump, writes to `0x00FC1A7C`.

The registers match this exactly:
- `edi` `0x39473D20` = anchor
- `ebx` `0x39473CF0` = controller = `edi - 0x30`
- `eax` = `edi + 8`
- `ecx` `0x00FC1A78`
- `ebp` = track `0x58965620`

The stack slots just below `esp` still hold the last `0x566650` call frame (`0x567190`, `0x39473CF0`, `1`). So the loop had just popped a node and run its callback.

**0x00FC1A7C is in `.rdata`**, 4 bytes into the string `"Animation/SequenceController/NodeList"` (`0xFC1A78`). That string is next to `".../TemporaryNodeList"` at `0xFC1A60`, and its only code reference is the constructor at `0x5674BC`. The faulting write is the game's own refcount increment on a pointer that the game's own constructor stored. The pointer is not a corrupted pointer, not a freed or recycled object (the anchor and the name slot are intact), and not a redirected call.

## 5. Causes, most likely first

The house rule applies: our build crashed, so the cause is our bug until proven otherwise.

1. **Changed game state reaches an EA invariant that is not guarded.** Our behaviour switches leave a SequenceController where a track finishes with a flag-4 node but no flag-2 node for that track. EA's loop then drains the list. The prime suspects drive Sim route-follow and locomotion, whose clips are queued per actor:
   - `ReplanDedupe` (serving; a replan answered from the dedupe cache instead of a new plan)
   - `[UnseenThrottle]`
   - `FallbackAsync` (async plans finish on later ticks)
   - the ts3fixes `legreplanskip` and `bouncerskip`

   The last two hitches were route-follow tasks. [inferred; the crash mechanism is verified, the trigger is not]
2. **Re-entry inside the loop.** `0x566650` calls `obj->vtable[+4]` and the object destructors while the loop runs. If such a callback removes the target node from this controller, the drain follows. This would be an EA latent bug that our timing exposes more often. [inferred]
3. **Cross-thread change of the list or the refcounts** by a worker: route jobs, decompress, or the slot RO thread. This is unlikely:
   - the anchor and the name slot are clean, with no torn pointers;
   - the routing worker closures (docs/60, docs/93) do not reach animation.

   [inferred]
4. **Profiler Frida hooks** (stage hooks on `0x571AD0`/`0x571B90`, task hooks, CModule). They time function entry and exit and read nothing in this list. They are the lowest-ranked cause and would only matter through timing. [inferred]

Refuted:
- a corrupted pointer or a freed object (§2) [verified];
- a ts3native detour or patch on this path: none of the detours in log lines 19-83 is in `0x565000-0x578000` or on the chain, and docs/68 lists no S3SS or S3PP site there [verified for ts3native, by docs for S3SS/S3PP];
- PlanDeadline and FailMemo (off, §1) [verified];
- ForegroundRender: its main-thread sites `0xECA9E2`/`0xEC9FD1` are on the other thread [verified thread].

## 6. Cheapest next step

1. **One exact rerun of `bp-profcost-on-2`** (same save, seed 12345, same switches), as a correctness run with no timing value. If it crashes at the same place again, the bug is deterministic, and the bisect below can use the same run. If it does not crash, it is rare (1 in 3 so far: off-1 and on-1 passed).
2. **Split run:** turn off `ReplanDedupe` and `[UnseenThrottle]` (the two native switches that change route-follow and locomotion state) and keep everything else, profiler included. Then turn off the ts3fixes `legreplanskip`/`bouncerskip` in a second run. Turning off the profiler stage hooks is the off-job setup, so `bp-profcost-off-2` already covers it.
3. **Optional safety net, not a fix:** a guarded clone of the `0x567103` loop with an empty-list check, logged as a counter. It would hide the trigger, so add it only after step 2 names the owner.
