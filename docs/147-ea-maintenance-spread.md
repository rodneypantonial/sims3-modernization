## 2. Venue cleanup (`easpreadlots`, built)

**What runs** [verified]: at 3:00 one global alarm (`InitVenueMaintenance`, the only caller) walks every lot: lots the active household cannot treat as home and does not control, and base-camp lots, get a magic clean-up with repairs (off the world lot) and their household fridge emptied; lots with virtual residential slots get the clean-up only; the rest only change season. Every lot that is not a bar resets its velvet ropes. Then every actor: NPCs get their inventory seeded and vampire fruit, and every Sim gets a stuck-check alarm (`RunStuckCheckHelper.Init`, 20-60 sim-minutes later). Last, the day's autonomy hot spots and dead zones are chosen. The active Sim is read once, when the alarm fires. All of it runs in one alarm tick.

**Fix** (`mods/ts3fixes/src/EaSpread.cs`, switch `easpreadlots`, tuning `kEaSpreadLots`, default off): the alarm callback is swapped (same header-swap as every hook); on, it captures the active Sim and starts our one-shot task, which does the same per-lot step for a snapshot of the lots (at most 4 lots or 2 ms per tick), then the same per-Sim step for a snapshot of the actors taken after the lots (16 Sims or 2 ms), then the hot-spot choice. Destroyed lots and Sims are skipped; one step that throws is counted and the pass goes on (EA's loop would end there). World unloading ends the pass (`stopped`). A second alarm while a pass still runs (cannot happen within a sim-day, guard only) takes the game's own path.

**Same results:** same predicates in the same order, same game calls per lot and per Sim, the active Sim from the alarm tick [verified by reading]. Differences: the last lot is cleaned some ticks after 3:00, and the stuck-check alarms are armed with the Sim positions of that moment instead of the alarm tick's [inferred harmless: the check compares the position 20-60 minutes later with the one stored].

**Verify:** `easpreadlotsverify` logs, on either path, the lots per kind and a census of objects the clean-up would still clean (not in use) on the lots it cleans, before and after. Both paths should end at the same "after" (left: lots with active jobs, objects in use) [inferred]. Repro `bp-easpread-lots` runs the game's path, then ours, through `Fixes.EaSpreadNow("lots")` (a one-minute alarm, the same context as the real alarm).

**Risks:** a save during the pass sees some lots cleaned and some not (as with any alarm that has not fired); NRaas StoryProgression disables this alarm and runs its own per-lot scenario instead (then our hook never fires) [verified in docs/145 §6].

### 2.1 Units inside a lot (2026-10-21, after the rc-first run)

**Seen** [measured]: rc-first `bp-easpread-lots-repro`: same result as the game (cleaned 82 / season 1, verify after 0) in 37-39 ticks, but the longest tick 4.1-5.8 ms against the 2 ms budget: the budget was checked between lots, and one lot's `MagicallyCleanUp` (its objects-to-clean query over every lot object, the clean-up of each, repairs over every object) ran inside one check.

**Fix** (Rodney's rule: the budget counts the work items inside an object): each lot's work is a list of units built at its turn, and a tick ends after 64 units or 2 ms, resuming at the next unit of the same lot (`DailyPairPass` over lots, `EaSpreadCore.AddFindThenAct`). `MagicallyCleanUp(repair)` is opened up into the game's own steps in its order [verified by reading `Lot.MagicallyCleanUp` / `RepairAllObjects` / `MagicallyChangeSeason`]: dive-lot list cleanup and the active-jobs check (a lot with active jobs is left alone, as the game does); one unit per lot object running the game's predicate `Lot.DoesObjectNeedCleaning` (the object list read at the lot's turn, where the game queries it), then one unit per found object running the game's per-object body (in use skipped, force clean, snack bowls refilled, trash thrown away, books shelved / to the family inventory / faded out, destroy-on-cleanup objects faded out); fire restore, puddles, burnt tiles and unconscious cat prey (one unit); one unit per object for repairs (charred cleared, windows replaced, broken repaired); the season kick (the lot's own timer with its private callback `ChangeSeason` and field `mGoHomeForSeasonChangeTimer`, by reflection; missing = `easpreadlots` off). Fridge and velvet ropes are a unit each. An object destroyed between its find and act units is skipped. Differences [inferred, small]: the repair units use the object list read at the lot's turn (the game reads it again after the clean-up, so an object created by the clean-up itself is not repaired by ours); `home` for puddles is read at the lot's first unit, not after the find. Counter [209] `easpread_lots_max_units_tick`; [181] stays the longest tick. Expected longest tick ~2-3 ms (one object's step over the cap at most) [inferred].

**Selftest:** a lot of 1,000 objects (every third dirty) and two small lots, 64 units per slice: >= 31 slices, the found set = the predicate's, every found object still there cleaned exactly once in list order, objects destroyed mid-split (after the find phase, before their act) never touched, no slice over budget.

## 3. Pet pool alarm (`easpreadpets`, built)

**What runs** [verified]: the alarm clears its handle, returns when every pool is full, else picks a pool type, builds one pet with that type's creator and adds it, then re-arms (5 or 30 sim-minutes). The builder for cats, dogs and horses (`GeneticsPet.MakeRandomPet`) randomizes the pet (`CASLogic.RandomizePet`: a part search over every CAS part, ears, eye colour, missing parts, preset blends, coat), then builds the outfit; between the outfit steps it calls its own `SleepIfPossible`, which sleeps only when the caller may yield. An alarm may not, so today the whole build is one tick.

**Fix** (switch `easpreadpets`, tuning `kEaSpreadPets`, default off): the alarm runs the game's own `AlarmCallBack` unchanged inside our one-shot task. Nothing else changes: EA's sleep points now split the outfit steps over ticks (3 + one per extra outfit category for cats/dogs/horses). A second alarm while a build is still running takes the game's path (counter `busy`).

**Same results:** the same method body runs [verified]; only its sleep points become active. The pool alarm handle stays the fired one until our task clears it (a tick later); `StartAlarm` from elsewhere in that tick sees a handle and does not arm, and our task re-arms at its end, as the game does [verified by reading].

**Est. saving / limit:** `RandomizePet` has no sleep point and holds 15 of 19 samples [measured], so the pet frame shrinks by the outfit part only (~20%) [inferred]. A bigger cut needs `RandomizePet` sliced (its part-search loop over every CAS part) or a pre-built pet per pool type; both rewrite EA's randomizer and are not built.

**Verify:** each path logs the pets in all pools before and after; ours logs the ticks used. Repro `bp-easpread-pets`: `petbuild` (one stray cat through the pool's own creator, then disposed; works with full pools) on the game's path (1 tick) and ours (> 1 tick), then the real alarm.

### 3.1 Duplicate alarm chain (found live 2026-10-21, fixed)

**Seen:** in `rc-first-2026-10-21-bp-easpread-pets-repro`, `pet pool alarm (ours)` fired once per ~30 sim-minutes until simmin 21983, then twice per period, 2-3 sim-minutes apart (21983/21986, 22014/22016, ...) [measured]. The doubling starts at the repro's third step, `EaSpreadNow("pets")` (04:00:57 UTC; ~9.5 sim-minutes per second at that point puts its fire at ~21980) [measured from the step log and the simmin stamps].

**Cause** [verified by reading `PetPoolManager` and our trigger]: the pool keeps one alarm handle (`sPoolAlarm`). The callback clears the handle (without removing an alarm still pending under it), builds, and re-arms only when the handle is clear. Our trigger called the callback out of schedule while the real alarm was pending: the handle was cleared, the callback armed a new alarm, and the old one still fired 2-3 minutes later and re-armed in turn, so two chains ran from then on. Not the hook, the task, or a switch change: the game's own path does the same when its callback is called out of schedule.

**Fix:** (1) the `pets` trigger removes the pending pool alarm before it runs the callback, so it takes that alarm's place; (2) a guard in the hook on both paths: a fire while the stored alarm is still due later (`AlarmManager.GetTimeLeft` > 0; at a genuine fire it is 0, and 0 while a build runs because the handle is clear) comes from a second chain and is dropped, which ends that chain (counter [207] `easpread_pets_extra_dropped`, log line `extra fire ... dropped`). Selftest: a model of the pool alarm (stored handle, clear, build in a task a tick later with sleeps, other code arming during a build, switch flips, mid-period triggers) keeps exactly one chain over 3,000 sim-minutes for 300 seeds with the fix, and reproduces the double chain without it.

**Lots and decay:** both are daily repeating alarms (`AddAlarmDay`) whose callbacks arm nothing of their own, so an out-of-schedule trigger runs one extra pass and adds no chain [verified]; the lot pass arms one extra one-shot stuck check per Sim (EA's helper, not repeating).

## 4. Relationship decay (`easpreaddecay`, built)

**What runs** [verified]: at 0:00 `DecayAll` walks every Sim in the relationship table (skipping long-distance friends) and, for each pair it owns (the Sim with the lower id), teaches household members and blood relatives about each other, skips genie-wish pairs, long-distance friends and boarding-school students, decays the romance visibility, skips pairs whose relationship state is younger than `MinHoursToHoldRelationshipState`, skips friendly pairs when either Sim is a super-friendly charisma master, moves liking toward 0 by the short- plus long-term decay (times `NPCRelationshipDecayMultiplier` when both are NPCs, distant-friend bit when it falls below Friend), decays the short-term context, and notes when a stranger/acquaintance pair reached 0 liking; pairs at 0 for `NumDaysAfterWhichZeroRelationshipIsDropped` are removed from both sides after the loop.

**Fix** (switch `easpreaddecay`, tuning `kEaSpreadDecay`, default off): the same per-pair step (the game's own methods for every change: `UpdateLiking`, `SetLiking`, `AddInteractionBit`, `DecayCurrentCommodityValue`, `LearnInfoAboutEachOther`, and by reflection the private `CanRelationshipDecayAway`, `DecayVisibility`, the genie flag and the zero-since date) a relationship at a time (`DailyPairPass`): the Sims in alarm order, each Sim's partners read at its turn, 96 relationships stepped or 2 ms per tick, the next tick resuming at the next partner of the same Sim (§4.1); drops applied at the end as `DecayAll` does. Every time check uses the alarm time, so a Sim handled ticks later decides as in the alarm tick. A pass still running when the next alarm fires is finished first, so no pair misses a day or gets two steps in one; switching off mid-pass finishes it at the next alarm before the game's own runs. Missing reflection members = log `Relationship members differ from the Steam build, off`, nothing patched.

**Same results:** each pair is stepped once per day, under the same owner, with the same inputs except relationships changed between the alarm and that Sim's turn (a pair that socialised in between is decayed after that, not before) [inferred, ticks apart]. A pair added after its owner's list was read is not stepped this pass, as in `DecayAll` (which reads each list at the Sim's turn); a pair removed or a Sim destroyed meanwhile is skipped. One step that throws is counted and the pass goes on (`DecayAll` would stop there).

**Selftest** (`node tools/selftest/easpread/run.ts`, PASS): (1) `SlicedPass` hands every item out once, in order, at every slice size 1-9 and list size 0-59, at least one item per slice, time budget honoured; (2) a model world of 40 Sims and ~300 pairs, decay = one unit toward 0, zero noted then dropped a day later at the end of the pass, decayed 12 days by `DailyPass` in random slices (often none before the next alarm) equals the one-tick reference after every finished pass and at the end, for 200 seeds, including the per-pair step count; (3) a Sim with 300 relationships is split over >= 18 slices of 16 pairs while it gains and loses relationships and another Sim is destroyed: pairs present throughout stepped once, removed ones 0 or 1 (by timing), added after the read 0, no pair twice; the time cap ends a slice after one pair. A mutant that drops the unfinished pass instead of finishing it fails all 200 seeds.

**Verify:** `easpreaddecayverify` logs a census on either path: relationships stored before/after, pairs with non-zero liking, sum of |liking|. Equality of two days cannot be shown in one load (each path decays a different day); the per-pair equality is the selftest's. Repro `bp-easpread-decay`.

### 4.1 Live repro 2026-10-21 (rc-first): drops and the longest tick

**Seen** [measured]: the game's pass (trigger, simmin 20353) dropped 4 (relationships 1202 -> 1198); ours dropped 0 at simmin 21324 (trigger) and 21611 (the real midnight alarm), relationships unchanged (1226, 1238); ours took 43/42 ticks, longest 9.5 / 4.6 ms against the 2 ms budget.

**Drops: no bug found** [verified by comparing with `DecayAll`]: EA drops a pair only when, after its step, liking is 0, the pair can decay away (stranger/acquaintance, not household, blood or work relation), and its zero date was set by an earlier pass at least `NumDaysAfterWhichZeroRelationshipIsDropped` (1) day before; a pass that finds it at 0 for the first time only sets the date, and any liking change clears it. The removal list is applied after the loop from both Sims' sides. Ours has the same conditions in the same order and the same end-of-pass removal (from both sides). In the repro our first pass ran 16 sim-hours after the game's (dates it set were < 1 day old), and the second was the real midnight, when only pairs noted at the previous midnight (simmin 20160, before the repro) could be due; the log cannot show whether any existed. **Added:** both paths now log `drops due at start N` (with `easpreaddecayverify`): the pairs `DecayAll`'s rules drop in a pass starting now (pairs already at 0 stay at 0 in the step, so this is known up front); ours must end with `dropped` = N, the game's with relationships before - after = 2N. The model selftest checks due = dropped on every day of 200 seeds.

**Longest tick: cause** [verified]: the slice budget was checked between Sims only; one Sim's whole relationship list ran inside one check (a Sim with a few hundred relationships, each pair with reflection calls and the household info step). **Fix** (Rodney's design: the budget counts relationships, not Sims): `DailyPairPass` steps one relationship at a time and checks 96 stepped pairs or 2 ms after each; a Sim with many relationships continues at its next partner in the next tick. Counters: [193] ticks, [194] longest tick (µs), [208] most relationships stepped in one tick; the log line gives both per pass. Expected longest tick ~2-3 ms (one pair's cost over the cap at most) [inferred].

**Risk:** a save while a pass runs, then loading that save, loses that day's step for the Sims not reached yet (the pass is not persisted) [inferred; seconds-long window]. Reflection calls cost more per pair than the game's direct calls; sliced, so no frame grows.

## 5. Object spawners (design only, not built)

**What runs** [verified]: each spawner has its own alarm (spawn frequency from its tuning, random in a range; gatherer-trait Sims nearby shorten it); `TriggerSpawn` tries one spawn and re-arms. Insect, rock/gem/metal and seed spawners call both `MinorPet.CanSpawnMoreMinorPetsInWorld` and `Wildflower.CanSpawnWildflowers` per try [verified: call graph]; each builds an array of every object of that type in the world (`Queries.GetObjects<T>`) and counts the uncaptured / uncollected ones up to a cap (wildflowers 20; minor pets from a per-device tunable).

**Measured:** the cost is these two world-wide queries (33 of 43 samples), not placement (2 of 43); docs/145's guess (placement search) is refuted [measured]. There is no batch: each spawner fires alone, so spreading does not apply.

**Design D1 (count first, exact):** before the array walk, ask the native count of all objects of the type (`Queries.CountObjects<T>`, exists); when the total is below the cap, the uncaptured count is too, so the answer is "yes" without the array. Same answer in every case; saves only when the world is under the cap. **D2 (tick memo):** keep each answer for the rest of the sim tick and drop it when any spawner creates an object; near-exact (a capture mid-tick is seen a tick later). Before either: one capture with a probe counter of cap checks per tick and the share of "under cap" answers (~15 min run), because the measured total (~1.8 s over ~32 h) is too small to justify a hook blind. Effort if the capture says yes: D1 ~30-60 min + 1 repro.
