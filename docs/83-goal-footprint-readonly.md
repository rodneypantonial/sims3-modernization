# 83. A read-only `GoalFootprintGather` for the locomotion caller (`0x85F5A0` -> `0x82F0B0`)

Written 2026-10-17. Static only, continues docs/81 and docs/82; the game was not run. Tools: Ghidra headless decompiles on a private copy of the docs/82 project (`game-copy/ghidra-gf`, read-only runs) and capstone 5 on `game-copy/bin/TS3W.exe` (Steam 1.67): a raw `E8`/`E9` caller index checked against instruction starts, a 5-hop forward closure that follows direct calls, function-pointer arguments and footprint vtable slots resolved through the 9 classes of docs/82 §3.1, and a non-stack write / `lock` / absolute-write / `Lock_Acquire` scan per function. Scratch scripts stay in the session scratchpad. `native/` was read, not changed.

Tags as in AGENTS.md: **[verified]** = read in the disassembly or decompile (address given); **[inferred]** = reasoning, to confirm with the §7 probes or the emulator.

## 1. Summary

- **First check the measurement.** `RouteFollow_EditPath 0x85F5A0` has two callers: locomotion (`Locomotion_ObstacleCheck 0x85FD10`, call `0x85FED7`, return `0x85FEDC`) and `0x85FF30` (return `0x85FFC7`), which `Route_PlanCommon 0x7606E0` calls at `0x760F92` **after** `Route_PlanLocked` returns at `0x760DE1`, once per path of a planned route [verified]. The G11 window opens when the `Route_PlanLocked` detour returns (`PlanLockedHook`, `ts3native.cpp` ~line 1099) and `vfG11CloseBy` keys a close by the return address of `0x82F0B0` only (`0x85F6CB`, the same for both callers). In a sync run the next `+0x918` touch after `Route_PlanLocked` is therefore almost always the same `IC_Route_Plan`'s own tail (`0x760F92 -> 0x85FF30 -> 0x85F5A0 -> 0x82F0B0`). In async mode that tail runs on the worker inside the job, which holds `+0x918` for the whole `IC_Route_Plan`, so it cannot close a window. Also, locomotion calls `0x82EDB0` (`0x85FE0B`) before `EditPath` in the same pass, yet `0x85FE10` barely appears among the closers. So the 94.7% / 96.9% is most likely the plan's own tail, not steering [inferred, strong]. **Re-key `vfG11CloseBy` by `EditPath`'s return address (or "inside `IC_Route_Plan` on this thread") before building anything (§7, probe P0).**
- **Read set** (§2, §4): world lot grid (`0xC688A0`), lot table buckets and nodes (`P+0x48..+0x50`), the lot entry (level base `+0x40`, quadtree vector `+0x74/+0x78`, transform `+0xA0..+0xD8`), quadtree Q (`+0x24`, `+0x38`, `+0x44`, counter `+0x48`, deferred flag `+0x4C`), tree nodes and leaf entry lists, `FootprintMapEntry` objects, footprint scalars (`+0x14/+0x18` id, `+0x34` class byte, `+0x35` type) and the level-0 polygon cache (`[fp+0x38]`).
- **Write set of the original** (§2): `+0x918`; `Q+0x48` plain `+1/-1`; deferred flush `0x666A40` (apply insert/remove: node split/merge, entry create/free, polygon rebuild `+0x70`); footprint refcounts `[obj+8]` plain, at 10 places on the gather path (§3); lot-table insert on a miss; set/vector allocations; in `EditPath`, polygon-cache rebuilds (`0x85FA50`, `+0xDC`, `+0xE8`, `+0xB8`). No managed call, remote call or world event within 5 hops of either function [verified, direct and resolved vtable edges].
- **Races** (§4): all of the original's writes race with the job, and one of them can free memory under the other thread. Without exclusion, the RO reads are **unsafe** (the memory can be freed) for the lot table, the lot entry vectors, Q, tree nodes, entries and polygon caches. They are only **stale** for footprint scalars, `Q+0x48/+0x4C` and the lot grid (the last is an existing race). **What keeps a footprint alive in the quadtree:** each `FootprintMapEntry` (vtable `0xFEAC7C`, 0x14 bytes) holds a counted reference at `entry+8`, taken in apply-insert at `0x665D99` and dropped only by the entry's destructor `0x61ED10`, which runs from apply-remove `0x666750` [verified]. So a footprint reached through a tree entry can be freed only inside apply-insert/remove.
- **Design (§6):** a sim-thread detour on `EditPath` (`55 8B EC 83 E4 F0`, 6 bytes) that, only for return `0x85FEDC` while a job runs, runs a read-only clone of `EditPath` and the gather under our reader/writer lock **QL** taken *shared with try-only* (never blocks). The clone uses no `+0x918`, no gate leaf, no `Q+0x48`, no flush, no refcounts and no cache rebuild. The worker takes QL *exclusive* inside 13 leaf mutators (12 new detours plus the existing `0x63CB90` gate stub). If anything is uncertain, the detour calls the original, which waits as today. The clone's code is closed at hop 4 (54 functions, all vtables resolved).
- **6-hop pass: not needed** for the read-only path (§8). Do probe P0 first.

## 2. What `0x82F0B0` does (Q1)

`thiscall(world)(start, goal, outVec, flag, opt, w)`, `ret 0x18` [verified `0x82F0B0..0x82F469`]. Steps: take `+0x918` (`lea ecx,[edi+0x918]` at `0x82F0C1`, `Lock_Acquire` at `0x82F0D0`); release and empty `outVec` (`FootprintRefVec_ReleaseRange 0xAAC090`); look up the goal's lot and, failing that, the start's (`World_LotLookup 0xC68990`, `ecx = [world+0x964]`), swapping the endpoints in the second case; with no lot, release and return 0. Otherwise it builds a stack query context: context at stack `+0x70`; `ctx+0x54` = lot (`0x82F1EF`); `ctx+0x40` points to an options block whose `+0` = `opt`, `+8/+0xC` = 0 and `+0x28` = 0; `ctx+0x44` = 0 (`0x82F2EE`); a "PortalCheckCache" hash; and a "GetFootprintsWithinNode/FootprintSet" red-black tree at stack `+0x34` (size at `+0x14`). Then it calls `LotRouting_FootprintsAlongSegment 0x631E20` (`ecx = P = [world+0x95C]`). If that returns true, it reserves `outVec` (`0x82BDB0`) and copies every tree element into `outVec`, sorted by sub-object pointer (`0x6D8BD0` lower bound, `0xAAE690` insert), with a temporary `+1` (`0x82F351`), a `+1` for the vector (`0x82F38F` or inside `0xAAE690`) and a `-1` (`0x82F3AA`, delete through sub slot 0 at zero). It frees the tree (`FootprintSet_FreeTree 0x6282F0`: `+0x94` release per node) and the hash (`0xD2BC10`), releases the options object atomically (`0x82F43E`; never set on this path), releases `+0x918` and returns 1 [verified].

`0x631E20`: `LotTable_Contains 0x628A90` (gate 13); `LotTable_GetCellGraph 0x62FB10` (Contains again, then `LotTable_GetOrInsert 0x62EAB0` (gate) and `entry+0x74[level - entry+0x40]`, where level = `start+8`); two transforms (`0x62ED40`, `GetOrInsert` plus the matrix at `entry+0xA0..+0xD8`); then `LotQuadTree_QuerySegment 0x667400` with `ecx = Q` and visitor context `ctx` if `ctx+0x44 != 0`, else NULL. **Here NULL** [verified `0x631EA4..0x631ED7` with the store at `0x82F2EE`]. `0x667400`: if `Q+0x48 < 1` it calls `FlushDeferred 0x666A40`; then `Q+0x48 += 1` (`0x66740F`), walk `QuadTreeCellPos_A 0x663B20` with visitor `0x662DD0` (flag 1, the value passed here) or `0x662DB0`, `Q+0x48 -= 1` (`0x667462`); it returns `set.size != 0`.

Walk and visitor [verified]: `0x663B20` iterates cells with a stack iterator array (`0x669BE0`, `0x669C30`, `0x669C20`, `0x66A040`, `0x61B7C0`), tests cells against the segment (`0x66A760`, `0x66A3B0`, `0x662EC0`) and calls the visitor; it writes only its stack. The visitor `0x662DD0 -> LotQuadTree_FootprintVisitor 0x669CD0` (`this` = cell iterator) works on the cell's node (`iter+0xC`). If the iterator byte `+0x1C` is set, it runs `CollectMasked 0x669230`, which keeps entries whose 64-bit mask has the bit `[0xFEDE48 + byte*4]`. Else, on a leaf (`(node+4)&3 == 0`), it runs `CollectLeaf 0x669850`. Else it runs `CollectChildren 0x669B90 -> 0x669B30`, recursing over the 4 children at `node+0xC..+0x18` down to the leaves. A leaf list is at `node+8`: inline when bit 0 is clear, else a heap array at `[node+8] & ~1` with count `node+0xC`; entries are 12 bytes (entry pointer, mask lo, mask hi). For each entry, with this caller's NULL context: footprint `obj = entry+8`; `+0x60` (true stub `0x9C1B00` in all classes); `+0x28` (false stub `0x620D60`; `0xFEAE08`: byte `+0x48`); class `c = +8(NULL, entry+0x10 byte)`; type `t = +0xC` (byte `+0x35`; `0xFEAE08`: 0xA). If `t == 0x1F`, it marks "seen" and skips the entry; if `t == 0x14`, it sets `c = 1`. If `c == 2`, the footprint goes to a local list (`0x6691F0`, `+0x90` AddRef); if `c > 1` and `c != 0xD`, it goes into the set (`FootprintSet_Insert 0x628340 -> 0x626B70`, `+0x90` at `0x626BCF`). At the end, if "seen", the local list joins the set; then every local entry is released (`+0x94`) [verified `0x669230`, `0x669850`, `0x620CA0`].

## 3. Locks, lock order, managed and remote calls (Q1)

Lock order inside the gather: `+0x918` first, then one of the leaves `wm+0x228` (lot index dirty), `0x11D9068` (last footprint reference dropped under the lock), `0x11CEFA8` (entry pool, flush path) or the allocator critical section. Nothing waits for `+0x918` while holding them [verified within the scanned closure]. Outside the lock, `EditPath` reaches the object lock `X+0xA0` (`0xB96380`, `0xB99150`, `0xB971F0`, hop 5) through a polygon rebuild of class `0xFEBD10` (docs/82). No call to `0xD75FA0`, `0xEA1400`, the managed slot `[0x1195B60]`, `RemoteCall_Dispatch 0x7D98C0` or `World_FireEvent 0x78F2B0` within 5 hops of `0x82F0B0` (118 functions) or of `0x85F5A0` (268) [verified]. ## 5. What `EditPath` does with the set (Q3)

`EditPath` is cdecl with 12 arguments (`wm, world, P, ids, start, goal, opt, exclude, ign1, n1, ign2, n2`) [verified uses `ebp+8..+0x34`]. Locomotion passes the **same node pointer as start and goal** (`push eax` twice at `0x85FECE`/`0x85FECF`), so the "segment" is a point. Before the gather it converts the nodes (`0x85AE60`, which reaches terrain height and `Lot_RoomLookup`); that code already runs today concurrently with jobs because it precedes the lock [verified order]. After the gather, for each element in vector order: `+1` (`0x85F7DE`); sub `+4` id and sub `+8` type, skipping types `0x14, 9, 0x11, 0xC, 0xD, 0x17`; skip ids in the ignore lists (`0x85AAA0`), ids already in `ids`, and ids of the `exclude` footprints (the `0x82EDB0` results of this pass). Then outer `+0xC0` (true for the 8 middle-derived classes, false for `0xFEAE08`): false or no lot means append the id. True means the level-0 segment test `+0xE8 0x80E690` (outer slot 0 = level count, `0x80E5B0` only if invalid, then `0x7CE550`/`0x7CD7E0`); false means skip, true means a polygon loop (`0x80E5B0` at `0x85FA50`, `+0xDC`, `0x85AC20`, `+0xB8`) **whose result is never read**, then append. The flag `[esp+0x17]` only ends the loop; `0x85FC31..0x85FC47` free the polygon vector and append unconditionally [verified]. So the polygon loop only warms the cache. Then `-1` and next; at the end, `0xAAC090` and `EA_Free` [verified].

No pointer outlives the call: the footprint vector is freed at `0x85F960/0x85F971` and only the 8-byte ids escape (`IdVec_PushBack 0x572400`) into the caller's per-tick list, which is rebuilt every tick [verified]. The ids go to agent `+0x60` and then to world event `0x3A` (§3). A stale set (the world in the middle of the job) differs from today's answer only by the job's own in-flight writes (portal re-flags, pending updates, lazy builds); the sim cannot move footprints during a job [inferred, docs/81 §4]. An empty set means no blocking ids for that node in that tick (docs/81 skip). A fallback to today costs exactly today's wait for that call, which is up to the rest of the job.

## 6. Read-only design (Q4)

**Sim detour S1** `RouteFollow_EditPath 0x85F5A0`, bytes `55 8B EC 83 E4 F0` (6, no relative operand), cdecl, `ret`. When it takes the RO path (all must hold): sim thread; return address `0x85FEDC`; a job is live (`g_async.state == A_RUNNING`); this thread does not own `+0x918` and is not in a job callback or gate frame; `[[world+0x964]+0x1CC] == 0` (lot index clean); `TryAcquireSRWLockShared(QL)` succeeds. Otherwise it jumps to the trampoline (today's behaviour). Inside RO, any of these sends it to *release QL, call the trampoline*: no lot found in the table, more than 512 hits, `Q+0x4C != 0 && Q+0x48 < 1` (the original would flush first), or a candidate with `[obj+0x38] == 0` or level-0 valid byte 0.

**Clone steps** (no writes outside our stack and the caller's `ids`):
1. `0x85AE60` twice, unchanged (already concurrent today).
2. Lot: `World_LotLookup 0xC68990` (ecx = `wm`) on the goal, else the start, with the swap as at `0x82F16C..0x82F1DD`.
3. Contains and find without the gates: if the lot id is 0, or both halves are `0xFFFFFFFF`, or it equals `[[0x11ECBC4]+0xB0]+0x48/+0x4C` (`0xC88FD0`), there is no answer. Else `LotTable_Find 0x627E00` (`ecx = P+0x48`): the node must not be the end bucket and must have key `node+0x10/+0x14`; then entry = `node+0x10`, the same pointer `0x62EAB0` returns on a hit.
4. Q = `entry+0x74[start.level - entry+0x40]`, bounds-checked against `+0x78`. Lot coordinates of start and goal are computed with the `0x62ED40` formula (x87, in the same order; the shadow check proves bit-exactness).
5. Fallback rule on `Q+0x4C/+0x48`; then call `0x663B20` directly (`ecx = Q`; arguments `0, sx, sy, gx, gy, 0.0, RoVisit, 0, &list`; `ret 0x24`).
6. `RoVisit` (stdcall, 3 arguments, returns 1) implements the visitor of §2 for the NULL context on the same node layout. It calls the original slots `+0x60`, `+0x28`, `+8`, `+0xC` and stores raw outer pointers in a fixed array: no `+0x90/+0x94`, no tree, no local list refcounts.
7. Sort and unique by sub pointer (`obj+4`), the order `0x6D8BD0`/`0xAAE690` produce [inferred; shadow check].
8. Consumer as in §5, without the refcounts and without the polygon loop: ids via sub `+4`, types via sub `+8`, `0x85AAA0`, the `ids` and `exclude` comparisons by id, `+0xC0`, then `+0xE8` (level 0, the lot coordinates from step 4 using the `0x62EF30` formula) after the valid precheck. Ids collect locally.
9. Release QL; append the ids with `0x572400` (the caller's vector, sim-owned).

**Original functions called unchanged** (pure under concurrent writes once QL is held): `0x85AE60` (existing concurrency), `0xC68990` and its callees with the dirty precheck, `0x627E00`, `0xC88FD0`, `0x663B20` and its iterator and cell-test helpers, the footprint slot targets (§8), `0x80E690` with the valid precheck, `0x7CE550`, `0x7CD7E0`, `0x85AAA0`, `0x572400`. **Replaced:** `0x82F0B0`, `0x631E20`, `0x62FB10`, `0x62ED40`/`0x62EF30` (gate leaves), `0x667400` (counter and flush), `0x662DD0 -> 0x669CD0` (refcounts), the set and vectors, and `EditPath`'s own refcount and polygon-loop code.

**Worker detours W1-W6** (worker thread with a job live only; elsewhere, jump straight on). Each one: if `depth++ == 0`, `AcquireSRWLockExclusive(QL)` and `qlSeq++`; release through a return thunk (the `RgLeaveThunk` pattern) when the depth drops to 0. All bytes were read from the exe; no relative operand.

| W6g | `+0x100 0x80CB40` / `0x806770` | `55 8B EC 83 E4 F0` (6 each) | `8` | classes `0xFEB848` / `0xFEB970` |

None of these addresses has a ts3native detour today except `0x63CB90` [verified grep]; run `tools/hook-sites.ts --check` against S3SS/S3PP before building. The slot table entries are the same in all 8 middle-derived classes and the middle table `0x1020AE8` [verified `.rdata` scan], so hooking the targets covers every caller, including the untraced `+0x18` callers (docs/82 §10). The valid-byte writer scan covered `0x805000..0x812000` only; anything outside it is caught by tripwire T3.

**Why no deadlock:** the sim never blocks on QL (try only), and it holds QL across no wait. Its only lock on the RO path is `wm+0x228` in a lot-index rebuild, and the precheck avoids that; even if a race lets it run, the rebuild waits for nothing that needs QL. The worker can wait inside QL (on `wm+0x228`, `X+0xA0`, a proxied managed callback in `LotGraph_Build`); the sim then fails its try-acquire and falls back to `+0x918`, whose pumping wait serves the proxy. The main thread never takes QL. **Cost:** worker, one uncontended SRW pair per leaf mutation (tens of ns) [inferred]; sim, the clone does less work than today's call (no refcounts, no polygon loop). The worker waits at most one RO call (µs) when the try-acquire wins.

**Why not a seqlock alone:** the visitor and consumer call vtable slots on footprints reached through nodes. A writer that frees a node in the middle of the walk turns those pointers into calls through freed memory, before any sequence check can run. The sequence counter `qlSeq` stays a tripwire only.

## 8. Closure check (Q6)

The read-only path closes at **hop 4**: 54 functions, no new function at hop 5 [verified with the closure scan]. Roots: the reused originals of §6 and the slot targets of every class for the slots used: `+0x60` `0x9C1B00`; `+0x28` `0x620D60`/`0x620DD0`; `+8` `0x80F840`, `0x807090`, `0x80C300`, `0x8066C0`, `0x807B70`, `0x6119F0`; `+0xC` `0x624450`/`0x70AE20`; `+0x7C` `0x806FE0`; `+0xC0` `0x7EAEA0`/`0x620D60`; `+0xE8` `0x80E690`; slot 0 `0x619EF0`/`0x83F5F0`; sub `+4` `0x620E60`, sub `+8` `0x624ED0`/`0x620E50`. Its only writes are our stack, out parameters (`0x627E00`, `0xAB8540`, `0xD4E550`, `0x66A3B0`) and the caller's `ids` (`0x572400 -> 0x572260`, allocator and `memmove`). There is no lock, `lock` write, absolute write, managed, remote or event call, and no unresolved vtable; `0x807090`'s `+0x7C` and `0x807B70`'s `+0xC` are resolved. Two guarded edges are not taken under the prechecks: `0x80E5B0` (valid byte) and `RebuildLotIndex` (dirty flag). With a NULL context the class slots read only footprint bytes; the vector reads in `0x807090 -> 0x946E90` sit behind `param != 0` [verified `0x80F850`, `0x807095`, `0x80C305`]. Excluded on purpose: `0x85AE60`'s terrain closure (open at hop 5, already concurrent with jobs today, unchanged).

**Recommendation: no 6-hop pass for the read-only path.** A 6-hop pass is needed only (a) if the sim must ever *block* on QL (then the worker's QL sections need a wait-free proof: `0x665C50`, `0x666750`, `0x63CB90`, `0x80E610`, `0x80E980`, `0x80EC30`, `0x80CB40`, `0x806770` and their `+0xF8` rebuild targets `0x80C200`, `0x80B060`), or (b) to extend RO to `0x82EDB0` (point walk `0x663E20`, visitor `0x662DB0`/`0x662DD0`; a one-function check, not a pass).

## 9. Open items and risks

1. P0 decides whether this is worth building (§1). If the tail `EditPath` carries the loss, async mode has already removed it, and the next sync closers to study are gate 10 (`0x75C2D0`) and quadtree reinsert.
2. Coverage of the worker writer list: anything that mutates nodes, entries, Q or caches outside W1-W6 (tripwires T3/T4); the valid-byte scan was range-limited.
3. Order of the id list (sorted by sub pointer, inferred); consumers probably do not depend on it.
4. Existing races this design does not add or fix: the lot grid read, sim-thread flushes without `+0x918` (`0x631FD0`, `0x82E340`) against the worker's walks, and `IC_Route_PlaceSocialFootprint -> 0x755EA0 -> 0x80C930` cache writes.
5. Footprint scalar writes by the portal re-flag (`0x632460`) while the lot is pinned give a stale class or type for one tick (bounded, no crash).
